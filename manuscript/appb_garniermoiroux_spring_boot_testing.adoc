= Beans and the ApplicationContext: dependency injection in Spring

Every time you hear about Spring, there will be a mention of "beans".
Most users will be familiar with the concept, and even newcomers have an understanding that these are "special objects managed by Spring".
These beans have a fundamental impact in testing, and it is worth exploring what they are exactly.

One the core technologies of Spring is it's _Inversion of Control container_, or IoC container for short.
It is designed for a specific form of IoC, called _Dependency Injection_ (DI).
The main idea of dependency injection is that if a instance of class A needs an instance of class B, say, as a field, instead of having A create B with `new B(...)`, that instance of B is passed to A, usually in a constructor, e.g. `public A(B instanceOfB)`.
This way, A does not need to care about how to create an instance of B, or B's dependencies are.
Furthermore, A can use any subclass of B. Let's say B is a data store, then there could be a JDBC-based implementation, an in-memory implementation, a Redis-based implementation, etc.
A does not need to decide which one should be used.

Spring, like other DI frameworks, allow you to express your objects and their dependencies without having to create them manually using their constructors such as  `new A(...)`.
You simply declare that you want an instance of A, which depends on B, and Spring figures out the dependency graph (A depends on B, which depends on C and D, etc.) and instantiates the objects for you.
All these objects, managed by Spring, are called _beans_.
To "declare" what you want, you provide Spring with _configuration metadata_.
In the early days, this was done through XML files, but today, you are likely creating Java code containing specific Spring annotations.
There is a myriad of ways to create beans in Java, with as many subtleties, but the most common ones are: using an annotation on a given class, and using a factory method.

To make a class a Spring bean, you annotate with one of the Spring stereotype annotations, such as `@Component`, `@Service`, `@Controller`, `@Repository`, etc.
For example:

[#ch2-di-component, reftext={appendix}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Creating a bean with an annotation
[source,java]
----
@Service // <1>
class FooService {

    private final BarRepository barRepository;

    public FooService(BarRespository barRespository) { // <2>
        this.barRepository = barRespository;
    }

}
----

1. This class is a Spring bean
2. It depends on another Spring bean, `BarRepository`

Through the constructor signature, you can express the dependencies of your `FooService`.

To create a bean using a factory method, you use the `@Bean` annotation on a configuration class, like so:

[#ch2-di-factory-method, reftext={appendix}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Creating a bean with an annotation
[source,java]
----
@Configuration // <1>
class FooConfiguration {

    @Bean // <2>
    FooService fooService(
            BarRespository barRespository  // <3>
    ) {
        // ... pre-processing ... <4>
        return new FooService(barRespository);
    }

}
----

1. This class contains beans
2. This method creates a Spring bean, `FooService`
3. It depends on another Spring bean, `BarRepository`
4. Any code you need to execute before creating your bean

Dependencies are expressed through the arguments passed to the factory method.
The factory can also use fields from the containing configuration class, which also expresses dependency.

NOTE: In this book, for brevity, we use the `@Configuration` annotation.
It is common to use it with a parameter `@Configuration(proxyBeanMethods = false)`, which is technically what most users want.
When the default value is used, which is equivalent to set `proxyBeanMethods = true`, Spring will wrap your factory methods in proxies and ensure they always return the same instance of a bean if you call the method directly.
This is rarely needed, so using `@Configuration(proxyBeanMethods = false)` will save you a bit of resources, however small.

The Spring IoC container is called the `ApplicationContext`, and is tasked with creating instances of these beans for your.
There are many implementations of `ApplicationContext`, with many specificities: some for web apps, others for annotatin-based configurations, etc.
In Spring Boot, the ApplicationContext is configured to scan your classpath: it finds your annotated classes, and, together with configuration that Boot provides, creates your bean in the correct order.
As it creates beans, it stores the instances in the container so they can be easily re-used.
Consider the very simple application definition:

[#ch2-simple-app, reftext={appendix}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.A simple application with 3 beans
[source,java]
----
@Configuration
class FooConfiguration {

    @Bean
    A a(B b, C c) {
        return new A(b, c);
    }

    @Bean
    B b() {
        return new B();
    }

    @Bean
    C c(B b) {
        return new C(b);
    }

}
----

The order in which you'd create the beans if yoy had to do it manually is trivial: B, because it has no dependencies, then C, because it only depends on B, and then A which depends on the other two beans.
However, for a complex application with many beans, this is much more complex.
You can see the general algorithm that Spring follows in figure <<appb-figure-2>>.

[#appb-figure-2, reftext={appendix}.{counter:figure}, caption='{figure-caption}.{counter:figure-number} ']
.The algorithm for creating beans used by Spring. On the left are the instructions that will be executed, in sequence. On the right is the state of the `ApplicationContext` at various points in the process, with the beans it contains.
image::appb_f002_garniermoiroux.png[]

This diagram shows how bean A is created.
Spring sees that it needs two dependencies, B and C, and tries to load them from the `ApplicationContext`.
Since they are not present, they will be created applying the same algorithm.
B, having no dependencies, will be created and then added to the context.
C depends on B, but by the time Spring creates C, B is already in the context and can be reused: no need to create another instance, reuse the existing singleton from the context.
A Spring Boot application will usually have tens or hundreds of beans in the context.
A lot of those are not beans are created by Spring Boot - for example, depending on your application, you'll find `HttpMessageConverter`, `RestClient.Builder` or `JdbcTemplate`, which you can inject in your own code.
Alternatively, you can register your own beans of a certain type: they will be added to the context, and Boot will back off and use your code instead of the packaged defaults.

In testing Boot applications, one of the techniques is to play with the application context and register beans selectively.
You can provide some test-specific configuration that represents a subset of the application you're trying to test, or take the full application but replace beans selectively.
You'll end up a with a "test application" fine-tuned for your needs.

NOTE: This appendix is a gigantic over-simplification of how the Spring IoC container works. We brushed anything beyond the most basic use case. How do you handle multiple beans of the same type? How does Spring determine bean dependencies? What if there are cyclic dependencies? We'd need several chapters to explore this topic in depth, and that's well beyond the ambitions of this humble book.
