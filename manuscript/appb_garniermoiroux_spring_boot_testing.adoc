= Beans and the ApplicationContext: dependency injection in Spring

Every time you hear about Spring, there will be a mention of _beans_.
Most users will be familiar with the concept, and even newcomers have an understanding that these are "special objects managed by Spring".
Some Spring Boot testing techniques include manipulating those beans, and it is worth exploring what they are exactly.

One of the core technologies of Spring is its _Inversion of Control container_, or IoC container for short.
It is designed for a specific form of IoC, called _Dependency Injection_ (DI).
The main idea of dependency injection is that if an instance of class FooService needs an instance of class BarRepository, that dependency is not created by FooService itself, but rather passed from the outside.
In practice, it would look something like:

[#appb-basics, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Dependency injection
[source,java]
----
interface BarRepository { } <1>

// Without dependency injection
class FooService {

    private final BarRepository barRepository;

    public FooService(BarRepository barRepository) {
        this.barRepository = new SqlBarRepository(); <2>
    }

}

// With dependency injection
class FooService {

    private final BarRepository barRepository;

    public FooService(BarRepository barRepository) {
        this.barRepository = barRepository; <3>
    }

}
----
<1> The dependency we want to inject
<2> Without DI, the dependency is created by FooService
<3> With DI, it is passed from the outside

There are drawbacks to not using DI.
For example `FooService` needs to be aware of the lifecycle of `SqlBarRepository`.
It is also difficult to use a different implementation of `BarRepository`.
With DI, `FooService` can accept alternative implementations of the repository, such as `InMemoryBarRepository` or `NoSqlBarRepository`.
And it does not need to even know which data storage is used in the repository, and does not need to decide.
The drawback is that you will need to instantiate both classes at the top level, for example:

[#appb-manual-injection, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Injecting the dependency
[source,java]
----
public class Main {

    public static void main(String[] args) {
        var barRepository = new SqlBarRepository();
        var fooService = new FooService(barRepository);
    }

}
----

This means you now need to track the order in which your dependencies are created.
This is cumbersome and leads to a lot of setup code.

Spring, like other DI frameworks, allows you to skip this "instantiation" step.
Instead, you express your object's dependencies, similar to what we did in listing <<appb-basics>>.
You simply declare that you want an instance of `FooService`, which depends on `BarRepository`, and Spring figures out the dependency graph (FooService depends on BarRepository, which might depend on C and D, etc).
Using this graph, it creates instances for you, and you do not need to call `new` explicitly.
All these objects, managed by Spring, are called _beans_.
To "declare" what you want, you provide Spring with _configuration metadata_.
In the early days of Spring, this was done through XML files.
These days, when you create new Spring apps, you are likely writing Java code, decorated with Spring annotations.
There are a myriad of ways to create beans with Java-based configuration, but the most common ones are using an annotation on a class declaration and using a factory method.

To make a class a Spring bean, you annotate with one of the Spring stereotype annotations, such as `@Component`, `@Service`, `@Controller`, `@Repository`, etc.
For example:

[#appb-component, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Creating a bean with an annotation
[source,java]
----
@Service <1>
class FooService {

    private final BarRepository barRepository;

    public FooService(BarRepository barRepository) { <2>
        this.barRepository = barRepository;
    }

}
----
<1>  This class is a Spring bean
<2>  It depends on another Spring bean, `BarRepository`

With the signature of the constructor, you can express the dependencies of your `FooService`.

To create a bean using a factory method, you use the `@Bean` annotation on a configuration class, like so:

[#appb-factory-method, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Creating a bean with an annotation
[source,java]
----
@Configuration <1>
class FooConfiguration {

    @Bean <2>
    FooService fooService(
            BarRepository barRepository  <3>
    ) {
        // ... pre-processing ... <4>
        return new FooService(barRepository);
    }

}
----
<1> This class contains beans
<2> This method creates a Spring bean, `FooService`
<3> It depends on another Spring bean, `BarRepository`
<4> Any code you need to execute before creating your bean

Dependencies are expressed through the arguments passed to the factory method.

NOTE: In this book, we use the raw `@Configuration` annotation with no parameters.
This is a shortcut, for brevity's sake.
It is extremely common to use it with a parameter, `@Configuration(proxyBeanMethods = false)`.
When the default value is used, which is equivalent to set `proxyBeanMethods = true`, Spring will wrap your factory methods in proxies and ensure they always return the same instance of a bean if you call the method directly.
This is rarely needed, so using `@Configuration(proxyBeanMethods = false)` will save you a bit of resources, however small.

The Spring IoC container is called the `ApplicationContext`, and is tasked with creating instances of these beans for you.
There are many implementations of `ApplicationContext`, with many specificities: some for web apps, others for annotation-based configurations, etc.
In Spring Boot, the ApplicationContext is configured to scan your classpath: it finds your annotated classes, and, together with configuration that Boot provides, creates your beans in the correct order.
As it creates beans, it stores the instances in the container so they can be easily re-used.
Consider the very simple application definition:

[#ch2-simple-app, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.A simple application with 3 beans
[source,java]
----
@Configuration
class FooConfiguration {

    @Bean
    A a(B b, C c) {
        return new A(b, c);
    }

    @Bean
    B b() {
        return new B();
    }

    @Bean
    C c(B b) {
        return new C(b);
    }

}
----

This can be visualized as a graph.
The nodes are our bean instances, and the edges are the dependencies between beans.
This is illustrated in figure <<appb-figure-1>>.

[#appb-figure-1, reftext={chapter}.{counter:figure}, caption='{figure-caption}.{counter:figure-number} ']
.The dependency graph of our simple bean application
image::appb_f01_garniermoiroux.png[230,580]

For such a trivial example, the order in which you would instantiate those beans is obvious: first B, because it has no dependencies, then C, because it only depends on B, and finally A which depends on the other two beans.
For a more complex example, you would apply an algorithm.
For example, start with the leaf nodes, that have no dependencies - in this case, B. Then, for the remaining beans in the graph, create nodes that only need dependencies that were already instantiated - in this case, C.
Rinse and repeat until all instances have been created.
Spring follows a different approach, starting from an entry point and recursively creating nodes as needed.
You can see the general algorithm in practice in figure <<appb-figure-2>>.

[#appb-figure-2, reftext={chapter}.{counter:figure}, caption='{figure-caption}.{counter:figure-number} ']
.The algorithm for creating beans used by Spring. On the left are the instructions that will be executed, in sequence. On the right is the state of the `ApplicationContext` at various points in the process, with the beans it contains.
image::appb_f02_garniermoiroux.png[]

This diagram shows how bean A is created.
Spring sees that it needs two dependencies, B and C, and tries to load them from the `ApplicationContext`.
Since they are not present, they will be created applying the same algorithm.
B, having no dependencies, will be created and then added to the context.
C depends on B, but by the time Spring creates C, B is already in the context and can be used: no need to create another instance, get the existing singleton from the context and inject it.
A Spring Boot application will usually have tens or hundreds of beans in the context.
A lot of those beans do not come from your Java configuration.
Instead, they are created by Spring Boot - for example, depending on your application, you'll find `HttpMessageConverter`, `RestClient.Builder` or `JdbcTemplate`, which you can inject in your own code.
If you don't like the defaults that Spring Boot provides, you can register your own beans of a certain type: they will be added to the context, and Boot will back off and use your code instead of creating default beans.

In testing Boot applications, one of the core techniques is to leverage the application context and register beans selectively.
You can provide some test-specific configuration that represents a subset of the application you're trying to test, or take the full application but replace some beans by test-specific variants.
By doing this, you can prune branches from your dependency graph, when you do not need to test it in detail.
You'll end up a with a "test application" fine-tuned for your needs.

NOTE: This appendix is a gentle introduction to how the Spring IoC container works.
It is a massive oversimplification, and we brushed aside anything beyond the most basic use case.
How do you handle multiple beans of the same type?
How does Spring determine bean dependencies?
What if there are cyclic dependencies?
We'd need several chapters to explore this topic in depth, and that's well beyond the ambitions of this humble book.
