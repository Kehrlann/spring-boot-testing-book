= Testing a Spring Boot "Hello World" application

This chapter covers:

* Interacting with your application inside a `@SpringBootTest`
* Decoupling from external dependencies with mocks
* Factoring common setup with JUnit
* Deciding when (not) to use `@SpringBootTest`

When you create a project on Spring Initializr, also known as https://start.spring.io, you get testing libraries bundled in, as we mentioned in the previous chapter.
There is also a single test file bundled in your project, ready to execute.
It contains a single test method, which is empty, and the only thing it validates is that the application can start.
This has value in and on itself, as it validates your Spring dependency graph, and your Spring Boot properties.
Having this test file also makes it easy to add your own tests, without too much to decide: the next logical step is to add another method to this test file.

It's a good start, but where do you go from here?
When writing "integration" tests, there are a few key points that structure how your test suite will look like.
You need some specific code to interact with your test application, and perform actions such as HTTP requests.
Then you will want to check the result of your actions, through return values and the internal state of the test application.
If there are dependencies outside the scope of your code, you must avoid using those and replace them with some test-specific code.
And, as you add tests and your test suite grows in size and complexity, it will call for some reuse to keep the sprawl under control.

In this chapter, we will look at a very basic application and work through what Spring Boot Test has to offer to address all those needs.
While we will not go deep on any of the particular solutions, we will paint a broad picture of what the structure of a Spring Boot Test is, and what the basic building blocks look like in practice.

== Adding your first test

Before diving deep into the features of our application, let's ensure that it responds to HTTP requests on the index page, or `/`, and that it displays _something_.
This tells you that there is an actual `/` endpoint, and that it does, indeed, render an HTML page.
To do so, you need to make HTTP calls to your application.
Spring has useful tools for making this easy, as show in listing <<ch2-listing-first-test>>.

[#ch2-listing-first-test, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
[source,java]
----
include::../code/ch2/weather/src/test/java/wf/garnier/spring/boot/test/ch2/weather/ExampleTests.java[tags=annotations;class;mock-mvc-tester;first-test]
----

<1> The test is a Spring Boot Test.
<2> Make `MockMvcTester` available in the test method.
<3> Use `MockMvcTester` to make an HTTP request.
<4> Verify the data from the response.

There is a lot to unpack in this test.
First, the class is annotated with `@SpringBootTest`, just like the previous test.
This means that, before running any of the tests in this class, a test application will be started, based on your `@SpringBootApplication` class.

Second is the presence of `@AutoConfigureMockMvc`, which makes a `MockMvcTester` bean available in your test.
That class is a utility class that allows you to make requests targeting the test application.
Notice that you can ignore the host and port where the app runs on when making HTTP requests: you only specify the method and path, in this case `GET /`.
Also notice that it has a nice fluent API, which is both simple and very explicit.

Lastly, a word on the structure of the test method itself: most of our tests will be written in some form of the classic "Arrange/Act/Assert", or "Given/When/Then".
This is a common way to write tests, spelling out three parts:

* **Arrange:** Set up the data and code you need to run your tests.
In the previous example, there's nothing in particular to set up
* **Act:** Run the action or set of actions you want to test.
Here, we are fetching the index page of the application.
* **Assert:** Verify that the action has the intended result or consequence.
Here, we ensure the response to the request is `HTTP 200`, and that the returned page contains an HTML header with "Weather App".
To do this, we use the AssertJ assertion library, which integrates nicely with Spring's `MockMvcTester`.

== Factoring common setup with JUnit

Now, imagine you want to add a test that shows that a city can only be present a single time in the selection database, and that there is no duplication.
The structure of the test is fairly simple: add the same city twice, and ensure that there is only one entry in the database.
Using our `selectCity(...)` help method from the previous section, we can write the test in listing <<ch2-listing-no-duplicates>>.

----

Running this test by itself works.
But if all the tests in the file, it will run both `noDuplicates` and  `addSelectedCity` test from section <<ch2-section-4>>, which both add a city.
And both expect there to be a single city in the database, so at least one of them is going to fail.
There are multiple ways to fix this issue.
You could order the tests, and expect one city, then two cities in the second test, etc.
That's additional context that you would need to keep in mind while writing tests, and you would not be able to run them independently anymore: each test depends on the previous test to run to succeed.
You could also count the number of cities at the beginning of each test and ensure it increases by 1, but that's more code to read to understand the goal of a specific method.
Or you could ensure that the database is empty before running each test, for example by calling `selectionRepository.deleteAll()` at the beginning of each test.
This works fine, but you need to remember to add it to every test, and as your suite grows, so does the duplication.

Fortunately, you can fold common setup code with JUnit, resulting in listing <<ch2-listing-before-each>>'s method, which will be executed before every test.

Running the whole file should now pass, and running each method independently still works.
By force of habit, "before each" methods are often called `setUp()`, which was a requirement in JUnit 3 and earlier.
In modern versions of JUnit, you can have as many `@BeforeEach`-annotated methods as you want, and you can use any name you want.

== Decoupling from external dependencies with mocks

So far, none of the tests we have written make use of the external Open-Meteo API, represented by the `WeatherService` class.
But gathering weather data is a core feature of our application!
Let's write a test that ensures that our application returns the correct data.
To avoid parsing the HTML page to find the data we care about, we will use the JSON API that the application provides.
It should return a response that looks something like this: `{"cityName": "<SOME CITY>", "temperature": <SOME TEMPERATURE>}`.
Putting it all together, we can write listing <<ch2-listing-weather-data>>.

----

The structure is familiar: ensure that the city is selected (arrange), call the `/api/weather` endpoint (act), and verify that the result has the correct values (assert).
The assertion here uses `MockMvcTester` 's support for AssertJ, and some JSON-compatible extensions.
With that, you can easily compare JSON structures and avoid the usual issues of string-based comparisons, such as the order of properties, or the exact spacing and new lines.

While this test looks reasonable, it will only pass when the reported temperature is _exactly_ 22.6 degrees.
That's a problem!
You could, of course, rework the test to assert that "a temperature value" is returned, in a number format.
Maybe you could even ensure that it's within a reasonable range, say -30 to +50 Celsius, but this would mean more code, and the method would be harder to understand.
And if you did this, you would have another class of issues, that stem from relying on an external system for running your tests.
If the API provider goes down, the test fails every time, even if you have error-handling code.
If the network is unstable, your test becomes flakey, less deterministic, and therefore less useful.
Running your tests would eat up in your daily API calls quotas.
And you'd add tens or hundreds of milliseconds of latency to every test.
Generally, it's considered bad practice to call out to external services during tests, unless you're doing end-to-end testing.
Instead, you should be providing an alternative implementation, that you can program, and that returns predictable results, often called "stubs" or "mocks".
Spring Boot Starter Test brings the Mockito dependency, and the Spring framework has hooks to integrate it seamlessly in Spring Boot tests.
We can replace beans the application context with a mock, and configure it to return the results that we want, as show in listing <<ch2-listing-mocks>>.

The test is now decoupled from the external dependency, making it deterministic and predictive.

== A word of caution: when NOT to use `@SpringBootTest`

This book is all about Spring Boot Test, and you will see the `@SpringBootTest` across many examples.
When the application is small enough, such as with our weather application example here, testing everything through Spring Boot Tests is reasonable.
However, the bigger the application, the more complex the features, the harder it is to test it in its entirety through integration tests.
You will need to introduce unit tests, focused on smaller pieces of logic.
As we've discussed in chapter 1, at that level, you should not be running a Boot application to verify behavior.

Imagine that our weather is much more complex, and has a full "travel recommendation" engine, taking many parameters into account to suggest some holiday plans, such as travel type and cost, lodging costs, weather history averages, user preferences, etc.
The general scoring is complex, and testing all possible variations from the final API endpoint would require setting up 8 different data sources for each case, with subtle variations for each.
It is simpler to break the problem into simpler chunks, that you can reason about independently.
For example, one `@Service WeatherScoringSerivce` class generates an aggregate score based on weather history, and user preferred temperature ranges.
For testing all the possible variations, you would write unit tests.
To give you an idea of what those tests could look like, see listing <<ch2-unit-test>>.

[#ch2-unit-test, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
[source,java]
----
@Test
void temperatureHistoryAboveAcceptableRange() {
  var data = WeatherHistoryData
      .withDataPoint(2022, 6, TemperatureRange.min(12).max(32))
      .withDataPoint(2023, 6, TemperatureRange.min(9).max(24))
      .withDataPoint(2024, 6, TemperatureRange.min(10).max(23));
  var userPrefs = UserPreferences
      .acceptableRange(5, 30)
      .preferredRange(15, 25);
  // Omitted: configure mocks to return data above
  var weatherService = new WeatherScoringService(
          mockWeatherService,
          mockUserPreferenceRepository
  );

  var score = weatherScoringService.score("Paris", 6);

  assertThat(score).isEqualTo(0);
}
----

This is a perfect example of tests that you should not make into Spring Boot Tests.
It focuses entirely on a simple feature with complex behavior, in this case "weather scoring".
You do not need to set a full dependency tree of mock for hotel prices, train comparison, etc.
By keeping it decoupled from the rest of the application, it keeps it straight to the point, easy to reason about, and easy to duplicate to test for other things: when the temperatures go below the acceptable range, the score variations for when they are always in the preferred range vs only sometimes, what happens when there is no historical data, etc.

== Summary

- Spring projects generated on https://start.spring.io provide you with a single test, which is a great place to start writing your own integration tests.
- A `@SpringBootTest` automatically finds your main class annotated with `@SpringBootApplication`, runs it, and makes it available in your test code.
- `MockMvcTester` is a test utility to test the HTTP endpoints of your application, whether they return HTML or JSON.
- With JUnit, the test framework offered by Spring Boot Tests, you can reuse your setup code.
- With Spring Boot Test's Mockito integration, you can replace beans in your application and stub out external services.
- The `@SpringBootTest` should not be used for all kinds of tests.
When you want to test complex features with many variables, unit tests are better suited to the task.
