= Testing a Spring Boot "Hello World" application

This chapter covers:

* Interacting with your application inside a `@SpringBootTest`
* Factoring common setup with JUnit
* Decoupling from external dependencies with mocks
* Deciding when (not) to use `@SpringBootTest`

When you create a project on Spring Initializr, also known as https://start.spring.io, you get testing libraries bundled in, as we mentioned in the previous chapter.
There is also a test class in the zip file containing your project, ready to execute.
It contains a single test method, which is empty, and the only thing it verifies is that the application can start.
This has value in and on itself, as it validates your Spring dependency graph, and your Spring Boot properties.
Having this test class also makes it easy to add your own tests, without having too much to decide: the next, obvious step is to add another method to this test file.

It's a good start, but where do you go from here?
When writing "integration" tests, there are a few key points that structure what your test suite will look like.
You need some specific code to interact with your test application, and perform actions such as HTTP requests.
Then you will want to check the result of your actions, through return values and the internal state of the test application.
If there are dependencies outside the scope of your code, you must avoid using those and replace them with some test-specific implementation.
And, as you add tests and your test suite grows in size and complexity, it requires some reuse to keep the sprawl under control.

Now, let's look at a very basic application and work through what Spring Boot Test has to offer to address all those needs.
While we will not go deep on any of the particular solutions, we will paint a broad picture of what the structure of a Spring Boot Test is, and what the basic building blocks look like in practice.

== Our test subject: sample application

Before you add tests, you need _something_ to test.
Even if you did test-driven development, you would need to decide _what_ you are going to build before writing tests.
This book is about writing tests, so we will not be explaining how to build the applications we will use as examples for our tests.
Instead, you can download the test applications at https://github.com/Kehrlann/spring-boot-testing-book-samples/.
Each chapter will have one or more dedicated projects, located in a directory with the chapter number, e.g. `ch02`.
To run the examples, you will need Java 25, the latest LTS version.

Before we start discussing, let's get familiar with the application under test.
For this example, you will use a simple web page that displays the weather and temperature for cities.
The user can select the cities they want to display in their dashboard, and the weather is fetched in real time from https://open-meteo.com.

NOTE: The applications in this book are demo apps, and are not meant to be production-grade quality.
As such, there might be shortcuts taken here and there, and some best practices may be overlooked.
Please take the implementation of those apps with a grain of salt.

First, get the source code in the samples in the `ch2/weather` directory, or directly from https://github.com/Kehrlann/spring-boot-testing-book-samples/tree/main/ch2/weather.

Then run the application, for example by running the Maven wrapper command:

----
./mvnw spring-boot:run
----

In this mode, the application uses weather data from the Open-Meteo API.
If you'd like the application to run locally without relying on an external API, you can use a "fake" API that returns random weather, by running it with the `local` profile:

----
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
----

Once it is running, you can access it by navigating to `http://localhost:8080`.

== Adding your first test

Before diving deep into the features of this weather dashboard website, let's ensure that the Spring Boot application responds to HTTP requests on the index page, or `/`, and that it displays _something_.
This tells you that have created the appropriate mapping for the `/` path, and that it does, indeed, render an HTML page.
To do so, you need to make HTTP calls to your application.
This is such a common scenario that Spring Boot Test has specialized utility classes for this, such as `MockMvcTester`:

There is a lot to unpack in this test.
First, the class is annotated with `@SpringBootTest`, just like the example in the previous section.
This means that, before running any of the methods in this class, a test application will be started, based on your `@SpringBootApplication` class.

Second is the presence of `@AutoConfigureMockMvc`, which makes a `MockMvcTester` bean available in your test.
It is a utility class that allows you to make requests targeting the test application.
Notice that you can ignore the host and port where the app runs on when making HTTP requests: you only specify the method and path, in this case `GET /`.
Also notice that it has a nice fluent API, which reads well and keeps the intent clear by only showing what is necessary to make such a request.

Lastly, a word on the structure of the test method itself: most of our tests will be written in some form of the classic "Arrange/Act/Assert", or "Given/When/Then".
This is a common way to write tests, spelling out three parts:

* **Arrange:** Set up the data and code you need to run your tests.
In the previous example, there's nothing in particular to set up, so this step is empty.
* **Act:** Run the action or set of actions that trigger the behavior you want to verify.
Here, we are fetching the index page of the application.
* **Assert:** Verify that the action has the intended result or consequence.
Here, we ensure the response to the request is `HTTP 200`, and that the HTML page it returns contains a header with the words "Weather App".
To do this, we use the AssertJ assertion library, which integrates nicely with Spring's `MockMvcTester`.

NOTE: To learn more about MockMvcTester, refer to chapter 4, "Testing web applications".
To ramp up on AssertJ, refer to chapter 10, "Writing elegant tests with Spring Boot’s bundled testing libraries".

Now that we have a full test, albeit very basic, we have a foundation we can build on.
Let's expand our scope and start testing actual features that are implemented in our Spring beans.

== Accessing context dependencies

The previous test was extremely simple, and did not demonstrate any weather-related features in our application, one that we would describe in detail in a "feature request", "ticket" or "user story".
It was a read-only test, one that does not add any data to the database.

To write the assertions for such a test, we could check that the resulting page contains the name of the city we have added, but it could be a bit brittle: for example, that city name is somewhere else on the page and the test would pass even if no city was selected.
In a more advanced use-case, we would parse the page to ensure that the correct HTML representing the city and its weather data are present.

Running this test by itself works.
But if you run all the tests in the file, JUnit will execute both `noDuplicates` and  `addSelectedCity` test from section <<ch2-section-4>>.
They both add a city, and expect that there is a single entry in the database.
But the second test that runs will now find two cities, and will fail.
There are multiple ways to fix this issue.
You could order the tests, and expect one city in the first test, then two cities in the second test, etc.
That's additional context that you would need to keep in mind while writing tests, and you would not be able to run them independently anymore: each test depends on running the previous test to succeed.
You could also count the number of cities at the beginning of each test and ensure it increases by 1, but that's more code to read to understand the goal of a specific method.
Or you could ensure that the database is empty before running each test, for example by calling `selectionRepository.deleteAll()` at the beginning of every test.
This works fine, but you need to remember to add the cleanup every time, and as your suite grows, so does the duplication: you will end up big chunks of cleanup code, repeated multiple times.

Fortunately, you can fold common setup code with JUnit, resulting in listing <<ch2-listing-before-each>>'s method, which will be executed before every test.

== Decoupling from external dependencies with mocks

So far, none of the tests we have written make use of the external Open-Meteo API, represented by the `WeatherService` class.
But gathering weather data is a core feature of our application!
Let's write a test that ensures that our weather dashboard displays the correct information.
To avoid parsing the HTML page to find the exact elements we want to verify, let's take a shortcut and use the JSON API that the application provides.
It should return a response that looks something like this: `{"cityName": "<SOME CITY>", "temperature": <SOME TEMPERATURE>}`.

The structure is familiar: ensure that the city is selected (arrange), call the `/api/weather` endpoint (act), and verify that the result has the correct values (assert).
The assertion here uses `MockMvcTester` 's support for AssertJ, with its JSON-specific extensions.
With that utility, you can easily compare JSON structures and avoid the usual issues of string-based comparisons, such as the order of properties, or the exact spacing and new lines.

While this test looks reasonable, it will only pass when the reported temperature is _exactly_ 22.6 degrees.
That's a problem!
You could, of course, rework the test to assert that "a temperature value" is returned, in a number format.
Maybe you could even ensure that it's within a reasonable range, say -30 to +50 Celsius, but this would mean more code, and the method would be harder to understand.
And even if you did this, you would still have to deal with a whole class of issues that stem from relying on an external system in your tests.
If the API provider goes down, the test fails every time, even if you have error-handling code.
If the network is unstable, your test becomes flakey, less deterministic, and therefore less useful.
And your tests would eat up in your daily API calls quotas.
And you'd add tens or hundreds of milliseconds of latency to every test.
Generally, it's considered bad practice to call out to external services during tests, unless you're doing end-to-end, full-system testing.
Instead, you should be providing an alternative implementation, that you can program, and that returns predictable results, often called a "stub" or a "mock".
Spring Boot Starter Test brings the Mockito dependency, and the Spring framework has hooks to integrate it seamlessly in Spring Boot tests.
We can replace beans the application context with a mock, and configure it to return predictable results, as shown in listing <<ch2-listing-mocks>>.

== A word of caution: when NOT to use `@SpringBootTest`

This book is all about Spring Boot Test, and you will see the `@SpringBootTest` annotation across many examples.
When the application is small enough, such as with our weather application example here, testing everything through Spring Boot Tests is reasonable.
However, the bigger the application, the more complex the features, the harder it is to test it in its entirety through integration tests.
You will need to introduce unit tests, focused on smaller pieces of logic.
As we've discussed in chapter 1, at that level, you should not be running a Boot application to verify behavior.

Imagine that our weather app is much more complex, and has a full "travel recommendation" engine, taking many parameters into account to suggest some holiday plans, such as travel type and cost, lodging costs, weather history averages, user preferences, etc.
The general scoring is complex, and testing all possible variations from the final API endpoint would require setting up N separate data sources for each case, with subtle variations for each.
It is simpler to break the problem into smaller chunks that you can reason about independently.
For example, we could introduce one `@Service WeatherScoringSerivce` class that generates an aggregate score based on weather history, and user preferred temperature ranges.
For testing all the possible variations, you would write unit tests.
To give you a rough idea, these tests could look something like this:

[#ch2-unit-test, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.A sample domain test without Spring-specific testing tools.
[source,java]
----
@Test
void temperatureHistoryAboveAcceptableRange() {
  var data = WeatherHistoryData
      .withDataPoint(2022, 6, TemperatureRange.min(12).max(32))
      .withDataPoint(2023, 6, TemperatureRange.min(9).max(24))
      .withDataPoint(2024, 6, TemperatureRange.min(10).max(23));
  var userPrefs = UserPreferences
      .acceptableRange(5, 30)
      .preferredRange(15, 25);
  // Omitted: configure mocks to return data above
  var weatherService = new WeatherScoringService(  // <1>
          mockWeatherService,  // <1>
          mockUserPreferenceRepository  // <1>
  );  // <1>

  var score = weatherScoringService.score("Paris", 6); // <2>

  assertThat(score).isEqualTo(0);
}
----

<1> Create object under test with the `new` keyword
<2> Call instance methods directly

This is a perfect example of tests that you should not make into Spring Boot Tests.
It focuses entirely on a single feature with complex behavior, in this case "weather scoring".
In some styles of software architecture, this would be called a "domain" test, or "application core" test.
You do not need to carefully create a full dependency tree of mocks for hotel prices, train comparison, etc.
By keeping the Service under test decoupled from the rest of the application, it keeps the test straight to the point, easy to reason about, and easy to duplicate for all your other test cases: when the temperatures go below the acceptable range, the score variations for when they are always in the preferred range vs only sometimes, what happens when there is no historical data, etc.
In terms of code, this setup means you can simply create the Service by calling `new` and passing dependencies to the constructor explicitly, without relying on the Spring "Inversion of Control" container and its autowiring capabilities.
By calling methods directly, you do not need HTTP-specific tooling such as `MockMvcTester`.
Lastly, since you are mocking all services and repositories, the test does not require a data layer or a database abstraction.
By not using any of the Spring features, your test is much leaner, does not require a lot of setup and is easier to maintain.
And, crucially, it does not start a Spring Boot app, so you get the results in milliseconds rather than seconds.
So, before you reach for the `@SpringBootTest` annotation, take a pause, and decide whether you are writing an integration test, that requires Spring-specific tooling, or just a simple unit test.

== Summary

- Spring projects generated on https://start.spring.io provide you with a single test, which is a great place to start writing your own integration tests.
- A `@SpringBootTest` automatically finds your main class annotated with `@SpringBootApplication`, runs it, and makes it available in your test code.
- `MockMvcTester` is a test utility to test the HTTP endpoints of your application, whether they return HTML or JSON.
- With JUnit, the test framework offered by Spring Boot Tests, you can reuse your setup code.
- With Spring Boot Test's Mockito integration, you can replace beans in your application and stub out external services.
- The `@SpringBootTest` annotation should not be used for all kinds of tests.
When you want to test complex features with many variables, unit tests are better suited to the task.
