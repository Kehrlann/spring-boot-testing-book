= Testing Configuration and Properties

This chapter covers

* Injecting property values in test classes
* Testing property validation logic, including failure cases
* Deciding when to test Configuration and Property classes

Spring Boot has many built-in options for configuring your application, from selecting the port it runs on to setting up a connection to a database.
The same infrastructure is also available for configuration options you create, declared through `@ConfigurationProperties`-annotated classes.
This allows anyone running your application to set it up for their own use-cases.
For example, in our "weather app" sample, you could make the URL of the external weather service configurable.
You could also imagine more complex use-cases, such as enabling caching only when a key-value store is available.
To implement either of those features, you'd need to write code, in one case to add properties and validate them, in the other to react to existing Spring Boot properties with custom configuration.

Configuration code is slightly different from what we've tested so far, as it is usually only exercised once at startup and may stop your application from running if even a single user-provided value is invalid.
Think of a database URL, for example: if users point their Spring application to a non-existent database, it won't even start.
As such, there are specific techniques for testing configuration code.
And, of course, Spring Boot Tests has dedicated utilities to make your life easier!

[#ch6-section-injecting-properties-into-test-classes, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== Injecting properties into test classes

To test configuration properties, you need to write tests that run your application with different options, and then write assertions against each variant.
This requires passing the settings you're verifying to the test framework.
Spring Boot Tests has four main APIs to achieve this.

But before we jump into our first tests, let's revisit our trusty weather application, with its brand-new configuration options.
You can find the complete code under `ch6/weather`, or directly at https://github.com/Kehrlann/spring-boot-testing-book-samples/tree/main/ch6/weather.
As usual, you can run the project with `./mvnw spring-boot:run`, and access the application at http://localhost:8080.
For end users, there is a single new feature: the weather cards now display the temperature in blue when it's below a certain "cold threshold", and in red when it's above the equivalent "hot threshold".

The main difference from the previous chapter is less visible, though.
When someone (say, an admin) runs our application, they can configure it well beyond Spring Boot defaults like the server port.
First, they can set the defaults for the preferences in the app: dark mode, unit system and whether cities are sorted alphabetically or by date added.
For example, the administrator can decide that, by default, the website is in dark mode.
When the user has not expressed their preferences, they get the default set by the administrator.
A flow chart helps visualize the behavior for preferences:

There is a predetermined maximum range, such that cold cannot be set below -90˚C, and hot must not be over 57˚C (both sitting at the extremes of temperatures recorded on Earth).
And, of course, the cold threshold must be below the hot threshold.

They are all mapped into a `@ConfigurationProperties` class called `PreferencesProperties`.

NOTE: This "mapping" of configuration files into beans is a feature of Spring Boot.
To learn more, please refer to the https://docs.spring.io/spring-boot/reference/features/external-config.html#features.external-config.typesafe-configuration-properties[Reference documentation].

To test how the configuration impacts the code, we need to create a test app with specific configuration properties.
The simplest thing you can do is write an `application.properties` file (or its YAML equivalent) in your test resources folder `src/test/resources`, but beware!
This overrides the file of the same name from your _main_ sources directory, possibly leading to a lot of duplication and configuration drift between prod and tests.
If you want to touch only a few values in your tests, you should use one of the dedicated APIs for property loading.
At the time of this writing, Spring Boot lists 15 ways (!) of loading configuration properties into an application.
Most of them are for production use, but some can be used in tests, including:

* The `properties` parameter in `@SpringBootTest`
* The `@TestPropertySource` annotation, pointing to a file
* The `@ActiveProfiles` annotation and profile-based configuration files

There is a fourth option, which we will not be discussing here: `@DynamicPropertySource` and `DynamicPropertyRegistrar`.
They allow injecting properties representing resources whose lifecycle is managed outside your application.
They were originally designed for Testcontainers, and we'll discuss them in depth later, in chapter 9, "Testing against real service dependencies with Testcontainers".

TIP: To learn all about Spring Boot configuration management, take some time to go over the https://docs.spring.io/spring-boot/reference/features/external-config.html[Externalized Configuration] section in the Spring Boot reference.
You'll likely discover options you've never heard of before.

Let's demonstrate the three most prominent alternatives.
We'll write a test that verifies that our app respects the defaults expressed in a configuration file.
The most obvious one is using the `@SpringBootTest` annotation with some properties inlined, as we've seen before:

This is the simplest form of configuring the application under test: passing whatever properties you want to test directly in the annotation as a string.
Once the test context is up and running, we verify that, when the user has not set preferences, the `PreferencesService` returns the defaults configured by the admin, here dark mode and imperial units.
In this sample test, we are using a text block with properties on each line, but you can just as well write one string per property:

[source,java,indent=0]
----
@SpringBootTest(properties = {
    "preferences.defaults.dark-mode=false",
    "preferences.defaults.units=imperial"
})
----

The `properties` parameter is available in every test slice annotation, so even your slice tests can have custom properties.
But remember from previous chapters that if you start writing variations of the same test by tweaking the properties, the test context will be different, and Spring Boot Tests will spin up a new app.
And while writing a text block and an array of strings in the annotation results in the same behavior, it's considered a different test context.
Even changing the order of the properties creates a new app, so this can cause a lot of context cache thrashing, massively slowing down your test suite!
Keep this in mind, as it applies to every example in this section.

TIP: As much as possible, you should try to create a single configuration with your custom values, so as not to pay the startup price every time.
In my own tests, I typically have a "default" case with no properties, and sometimes a single "custom" case with all the customizations I want to write tests for.

In this example, we scoped the test down to the "Preferences" module, but it's still a full integration test, loading all the JPA infrastructure, so it takes a few seconds.
From here on out, we will create smaller test applications by only loading the configuration class for the preferences module, and we'll only access the properties themselves in our tests.
Such tests aren't very useful in a real production application, as we're essentially testing that Spring Boot binds the properties correctly.
But for demonstration purposes, they're much faster to run, as they avoid loading the data layer, which is the slowest part of the application.

When the number of properties you write in `@SpringBootTest` grows, pasting values in the annotation becomes error-prone and subject to drift.
Fortunately, there is a way to pass properties consistently across tests: the Spring `@TestPropertySource` annotation.
You specify the `locations` of the properties files you want to load in your tests, and Spring Boot Tests will add them to your app's settings:

When you specify multiple files, they are read in order, and if a property is defined multiple times, the last declaration wins.
This is useful for composing multiple sources of properties: you can have a production `application.properties` that is loaded every time, a test file called `tests.properties` replacing some of the production values with test-focused overrides, and maybe a few other files with config for specific features.

Both examples used the properties format, where data is expressed as `<key>=<value>`, such as `spring.application.name=weather-app`.
Spring Boot also supports the YAML format for properties, which is commonly used for deeply nested properties structures, such as Spring Security's OAuth2 support.
Neither `@SpringBootTest` nor `@TestPropertySource` supports YAML out of the box, but there is one feature that does support both formats: Spring profiles.

NOTE: With a bit of elbow grease, or a mid-range coding agent, you can make `@TestPropertySource` read YAML files using the `factory` parameter.
This is beyond the scope of this book, but you'll find an example named `YamlPropertySourceFactory` in the sample repository.

You could imagine a `prod` profile for internet-facing deployments, and a `staging` profile that configures a different, cheaper database or a local LLM in your staging environment.
When you activate a profile, Spring Boot automatically loads the associated configuration file, in our case named `application-staging.yaml` or `application-staging.properties`.
This also applies in tests.

All the examples from this chapter come with the same tradeoff.
While it is very convenient to tweak the properties you set in your test app, every single variation makes Spring Boot Tests spin up a new test app, potentially evicting the most common version of your app from the cache, over and over again.
But what if you have complex validation rules that check user-provided configuration on startup, and you want to test all of them without blowing up the context cache?
The solution is to avoid `@SpringBootTest` entirely and write simpler validation tests.

== Testing property validation logic

When you introduce custom properties in your codebase, it is very common to add some validation to it: "this field must not be blank", "this property must be a valid URL", "that value must be greater than or equal to zero", etc.
Some of that logic may be involved enough that you want to ensure its correctness through automated tests.
In that case, creating a separate test context for each rule would be excessively expensive.
To load configuration files into property objects, Spring Boot does a lot of work, as demonstrated in Figure <<ch6-figure-02>>.

[#ch6-figure-02, reftext={chapter}.{counter:figure}, caption='{figure-caption}.{counter:figure-number} ']
.The different steps involved in transforming configuration files into Spring beans, including data loading, binding and validation.
image::ch06_f02_garniermoiroux.png[]

Spring Boot first finds all relevant files, reads them and transforms them into a `PropertySource`, the Spring API for loading properties.
We've used property sources in the previous section, with the `@TestPropertySource` annotation.
Then Spring creates beans, and when a class is annotated with `@ConfigurationProperties`, Spring Boot _binds_ data to it: it fetches properties from all available property sources and sets the fields in the bean, computing defaults if necessary.
Once the object is created and set up with all the necessary values, Spring runs _validation_ on it, verifying the constraints you've set on the object's fields ("must not be blank", etc.).
Lastly, all the post-initialization steps run (`@PostConstruct`, `InitializingBean#afterPropertiesSet()`, etc.).

To run a proper end-to-end test on these configuration objects, you need the full Spring Boot infrastructure, with the caching tradeoffs that entails.
But you don't need to run full data loading and binding to verify your validation rules.
You can focus on the single "property validation" box, which you isolate and check with blazing-fast unit tests.

For the first unit tests of this book, we'll verify the behavior of the `preferences.temperature-threshold` configuration option, with `cold` (min -90˚C) and `hot` (max 57˚C).

Notice that this test class is not annotated with `@SpringBootTest` or any slice annotation.
It is a humble unit test, but it does more than exercise a function or a class you wrote: it needs a few Spring bits to be relevant.
The difference from slice or Boot tests is that you manage the lifecycle of the Spring objects yourself.
You need to create a `LocalValidatorFactoryBean` and call `.afterPropertiesSet()` explicitly instead of relying on Spring's context management to do it for you.
Then you can use that validator on `TemperatureThreshold` objects to exercise the constraints we placed on them via annotations.
The second object, called `invalid`, uses a cold threshold of `-100`, which is below the `-90` limit we set earlier.
Therefore, the `validator.validate(...)` method returns a constraint violation for the field `cold` with the appropriate message.

There are a few limitations to this test.
First, it does not test the actual binding of properties to the Java object, and ignores things like default values.
Second, as far as validation itself is concerned, it only tests the temperature threshold subproperty, not a realistic scenario where all the nested objects are set up.
If you ever forget the `@Valid` annotation on the `temperatureThreshold` field in `PreferencesProperties`, then the validation on the properties under `preferences.temperature-threshold` never runs.
But our test focuses on the threshold object alone, and would miss issues related to nested properties.
To be more thorough, we'd have to create a full `PreferencesProperties` object, like so:

In that case, I prefer to use the YAML file format for my settings files, and to write my tests with the same format.

Of course, there are cases where you want to perform the full end-to-end configuration lifecycle described in Figure <<ch6-figure-02>>.

Unfortunately, `@SpringBootTest` does not support "invalid" configurations that make the app crash on startup: the tests are marked as failing, and the test method doesn't even execute.
To work around this, you must manage the lifecycle of your test apps manually.

== Programmatically running test applications

Testing for failure requires you to forgo `@SpringBootTest`.
Instead, you can create the test application with a `SpringApplicationBuilder`.
Let's start with a valid configuration:

----
include::../code/ch06/weather/src/test/java/wf/garnier/spring/boot/test/ch6/weather/preferences/internal/PreferencesConfigurationTests.java[tags=manual-app;!ignored]
----
<1> Build the application from Spring components
<2> Set properties you want to test
<3> Disable web capabilities
<4> Run in try-with-resources to automatically close the application context once it's dereferenced
<5> Access beans from the application context

`SpringApplicationBuilder` is very similar to the `@SpringBootTest` annotation you should now be familiar with.
You can specify which classes the application should be configured from, select the web environment type and pass properties.
The difference is that you are responsible for managing the lifecycle, that is, calling `.run()` to start the application and stopping it once the test has completed.
Here we achieve this with the Java _try-with-resources_ construct, which calls `.close()` once the `try` block exits.
You can then use the app's application context to access beans and perform your verifications.

[NOTE]
====
Because it defaults to `SERVLET`, you MUST set the web type to `NONE`, otherwise you'll get an error.
The default requires a full Servlet environment to run, that is, a configured Tomcat server.
This option matches the `spring.main.web-application-type` setting in Spring Boot, which can be `NONE`, `SERVLET` or `REACTIVE`.
This is different from `@SpringBootTest(webEnvironment = ...)`, and there is no straightforward `MOCK` equivalent.
Setting any value other than `NONE` starts a full web application context.
====

With this construct, you can check validation _failures_, cases where the app cannot start, which an annotated test class does not support.
The `.run()` method throws an exception, which we can capture and use in our assertions.
In that case, the application context closes automatically, and you don't need a try-with-resources.

One rule of our cold-hot temperature range that we have not tested yet is that `cold` should be smaller than `hot`.
This does not surface in the pure validation tests, as it is enforced in an `.afterPropertiesSet()` method.
We can test it with a `SpringApplicationBuilder`:

In these examples, we've been spinning up one application context, albeit small, for every single test.
We don't use the integrated lifecycle management from `@SpringBootTest`, so we do not benefit from context caching.
That's why we create the tiniest application context possible, with just a few classes: it only adds a few tens of milliseconds of extra execution time per test.
It should have no noticeable impact on your test suite run time, unless you run thousands of these tests, or the test app has too many moving parts.
If you find yourself creating bigger test apps with `SpringApplicationBuilder`, it's a sign that something is wrong.
Either your app's architecture is problematic and makes it hard to test, or you are trying to write an integration test, in which case you should probably reach for `@SpringBootTest`.
While `SpringApplicationBuilder` adds CPU cycles to your tests, the memory impact is negligible.
Each context will consume a few megabytes of RAM, but with try-with-resources, it is closed after use and memory is released.

== Summary

- To test different configurations of your application, you can use `@SpringBootTest(properties = "...")` to declare properties inline.
To declare your properties in a configuration file, use `@ActiveProfiles` or `@TestPropertySource`.
- Avoid creating too many variants of your test app with different configuration profiles.
Each variant will result in a new test app stored in the test context cache, leading to cache evictions and thrashing.
- To test validation of your `@ConfigurationProperties` classes, unit tests exercising a simple `Validator` instance are much more efficient than full-blown `@SpringBootTest`.
You can construct your properties instances either as plain Java objects, or write YAML configuration and parse it with Jackson.
- You can build small test applications programmatically using `SpringApplicationBuilder`, which allows you to test failure cases beyond single-property validation failures.
