= Testing Configuration and Properties

This chapter covers

* Injecting property values in test classes
* Testing property validation logic, including failure cases
* Deciding when to test Configuration and Property classes

Spring Boot has many built-in options for configuring your application, from selecting the port it runs on to setting up a connection to a database.
The same infrastructure is also available for any configuration you create, declared through `@ConfigurationProperties`-annotated classes.
This allows anyone running your application to configure it for their own use-cases.
For example, with our "weather app" example, you could make the URL of the external weather service configurable.
You could also imagine more complex use-cases, such as enabling caching only when a key-value store is present.
To implement either of those features, you'd need to write code, in one case to add properties and validate them, in the other to react to existing properties with custom configuration.

That code is slightly different from what we've tested so far, as it is usually only exercised once at startup and may stop your application from running if some configuration is invalid.
Of course, Spring Boot Tests has tooling dedicated to testing configuration, but there are also some lesser tricks you can use to write more efficient tests.

[#ch6-section-injecting-properties-into-test-classes, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== Injecting properties into test classes

When your code reacts to configuration properties, writing tests for them means writing tests for multiple values or value pairings and asserting on certain behavior.
To do this, you need to pass the appropriate configuration properties to the application under test, and Spring Boot Tests has four main APIs for this.

For our tests, we'll use the now familiar weather application, with a few new configuration options.
You can find the complete code under `ch6/weather`, or directly at https://github.com/Kehrlann/spring-boot-testing-book-samples/tree/main/ch6/weather.
As usual, you can run the project with `./mvnw spring-boot:run`, and access the application at http://localhost:8080.
There is a single new feature: the weather cards now display the temperature in blue when it's below a certain "cold threshold", and in red when it's above the equivalent "hot threshold".
The main difference with the previous chapter is less visible, though.
When someone runs our application, they can configure it, beyond Spring Boot defaults like the server port.
First, they can set the defaults for the preferences in the app: dark mode, unit system and whether cities are sorted by last added or alphabetically.
For example, the administrator can decide that, by default, the website is in dark mode.
When the user has not expressed their preferences, they get the default set by the administrator.

They are all mapped into a `@ConfigurationProperties` class, called `PreferencesProperties`, with regular Spring Boot property binding techniques we won't be detailing here.

To test how the configuration impacts the code, we need to create a test app with specific configuration properties.
The simplest thing you can do is write an `application.properties` or its YAML equivalent in your test resources folder `src/test/resources`, but beware!
This overrides the file of the same name from your _main_ sources directory, possibly leading to a lot of duplication and configuration drift between prod and tests.
If you want to touch only a few values in your tests, you should use one of the dedicated APIs for property loading.
At the time of this writing, Spring Boot lists 15 ways (!) of loading configuration properties into an application.
Most of them are for production use, but some can be used in tests, including:

* The `properties` parameter in `@SpringBootTest`
* The `@TestPropertySource` annotation, pointing to a file
* The `@ActiveProfiles` annotation and profile-based configuration files

There are also `@DynamicPropertySource` and `DynamicPropertyRegistrar` beans, which allows injecting properties representing resources whose lifecycle is managed outside your application.
It was originally designed for Testcontainers, and we'll discuss in depth further along, in chapter 9, "Testing against real service dependencies with Testcontainers".

TIP: Take some time to go over https://docs.spring.io/spring-boot/reference/features/external-config.html[Externalized Configuration] section in the Spring Boot reference, you'll discover configuration options you've never heard of before.

<1> Pass properties to the annotation

This is the simplest form of configuring the application under test.
You pass whatever properties you want to test directly in the annotation as a string and then test.
Then we verify that, when the user has not set preferences, the `PreferencesService` returns defaults configured by the admin, here dark mode and imperial units.
Here we are using a test block with properties on each line, but you can also write the equivalent configuration:

[source,java,indent=0]
----
@SpringBootTest(properties = {
    "preferences.defaults.dark-mode=false",
    "preferences.defaults.units=imperial"
})
----

This `properties` parameter is available in every test slice annotation, so even your slice tests can have custom properties.
But keep in mind that if you start writing variations of the same test by tweaking the properties, the test context will be different, and Spring Boot Tests will spin up a new app.
And while writing a text block and an array of strings in the annotation results in the same behavior, it's considered a different test context.
Even changing the order of the properties creates a new app, so this can cause a lot of context cache thrashing, massively slowing own your test suite!
Keep this in mind, as it applies to every example in this section.

TIP: As much as possible, you should try and create a single configuration with your custom values, as to not pay the startup price every time.
In my own tests, I typically have a "default" case with no properties, and sometimes a single "custom" case with all the customizations I want to write tests for.

In this example, we scoped the test down to the "Preferences" module, but it's still a full integration test, loading all the JPA infrastructure, so it takes a few seconds.
From here on out, we will create smaller test applications by only loading the configuration class for the preferences module, and we'll only access the properties themselves in our tests.
It's not a very useful test in a real production application, as we're essentially testing that Spring Boot bindings the properties correctly.
But for demonstration purposes, they're much faster to run as they skip the slowest part of the application, here the data layer.

When the number of properties you write in `@SpringBootTest` grows, pasting values in the annotation becomes error-prone and subject to drift.
Fortunately, there are possibility for passing properties is to use the Spring `@TestPropertySource` annotation.
You specify the `locations` of the properties files you want to load in your tests, and Spring Boot Tests will load it in your application:

When you specify multiple files, they are read in order, and if a property is defined multiple times, the last declaration wins.
This is useful for composing multiple sources of properties: you can have a production `application.properties` that is loaded every time, a test file called `tests.properties` replacing some of the production values with test-focused overrides and a few files dedicated to specific features.

Both examples were using the properties format, where data is expressed as `<key>=<value>`, such as `spring.application.name=weather-app`.
Spring Boot also supports the YAML format for properties, which is commonly used for deeply nested properties structure, such as Spring Security's OAuth2 support.
Neither `@SpringBootTest` nor `@TestPropertySource` support YAML out of the box, but there is one feature that does support both formats: Spring profiles.

NOTE: With a bit of elbow grease, or a mid-range coding agent, you can make `@TestPropertySource` read YAML files, using the `factory` parameter.
This is beyond the scope of this book, but you'll find an example in the sample repository.

Spring profiles allow apps to run with different configuration simply with simple names as keys.
You could imagine a `staging` profile that configures a different, cheaper database or LLM for your staging environment.
You can use them in your Spring configuration files, and Spring Boot automatically loads the associated configuration file, in our case named `application-staging.yaml` or `application-staging.properties`.
This also applies in tests.

You can even mix `.properties` and `.yaml` files without issues.

All the examples from this chapter come with the same tradeoff.
While it is extremely convenient to tweak the properties you set in your test app, with each and every variation, Spring Boot Tests spins up new test apps, potentially evicting the most common version of your app from its cache, over and over again.
But what if you have complex validation rules that check user-provided configuration on startup, and you want to test all of them?
The solution is to avoid `@SpringBootTest` entirely, and writing simpler validation tests.
