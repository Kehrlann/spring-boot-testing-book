= Testing web applications

This chapter covers

* Testing Spring web applications with `MockMvcTester`
* Using alternatives to `MockMvcTester`
* Simulating browser interactions with `HtmlUnit`
* Running the full web server in tests
* Driving a complete web browser in tests with Selenium
* Testing client applications with `MockRestServiceServer`

The vast majority of Spring Boot applications are web applications, either browser-based applications with HTML and sometimes Javascript, or server-side components exposing HTTP endpoints in REST, GraphQL or any other format.
One important category of integration tests interact with the application directly using the same interface as an end-user, be it an API or a web app.
This is often implemented as “black box” testing: the application is deployed to a dedicated environment, and tests are executed against the running application.
As we have discussed in the first chapter, this introduces a lot of overhead: for example, you need to provision test environments.
With the web being a core part of the framework, Spring Boot Tests has many options for testing HTTP applications locally, using simple JUnit tests.
Together, we'll discover how you can test your server application by making HTTP requests, how you can automate user interaction tests, and what's available for testing "client" applications.

Notice that we never had to worry about a full URL, with a scheme, host and port, like `http://localhost:1234`.
No need to worry about where the server is running: in fact, there is no server running!
By default, Spring Boot Tests are configured with the "mock MVC" stack, which does not start a full web server, but only the few classes it needs to help you run tests.
This might not be immediately apparent, because `@SpringBootTest` has default values.
With the default value explicitly spelled out, this is equivalent to `@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.MOCK)`.
The main difference between this and your production application is that there is no Servlet container running, serving HTTP requests.
Instead, `MockMvcTester` is configured to call Spring's `DispatcherServlet` and your own controller methods, directly.

[NOTE]
.The Spring MockMvc stack
====
Spring Boot Tests do not start a server, and yet your application is accessible in tests.
How is that even possible?
To understand the Spring MockMvc stack, you need to go back to the foundation on top of which Spring WebMvc is built: the _Servlet API_.
That specification defines the Java interfaces that you implement when you want to respond to HTTP request.
User classes that implement the servlet API run inside a servlet container, such as Tomcat or Jetty.
The container listens for incoming connections, accepts them and transforms the data from HTTP requests into a Java "request" object, prepares a "response" object, and then calls the servlet implementation with those two objects.
Spring has a special implementation, the `DispatcherServlet`, which processes the request, finds which of your controller methods to call, parses the body into your domain objects, and takes your return value to wrap it into an HTTP response.

In the case of MockMvc, there is no Servlet container: the embedded Tomcat server is never started.
When you perform a request in tests with a client, such as `MockMvcTester`, that client will create a mock request object, a mock response object, and invoke a test-specific version of the `DispatcherServlet`.
It does so by calling the `service(...)` method directly, which is a method that Servlet containers themselves use.

// TODO: diagram

This has important implications.
First, none of the logic implemented by the container itself is called: no Tomcat code is involved.
So if you integrate with Tomcat directly, for example by writing `Valve`, that code will not be included.
Session management, a responsibility of the container, is not invoked either.
Second, since your test code calls `MockMvcTester`, which in turns calls the `DispatcherServlet` and your controller methods, that means that your controller code is executed in the same thread as the calling test.
That may be useful for everything that works with thread-locals.
Lastly, relying on the dispatcher servlet means that WebMvc is required.
If your app and tests are WebFlux only, you'll need to rely on some other testing APIs.
