= Testing web applications

This chapter covers

* Testing Spring web applications with `MockMvcTester` and alternatives
* Running the full web server in tests
* Simulating browser interactions with `HtmlUnit`
* Driving a complete web browser in tests with Selenium

The vast majority of Spring Boot applications are web applications, either browser-based applications with HTML and sometimes JavaScript, or server-side components exposing HTTP endpoints in REST, GraphQL or any other format.
Some integration tests interact with the application using the same interface as an end-user, be it an API or a web app.
This is often implemented as “black box” testing: the application is deployed to a dedicated environment, and tests are executed against the running application.
In the first chapter, we called these _end-to-end_ tests, and we discussed the overhead they incurred: for example, you need to provision test environments.
With the web being a core part of the framework, Spring Boot Tests has many options for testing HTTP applications without going all out on end-to-end tests.
With those, you can write simple unit tests that run locally on your development machine, with minimal setup.
There are two broad categories of scenarios you'd want to test in web applications.
First, you can test APIs, usually JSON-based, by issuing direct HTTP calls.
Second, you can interact with website apps through a browser, at the HTML level, by clicking buttons and typing into fields instead of focusing on the HTTP layer.
Let's see what this looks like in practice.

This test follows the usual Arrange / Act / Assert structure: select a city / make a request / verify the result.
Our endpoint returns JSON, and, to test the content, we can rely on the `MockMvcTester` AssertJ integration, with dedicated JSON assertions.
They come in two flavors, one which asserts on the whole object, and one which allows you to traverse the JSON tree to make assertions on a specific parameter.

To check the whole object, we use `.isLenientlyEqualTo(...)`, which compares the request result to a JSON fragment _leniently_: it does not care about the order of properties, and it ignores any property from the result that are not in the expected JSON string you pass it.
This allows you to assert only on the stable properties from the result: the city name and country, which are constants, and weather data which we have hardcoded in our stub implementation of the weather service.
It also allows you to ignore data you do not want to focus on.
In this example, we omit the `cityId` in the expected JSON chunk, because hardcoding "37" in the JSON response would be awkward to read.

But we do want to ensure that the city ID is correct.
So we use the  `.extractingPath(...)` to check the value of a given nested JSON parameter.
To perform JSON parsing and traversal, Spring Boot Tests leverages one the dependencies it brings, the `com.jayway.jsonpath:json-path` library.
In our example, we use the expression `$.[0].cityId`.
Every JsonPath expression starts with a `$`, which is the root element.
In this case, it is the outer array.
We then get the first element of this array with `.[0]`, and from this first element, we extract the `.cityId` property, and compare it to the ID of Paris.

Notice that in all the listings until now, we never use an absolute URL, with a scheme, host and port, like `http://localhost:1234`.
Instead, we made requests by only specifying the path we want to call in the application, such as `/api/city`.
No need to worry about the port on which the test app's web server is listening: in fact, there is no server running!
By default, Spring Boot Tests are configured with the _Mock MVC_ stack, which does not start a full web server, and only loads the components it needs to allow for HTTP-like tests.
This might not be immediately apparent, because the `@SpringBootTest` annotation has default values for all its parameters.
But if we spell out the defaults, this is equivalent to using `@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.MOCK)`.
The main difference between this and your production application is that there is no Servlet container, such as Tomcat, running and serving HTTP requests.
Instead, `MockMvcTester` is configured to bypass all the network stack and web server logic, and call Spring directly without going through a server.
Spring will perform its usual logic, such as finding which of your controller methods it should call, and then invoke your code.

[NOTE]
.The Spring MockMvc stack
====
Spring Boot Tests do not start a server, and yet your application is accessible in tests.
How is that even possible?
To understand the Spring MockMvc stack, you need to go back to the foundation on top of which Spring WebMvc is built: the _Servlet API_.
That specification defines the Java interfaces that you implement when you want to respond to HTTP request.
User classes that implement the servlet API run inside a servlet container, such as Tomcat or Jetty.
The container listens for incoming connections, accepts them and transforms the data from HTTP requests into a Java "request" object, prepares a "response" object, and then calls the servlet implementation with those two objects.
Spring has a special implementation, the `DispatcherServlet`, which processes the request, finds which of your controller methods to call, parses the body into your domain objects, and takes your return value to wrap it into an HTTP response.

In the case of MockMvc, there is no Servlet container: the embedded Tomcat server is never started.
When you perform a request in tests with a client, such as `MockMvcTester`, that client will create a mock request object, a mock response object, and invoke a test-specific version of the `DispatcherServlet`.
It does so by calling the `service(...)` method directly, which is a method that Servlet containers themselves use.

// TODO: diagram

This has important implications.
First, none of the logic implemented by the container itself is called: no Tomcat code is involved.
So if you integrate with Tomcat directly, for example by writing `Valve`, that code will not be included.
Session management, or error page management, both a responsibility of the container, are not invoked either.
Second, since your test code calls `MockMvcTester`, which in turns calls the `DispatcherServlet` and your controller methods, that means that your controller code is executed in the same thread as the calling test.
That may be useful for everything that works with thread-locals.
Lastly, relying on the dispatcher servlet means that WebMvc is required.
If your app and tests are WebFlux only, you'll need to rely on some other testing APIs.
====

== Alternatives to `MockMvcTester`

`MockMvcTester` is not the only tool that Spring Boot Tests offer for testing web applications, which fulfill a very similar purpose.
You may encounter some of these in legacy code-bases, or tests with different stylistic preferences.
And if develop a WebFlux-based application, you do not have access to the MockMvc stack.

[#ch4-section-2-1, reftext={section}.{counter:subsection}, caption='{chapter}.{section}.{subsection}']
=== `MockMvc`, the original component

`MockMvcTester` is a recent addition to the testing portfolio: it was introduced in Spring Framework `6.2` and Boot `3.4`.
Prior to this, the accepted solution for testing MVC apps was `MockMvc`.
It has all the bells and whistles for HTTP requests on the MockMvc stack, and is very similar to `MockMvcTester`.
But it has two key differences: it lacks `AssertJ` integration, and the API is based on wrapping static methods.
A typical `MockMvc` test might look something like this:

This approach works and is supported, so it is not crucial to migrate your existing test suites to these classes.

NOTE: Under the hood, `MockMvcTester` wraps a `MockMvc` instances, and uses that for all request processing.
You could see it as "syntactic sugar", which makes `MockMvc` nicer to user.

A remarkable detail of `WebTestClient` is that the `exchange()` method, which performs requests, is blocking.
The `WebClient` that you use in your production code, on the other hand, is fully reactive and returns `Mono<...>` objects.
There's a very simple explanation: test methods are not reactive!
That's fine, even if you run tests in parallel, you're likely not running thousands of test methods at the exact same time.
You will not encounter any of the web-scale bottlenecks that Reactor helped solve in the first place.
Internally, `WebTestClient` simply calls `.block()` with a timeout, and returns the result.

.WebTestClient, under the hood
====
The `WebTestClient` is very similar to the `WebClient` designed for your production applications.
The both wrap an `ExchangeFunction`, which is the Spring WebFlux abstraction for asynchronously turning an HTTP request into an HTTP response.
They each have dedicated features and characteristics, though.
`WebTestClient` has utilities for capturing outgoing requests and incoming responses, and for making assertions.
On the other hand, `WebClient` is more extensible and has production-related features, such as observability integration.

We've discussed how the MockMvc stack works in section <<ch4-section-1>>.
WebFlux does not rely on the Servlet spec, and there is no Servlet container, that is, no Tomcat server.
Instead, traffic is served by Netty, and the core Spring abstraction is the `HttpHandler`.
When you use  `@AutoConfigureWebTestClient` does not start a web server to handle requests, but instead adapts the client's `ExchangeFunction` to call the test app's `HttpHandler` directly, without going through the full Netty stack.

But `WebTestClient` doesn't have to call the handler directly.
It can wrap any `ExchangFunction`, which means that it can also be used as a regular HTTP client!
====

There is another, fundamental difference with the MockMvc stack, which might not be apparent at first.
Unlike MockMvc, you can use `WebTestClient` to make real HTTP requests.
You need to create an instance programmatically, rather than inject the autoconfigured client, and specify the full URL you would like to use, including the scheme and fully qualified domain name.

== Simulating human interaction with HtmlUnit

In the first sections of this chapter, we've tested our application by making HTTP requests to various API endpoints, as if we were using cURL or Postman.
But not all applications are pure backend, REST-based apps.
Our weather app has an HTML front-end, with a bit of JavaScript, and users interact with it using a browser, not cURL!
To gain more confidence that the app functions as intended, we can get closer to the "end-to-end" side of the testing spectrum, and simulate browser interactions.
Using `MockMvcTester` or the other test clients, it is possible to get the HTML content of the page, parse it, and perform some interactions.
But it was not designed for this kind of usage, and it would get cumbersome quite quickly.
There's an obviously much better solution: browsers.
They were designed specifically to display and interact with HTML, and are a natural fit.
As we'll discuss in detail in section <<ch4-section-5>>, you _can_ run a full-fledged web browser from your tests, but it comes with a few constraints.
But before we think going all-in a web browser, we can use the _HtmlUnit_ project as a stepping stone.
As described on their website (https://htmlunit.sourceforge.io/), HtmlUnit is a "GUI-Less browser for Java programs".
GUI-Less means that it does not display anything to the screen, and "for Java programs" means that, to make it do things, you have to write some java code.
Think of it as a lightweight alternative to a browser, specifically for Java.
It's a great fit for tests, and Spring Boot Test has support for the library.
To use it, add it the dependency to your project:

It is connected to the Mock MVC stack that runs our server code, so there's no need to specify a full URL when making HTTP requests, and instead you can just use the path of the request.
Instead of getting HTML as a raw string, this client parses the response and exposes an `HtmlPage`, which you can use with familiar web DOM APIs, such as `.getElementById(...)`.
Here we're using `.querySelectorAll(...)` to find all HTML elements that match a given CSS selector query.
Those are the "cards" that display weather information about the cities the users has selected.
In this test, we only selected Paris, so there's a single card displayed, and the weather data matches the mock responses we pre-configured.
By default, `.querySelectorAll(...)` returns a list of `DomNode`, which is the most abstract type possible: it's any "element in the DOM tree".
As such, they are mostly used to navigate the tree, with methods for getting parent, child or sibling nodes.
But they also allow you to access any attribute, such as ID or classes, and their text content, which is enough to make basic assertions about the information that's visible on the page.

But `HtmlUnit` is much richer!
It offers more specialized types than a simple `DomNode`, and allows you to check the visibility of an element, type text into input fields, click items, and even run some JavaScript code.
There's a bit of JavaScript in our web page: when a user wants to select a city, they type the name of the city in a field, and an auto-complete popup shows up.
They can then select on the city of their choice from the dropdown, and the card will be added to the page without reloading the full page.

In this test, we simulate some interactions: the user selects the search input field and types "bogot".
The autocomplete will show a single result, Bogotá.
The user then clicks on the result, and a weather card for Bogotá is added to the page.
To simulate user interactions, we use the `.type(...)` method on the input, and the `.click(...)` method on the first auto-complete result.
Here we ask the `.querySelector("input#citySearch")` to return a specific type `HtmlInput`.
It represents an HTML `<input />`, and has a `.type(...)` method which is used to simulate the user typing the text box.
For the first element of the auto-complete result, we know it's an HTML element in the DOM, so we use `HtmlElement` as the return type from `.querySelector(...)`, which it exposes a `.click()` method.
Both the "type" and "click" actions trigger some JavaScript on the page.
When the user inputs data in the city search text box, the page makes HTTP requests to the backend to get matching cities and display auto-complete results.
And when they click on an entry, the page calls the API endpoint that selects the city, and refreshes weather data on the page.
This JavaScript code runs asynchronously on the page, taking a few milliseconds to get the answer back from our server.
We want our tests to ensure that these operations are completed before moving on to the next steps.
Since the `WebClient` is simulating the browser, it is responsible for running JavaScript on the page, so we can tell it to wait until JS code has finished executing.
This is achieved by calling  `.waitForBackgroundJavaScript(1000)`, with a 1000ms timeout, after which the `WebClient` will stop waiting and test execution will resume.

But for all its features, HtmlUnit only has limited support for JavaScript.
If you look at the JS file that our page loads, it is called `legacy.js`, and was written in ES6, a version of the JavaScript language that came out in 2015. But JS is a very active language, with a new release every year.
Our project has another version of the same script, called `modern.js`, which you can load into the page instead of the default by visiting http://localhost:8080/?mode=modern.
These scripts are functionally equivalent.
However, if you try to load the page with HtmlUnit, for example by doing `webClient.getPage("/?mode=modern")`, you'll get a very cryptic error:

----
missing ; before statement (http://localhost/js/modern.js#11)
----

The error looks like a parsing error, but only hint at the actual error is that it happens on line 11. That's because the first word on that line is the `async` keyword, which HtmlUnit does not support.
And this brings us back to the beginning of this section: HtmlUnit is not a "full-fledged browser".
It is very solid for testing server-rendered applications, possibly sprinkled with a bit of JS, but not a completed replacement for a full web browser.

[NOTE]
.JavaScript support in HtmlUnit
====
HtmlUnit is a Java implementation of a web browser.
Using only Java, it builds an internal representation of the DOM and allows you to interact with it.
A regular browser has a dedicated JavaScript engine, a subsystem that parses and runs all JS code.
In Chrome, for example, it is called V8.
In HtmlUnit, this engine is implemented in Java, so all JS codes runs inside the JVM.
It is based on a slightly modified version of a project called Rhino, by Mozilla (https://github.com/mozilla/rhino).
It does not support all modern JS features, as we've seen above with the `async` keyword.
If you're curious about what features are included and what's missing, take a peek at Rhino's compatibility matrix at https://mozilla.github.io/rhino/compat/engines.html.
====

== Running the full web server in tests

Up to this, we've run all our tests using the Mock MVC stack, or its WebFlux equivalent, without ever starting a live web server.
We mentioned earlier that when you don't have a web server, you'll be missing certain features in your tests.
For example, handling exceptions and rendering error pages is handled by the servlet container - think: web server - in WebMVC, and so is session handling.
Of course, any code that is tied to your specific server implementation, such as a custom Tomcat valve, also requires a full server to run.
To demonstrate this, let's test our app's custom 404 page.
If you navigate to a page that doesn't exist, say http://localhost:8080/does-not-exist, you should see a very simple page with a message "404 - NOT FOUND" and "This is not the page you are looking for".
This page is a simple HTML file, found at `src/main/resources/public/error/404.html`.
Whenever you try to access a URL that does not exist, Spring signals that a 404 HTTP error should be emitted, and Tomcat serves the appropriate file if it finds one in the default directory.
If you try to test that with the Mock MVC stack, the body of the page will be empty, because there's no Tomcat to serve our `404.html` page:

`MockMvcTester` lets you know that the status is HTTP 404, and gives you access to Spring's internal error message, but stops there.
If you want to test this feature, you need to run the Tomcat server.
The `@SpringBootTest` annotation makes it very easy with the `webEnvironment` parameter.
You have 4 possible values:

- *MOCK*: A "mock" server is created and exposes your controllers to your tests, but the real web server is not created.
This is the default.
- *NONE*: No web capabilities are enabled for your tests.
This makes most sense for non-web scenarios, for example CLIs or batch apps.
- *RANDOM_PORT*: The embedded web server is started for the tests, on a random, available port.
This is the recommended way to run your tests with the web server.
- *DEFINED_PORT*: The embedded web server is started for the tests, on whatever port is defined in the `server.port` property, or on port 8080 by default.
This may be useful if you need to know the running port before the app starts, for configuration purposes.

Running on a defined port risks conflicting with whatever other process is running on the machine.
And if you're running multiple tests contexts, you will need to assign a separate port to each so they don't conflict.
This is why the recommended approach is to use a random port: before starting your test app, Spring Boot Tests will try to find an available port, and use that.

Of course, we're not using the MOCK stack, so we can't use `MockMvcTester`, and we can't just use a regular HTTP client, say `RestClient`, and point it to the path we want to test.
Instead, we need a way to communicate with the web server over the network, albeit locally on your computer.
The simplest way is to use an autoconfigured `RestTestClient` or `WebTestClient` that we introduced in sections <<ch4-section-2-2>> and <<ch4-section-2-3>>.
Spring Boot Tests sets the base url of your client, and you do not need to care about the port on which your app is running.

== Testing through a real web browser with Selenium

In section <<ch4-section-3>> about browser-based testing with HtmlUnit, we discussed the limitations of that library.
Now that we know how to run our test app with the web server enabled, we can use a regular web browser to access it in our tests.
Of course, your test code has no way to interact with the Chrome or Firefox that's installed on your desktop.
You need two pieces of dedicated tooling to make this work.
The first is a _Web Driver_, a piece of software that allows you to programmatically interact with a browser, send it commands and read state from it.
It exposes an HTTP interface for easy interoperability, and, while you could write the HTTP requests yourself, it would be repetitive, and you'd likely end up writing a lot of helper functions for this.
Instead, you'll use the second tool, Selenium, which provides efficient abstractions for managing the driver lifecycle and interacting with it.

NOTE: While the concept of a WebDriver started with the Selenium project, it is now a World Wide Web Consortium (W3C) specification, describing how programs can interact with web browsers.
Each major browser has its own driver implementing this specification.
If you want to learn more, take a moment to read the first chapter of the specification: https://www.w3.org/TR/webdriver2/.

Perhaps surprisingly, this setup has more code than our usual tests.
The reason is that Spring Boot Tests does not have opinions on how you should configure Selenium, and requires you to choose which browser to use and how to configure it.
The second notable thing here is that we use `@BeforeAll` and `@AfterAll` instead of our usual `@BeforeEach` and `@AfterEach` setup methods.
Here, JUnit will run `startChromeBrowser` once before all tests, and `stopChromeBrowser` after all tests in the file have finished executing.
Creating a new browser instance takes more than 1 second, so to keep execution times low you want to avoid doing it before every single test.
The flipside of this is that the browser window is reused across tests, meaning that any local state is shared across tests.

TIP: If you need to reset cookies between tests, you may use `driver.manage().deleteAllCookies();`.

For our example, we use a `ChromeDriverService`, but you may swap it out for any driver you'd like, such as `SafariDriverService`, `EdgeDriverService` or `GeckoDriverService` for Firefox.
The only pre-requisite for this to work is that there is a version of the chosen browser installed on your local machine, and Selenium will do the rest.
The `ChromeDriver` instance represents a browser instance, that we launch in `--headless` mode, without any UI displayed.
This prevents Chrome from opening visible windows when you run your tests.
This configuration is required for CI environments, where there are no displays, and a browser with a GUI won't start.
Locally, this also avoids unexpectedly losing focus because Chrome just popped as the foremost window.
When you are debugging your tests and want to observe the interactions, removing this option allows you to see the tests being executed in real time.
The last configuration is the _implicit wait_ of the web driver.
This makes the driver wait when you look for an element on the page that's not present.
In our single page app, most interactions are asynchronous and our HTML elements may take a few microseconds to be displayed.
Instead of having to add test code to explicitly wait until they are present, we can leverage the web driver's implicit wait.
Lastly, it's important to clean up after the tests are finished, so we don't have lingering open browsers and processes.

[WARNING]
====
Here use a browser for the whole test class, but it will not be reused between classes.
If you want to use a single browser for the whole test session, you can provide a custom `@TestConfiguration` you'd reuse across tests, as demonstrated in chapter 3.

However, beware: Spring Boot Tests assign all beans of type `WebDriver` to a specific Spring scope, and this will end up creating many browser instances.
If you want to override this behavior, use the `@Scope("singleton")` scope on your `@Bean WebDriver`.

See the file called `SeleniumDriverAsBeanTests.java` in the sample project for an example.

That's what we do when we type into the search field.
First, we locate the field with Selenium's DSL, `driver.findElement()`, to which we pass a query, `By.id("citySearch")`.
This is the Selenium equivalent to the `window.getElementById("citySearch")` call using the native DOM API.
Then we can simulate sending keypress events to that field, which is what the user does when they type, with `citySearchInput.sendKeys("jak")`.
When our app detect those key presses, it performs an autocomplete search, by issuing HTTP requests to our backend, and displays results.
We can look for those results by finding the div with `id=cityResult` on the page, again with `.findElement()`.
Thanks to the implicit wait we added to our setup in listing <<ch4-listing-selenium-setup>>, we do not have to write code to wait for the background JavaScript to finish loading results.
Instead, Selenium will run the "find" query until an element shows up, or until the implicit wait timeout (1s) is reached.
In this `#cityResult` div, there are multiple child elements, that represent individual results.
We look these up using `.findElements()`, plural, which returns a list.
Here, we use a different query, `By.css(...)`, the Selenium counterpart to the browser's `window.querySelectorAll()`, and then extract and clean up the text from these results.
Finally, we can assert that exactly three cities should be displayed, in the following order: Djakotomé, Jakarta and Kamirenjaku.

[NOTE]
.Browser management with Selenium
====
Selenium uses a _web driver manager_ to determine which executables it will use for the web driver and the browser itself.
Using the name of the browser, for example "chrome" when you use `ChromeDriverService`, and some heuristics, it will find the browser installed on your machine, detect its version and the associated web driver.
If it can't find the driver on your machine, it will download one for you.
Of course, you can override this behavior.
For the driver, use  `ChromeDriverService.usingDriverExecutable(...)`, and for the browser executable itself, use `ChromeOptions.setBinary()`.

If you want to see which versions your tests are using, you can turn on logging for Selenium with the usual Spring Boot property, `logging.level.org.openqa.selenium=DEBUG`.
This will print out which browser executable the Selenium Driver Manager found, the version, the version of the driver, etc.

If you want to learn more about the Selenium Driver Manager, take a look at the official documentation at: www.selenium.dev/documentation/selenium_manager/
====

Selenium is very powerful tool, but it's also very broad, and we can't possibly cover all the use-cases in this book, we'd have to dedicate multiple chapters to it.
In fact, there are whole books about it!
See for example _Hands-On Selenium WebDriver with Java_ by Boni Garcia (O'Reilly, 2022).

Selenium is the reference for browser-based testing in the backend world, but recent alternatives, that originated in the frontend world, should be taken into account when deciding your test stack.
If you are developing a single-page app, a very rich frontend with a lot of business logic, chances are you've used a JavaScript or TypeScript-based framework, such as Angular, React or Vue.
In that case, it means you have significant JS expertise in your team, and you should JS-based testing tools, such as Cypress or Playwright.

== Summary

- The majority of Spring Boot applications are web apps, and Spring Boot Tests has dedicated tooling for those use-cases.
- There are two ways to run a test app, either with a "mock" web stack or with a full web server.
- The mock MVC stack is lightweight, easy to test with `MockMvcTester`, and should cover 90% of your testing use-cases.
- If you need to test capabilities of your web server, such as error dispatch or session handling, use `@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)`, along with `RestTestClient` or `WebTestClient`.
- `MockMvcTester` and the `*TestClient` s are best for testing APIs.
If you want to test HTML or JavaScript, use either HtmlUnit or Selenium.
- HtmlUnit works with the mock MVC stack, it runs 100% on the JVM, and is lightweight, but it doesn't perfectly emulate a web browser.
- Selenium requires a full web browser, is bigger and slower, but is better suited for more JavaScript-heavy applications.
