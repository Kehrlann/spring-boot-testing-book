= Testing web applications

This chapter covers

* Testing Spring web applications with `MockMvcTester` and alternatives
* Running the full web server in tests
* Simulating browser interactions with `HtmlUnit`
* Driving a complete web browser in tests with Selenium

The vast majority of Spring Boot applications are web applications--either browser-based applications with HTML and sometimes JavaScript or server-side components exposing HTTP endpoints in REST, GraphQL, or any other format.
Some integration tests interact with the application using the same interface as an end-user, whether an API or a web app.
This is often implemented as "black-box" testing: the application is deployed to a dedicated environment, and tests are executed against the running application.
In the first chapter, we called these _end-to-end_ tests, and we discussed the overhead they incurred; for example, you need to provision test environments.
With the web being a core part of the framework, Spring Boot Tests has many options for testing HTTP applications without going all out on end-to-end tests.
With these options, you can write simple unit tests that run locally on your development machine with minimal setup.
There are two broad categories of scenarios you'll want to test in web applications.
First, you can test APIs, usually JSON-based, by issuing direct HTTP calls.
Second, you can interact with website apps through a browser at the HTML level, clicking buttons and typing into fields instead of focusing on the HTTP layer.
Using a "weather app" similar to the one we tested in chapter 2, let's see these scenarios in practice.

[#ch4-section-1, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== Testing WebMvc applications with `MockMvcTester`

Most Spring applications that expose a web interface use Spring Web MVC, sometimes called "Spring Web".
The second class of apps, which we'll discuss later, uses WebFlux.
When you create a Spring Boot project with Web MVC, Spring Boot embeds a Tomcat web server, which is the component responsible for handling HTTP traffic and passing it to your Spring code.
It's a nontrivial component that takes a bit of time to start up.
It also brings in a lot of infrastructure that usually isn't relevant to your tests.
The Spring team avoided requiring this component in tests by creating test-specific APIs and bundling them in the `MockMvcTester` class.
But before you can see it in action, we need an app to test.

For the examples in this chapter, we'll use the "weather app" from chapter 2 with a few upgrades.
You can find the complete code under `ch4/weather`, or directly at https://github.com/Kehrlann/spring-boot-testing-book-samples/tree/main/ch4/weather.
As usual, you can run the project with `./mvnw spring-boot:run`, and access the application at http://localhost:8080.
The general behavior will be very similar to the app from chapter 2, but instead of doing server-only rendering, we have sprinkled the sample with a bit of JavaScript to turn it into something of a "Single Page Application".

NOTE: This example is not meant to showcase JavaScript best practices.
It is merely an app that we write tests for.
Please do not use it as a blueprint for a real, serious, production application.

This test follows the usual Arrange / Act / Assert structure: select a city / make a request / verify the result.
Our endpoint returns JSON, and, to test the content, we can rely on the `MockMvcTester` AssertJ integration, with dedicated JSON assertions.
They come in two flavors, one which asserts on the whole object, and one which allows you to traverse the JSON tree to make assertions on a specific parameter.
Both are present in the listing above.

To check the whole object, rather than using the default `.isEqualTo(...)` method, which requires two JSON documents to be _strictly_ identical, we check the result _leniently_ by calling `.isLenientlyEqualTo(...)`.
This comparison method does not care about the order of properties, and it ignores any property in the result that are not in the expected JSON string you pass to it.
This allows you to assert only on the stable properties in the result: the city name and country, which are constants, and weather data that we have hardcoded in our stub implementation of the weather service.
It also allows you to ignore data you do not want to focus on.
In this example, we omit the `cityId` in the expected JSON chunk because hardcoding "37" in the JSON response would be awkward to read.

But we do want to ensure that the city ID is correct.
So we use the  `.extractingPath(...)` to check the value of a given nested JSON parameter.
To perform JSON parsing and traversal, Spring Boot Tests brings the `com.jayway.jsonpath:json-path` library as a dependency.
In our example, we use the expression `$.[0].cityId`.
Every JsonPath expression starts with a `$`, which is the root element.
In this case, it is the outer array.
We then get the first element of this array with `.[0]`, and from this first element, we extract the `.cityId` property, and compare it to the ID of Paris.

Notice that in all the listings so far, we never use an absolute URL, with a scheme, host and port, like `http://localhost:1234`.
Instead, we made requests by specifying only the path we want to call in the application, such as `/api/city`.
No need to worry about the port on which the test app's web server is listening: in fact, there is no server running!
By default, Spring Boot Tests are configured with the _Mock MVC stack_, which does not start a full web server, and only loads the components it needs to allow for HTTP-like tests.
This might not be immediately apparent, because the `@SpringBootTest` annotation has default values for all its parameters.
But if we spell out the defaults, this is equivalent to using `@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.MOCK)`.
The main difference between this setup and your production application is that there is no Servlet container, such as Tomcat, running and serving HTTP requests.
Instead, `MockMvcTester` is configured to bypass all the network stack and web server logic, and call Spring directly without going through a server.
Spring will perform its usual logic, such as finding which of your controller methods it should call, and then invoke your code.

[#ch4-note-mock-mvc]
[NOTE]
.The Spring Mock MVC stack
====
Spring Boot Tests does not start a server, and yet your application is accessible in tests.
How is that even possible?
To understand the Spring Mock MVC stack, you need to go back to the foundation on top of which Spring Web MVC is built: the _Servlet API_.
That specification defines the Java interfaces that represent the logical elements involved in serving HTTP traffic, such as requests, responses, and cookies.
User-defined classes that implement the servlet API run inside a servlet container, such as Tomcat or Jetty.
A Servlet is a request handler, registered with the container for a specific path or path pattern.
The container listens for incoming connections, accepts them and transforms the data from HTTP requests into a Java "request" object, prepares a "response" object, and then calls `.service(...)` on the appropriate Servlet.
Spring has a special implementation, the `DispatcherServlet`, which processes the request, finds which of your controller methods to call, parses the body into your domain objects, invokes the method, and finally wraps the return value into an HTTP response object that it hands back to the Servlet container.

In the case of MockMvc, there is no Servlet container: the embedded Tomcat server is never started.
When you perform a request in tests with a client, such as `MockMvcTester`, that client will create a mock request object, a mock response object, and invoke a test-specific version of the `DispatcherServlet`.
In practice, when you execute an HTTP request `MockMvcTester`, it invokes the `service(...)` method directly instead of issuing a network call.

This has important implications.
First, none of the logic implemented by the container itself is called: no Tomcat code is involved.
So if you integrate with Tomcat directly, for example by writing `Valve`, that code will not be included.
Session management, or error page management, both a responsibility of the container, are not invoked either.
Second, since your test code calls `MockMvcTester`, which in turns calls `DispatcherServlet.service(...)` and your controller methods, that means that your controller code is executed in the same thread as the calling test, usually the main thread.
That may be useful for everything that works with thread-locals.
Lastly, relying on the dispatcher servlet means that WebMvc is required.
If your app and tests are WebFlux only, you can't use the Mock MVC stack.
Head over to section <<ch4-section-2-2>> to learn how to test WebFlux apps with `WebTestClient`.
====

== Alternatives to `MockMvcTester`

`MockMvcTester` is not the only tool that Spring Boot Tests offer for testing web applications.
You may encounter some of these tools in older codebases, created when the newer alternatives did not exist yet.
You may also find them in newer projects that feature different stylistic preferences.
If you develop a WebFlux-based application, you need an alternative to `MockMvcTester` that works with WebFlux.

[#ch4-section-2-1, reftext={chapter}.{section}.{counter:subsection}, caption='{chapter}.{section}.{subsection}']
=== `MockMvc`, the original component

`MockMvcTester` is a recent addition to the testing toolkit: it was introduced in Spring Framework `6.2` and Boot `3.4`.
Prior to this, the common solution for testing MVC apps was `MockMvc`, and you will likely encounter it in older projects.
It has all the bells and whistles for HTTP requests on the Mock MVC stack, and is very similar to `MockMvcTester`.
But it has two key differences: it lacks `AssertJ` integration, and the API is based on static methods rather than a fluent API with chained methods.
A typical `MockMvc` test might look something like this:

Your IDE usually won't have autocompletion for these methods, so you'll have to memorize them by heart or reuse code from another test.

The test is also, in my opinion, harder to read.
This approach works and is supported, so it isn't crucial to migrate your existing test suites to these classes.
For new tests, though, I'd recommend using the more recent `MockMvcTester`.

NOTE: Under the hood, `MockMvcTester` wraps a `MockMvc` instance, and uses that for all request processing.
You could see it as syntactic sugar, which makes `MockMvc` nicer to use.

=== `WebTestClient` for WebFlux-based applications

When working on WebFlux-based applications, the MVC stack is not present.
While it is possible, in some cases, to also add Spring MVC support in your tests, it often won't work: the WebFlux and MVC stacks are not designed to coexist in the same project.
Without MVC, there is no Mock MVC stack, and `MockMvcTester` is not available.
Instead, Spring offers a test utility called `WebTestClient`.
It is the testing equivalent of `WebClient`, which you use in your production code to make HTTP requests to third-party services.

A remarkable detail of `WebTestClient` is that the `exchange()` method, which performs requests, is blocking.
The `WebClient` that you use in your production code, on the other hand, is fully reactive, with reactive return types based on `Mono<...>`.
There's a very simple explanation for this difference: test methods are not reactive.
And that's fine!
Reactor was created to handle non-blocking, IO-bound workloads.
Your tests will not encounter any of the web-scale bottlenecks that Reactor helped solve in the first place, even if you run them all in parallel.
Internally, `WebTestClient` simply calls `.block()` with a timeout, and returns the result.

[NOTE]
.WebTestClient, under the hood
====
The `WebTestClient` is very similar to the `WebClient` that you use in your production applications.
Both of them wrap an `ExchangeFunction`, which is the Spring WebFlux abstraction for asynchronously turning an HTTP request into an HTTP response.
They each have dedicated features and characteristics, though.
`WebTestClient` has utilities for capturing outgoing requests and incoming responses, and for making assertions, while `WebClient` is more extensible and has production-related features, such as observability integration.

We've discussed how the Mock MVC stack works in section <<ch4-section-1>>.
WebFlux does not rely on the Servlet spec, and there is no Servlet container, that is, no Tomcat server.
Instead, traffic is served by Netty, and the core Spring abstraction is the `HttpHandler`.
When you use `@AutoConfigureWebTestClient`, it does not start a web server to handle requests, but instead adapts the client's `ExchangeFunction` to call the test app's `HttpHandler` directly, without going through the full Netty stack.

It is worth mentioning that `WebTestClient` doesn't have to call the handler directly.
It can wrap any `ExchangeFunction`, which means that it can also be used as a regular HTTP client.
====

There is another, fundamental difference with the Mock MVC stack, which might not be apparent at first.
Unlike MockMvc, you can use `WebTestClient` to make real HTTP requests.
You need to create an instance programmatically, rather than inject the autoconfigured client, and specify the full URL you would like to use, including the scheme and fully qualified domain name.

To make it work, you need to add the `org.springframework.boot:spring-boot-starter-webclient-test` dependency to your project, in the test scope.
Keep in mind that while it is technically possible, it is highly unusual.
This may fit certain niche use-cases, such as a project where you are transitioning from WebFlux to WebMvc, and would like to keep the tests intact.

=== Other alternatives

Spring Boot Tests offers two other testing HTTP clients, that you may encounter from time to time.
The first is the `RestTestClient`, just introduced in Spring Framework 7 and Boot 4. It's a test-specific version of `RestClient`, and works just like `WebTestClient`, except it's tailored to the MVC stack rather than WebFlux.
The API is almost exactly the same as `WebTestClient`.

== Running the full web server in tests

Up to this point, we've run all our tests using the Mock MVC stack, or its WebFlux equivalent, without ever starting a live web server.
We mentioned earlier that when you don't have a web server, you'll be missing certain features in your tests.
For example, in WebMvc, handling exceptions and rendering error pages is handled by the servlet container (the web server, such as Tomcat), and so is session handling.
Of course, any code that is tied to your specific server implementation, such as a custom Tomcat valve, also requires a full server to run.
To demonstrate this, let's test our app's custom 404 page.
If you navigate to a page that doesn't exist, say http://localhost:8080/does-not-exist, you should see a bare-bones page with the messages "404 - NOT FOUND" and "This is not the page you are looking for".
This page is a simple HTML file found at `src/main/resources/public/error/404.html`.
When a user requests a URL that doesn't exist, Spring signals that a 404 HTTP error should be emitted, and Tomcat serves the appropriate file if it finds one in the default directory.
If you try to test this with the Mock MVC stack, the page body will be empty, because there's no Tomcat to serve the `404.html` page:

`MockMvcTester` lets you know that the status is HTTP 404, and gives you access to Spring's internal error message, but stops there.
If you want to test the error page itself, you need to run the Tomcat server.
The `@SpringBootTest` annotation makes it very easy by changing the `webEnvironment` parameter.
You have 4 possible values:

- *MOCK*: A "mock" server is created and exposes your controllers to your tests, but the real web server is not started.
This is the default.
- *NONE*: No web capabilities are enabled for your tests.
This makes most sense for non-web scenarios, for example CLIs or batch apps.
- *RANDOM_PORT*: The embedded web server is started for the tests, on a random, available port.
This is the recommended way to run your tests with the web server.
- *DEFINED_PORT*: The embedded web server is started for the tests, on whatever port is defined in the `server.port` property, or on port 8080 by default.
This may be useful if you need to know the port on which the application is listening to in advance, for example for configuration purposes.

Running on a defined port risks conflicting with whatever other process is executing on the machine.
And if you're running multiple tests contexts, you will need to assign a separate port to each so they don't conflict.
This is why the recommended approach is to use a random port: before starting your test app, Spring Boot Tests will try to find an available port, and use that.

Of course, we're not using the MOCK stack, so we can't use `MockMvcTester`, and we can't just use a regular HTTP client, say `RestClient`, and point it to the path we want to test.
Instead, we need a way to communicate with the web server over the network, albeit locally on your computer.
The simplest way is to use an autoconfigured `RestTestClient` or `WebTestClient` that we introduced in sections <<ch4-section-2-2>> and <<ch4-section-2-3>>.
Spring Boot Tests sets the base url of your client, and you do not need to care about the port on which your app is running.

== Simulating human interaction with HtmlUnit

In the earlier sections of this chapter, we've tested our application by making HTTP requests to various API endpoints, as if we were using cURL or Postman.
But not all applications are pure backend, REST-based apps.
Our weather app has an HTML front-end with a bit of JavaScript, and users interact with it using a browser, not by making HTTP calls with cURL.
To gain more confidence that the app functions as intended, we can move closer to the end-to-end side of the testing spectrum and simulate browser interactions.
Using `MockMvcTester` or the other test clients, you can get the HTML content of the page, parse it, and perform some interactions.
But `MockMvcTester` was not designed for this kind of usage, and it would get cumbersome quickly.
There's an obviously much better solution: browsers.
They were designed specifically to display and interact with HTML, and are a natural fit.
As we'll discuss in detail in section <<ch4-section-5>>, you _can_ run a full-fledged web browser from your tests, but it comes with a few constraints.
Before we think about going all-in on using a real web browser, we can use the _HtmlUnit_ project as a stepping stone.
As described on its website (https://htmlunit.sourceforge.io/), HtmlUnit is a "GUI-less browser for Java programs".
GUI-less means it does not display anything on the screen, and "for Java programs" means that, to make it do things, you have to write some Java code.
Think of it as a lightweight alternative to a browser, created specifically for Java.
It's a great fit for tests, and Spring Boot Tests has support for the library.
To use it, add the dependency to your project:

When you use the Mock MVC stack, Spring Boot Tests auto-configures one for you, which you can inject into your tests.
In the `WebClient` API, you'll recognize method names you encounter when working with the DOM and JavaScript, such as `.getElementById` or `.querySelector`, which you can use to write test logic for your page.

In our application, when the user selects a city, it creates a "weather card", as pictured in <<ch4-figure-02>>.

Thanks to `@AutoConfigureMockMvc`, there's a `WebClient` bean available in our test context that we can inject.
It is connected to the Mock MVC stack that runs our server code, so there's no need to specify a full URL when making HTTP requests; you can just use the request path.
The `WebClient` parses the response's HTML body and exposes an `HtmlPage`, which you can interact with using familiar web DOM APIs, such as `.getElementById(...)`.
Here we're using `.querySelectorAll(...)` to find all HTML elements that match a given CSS selector query.
Those are the "cards" that display weather information about the cities the user has selected.
In this test, we selected only Paris, so a single card is displayed, and the weather data matches the mock responses we preconfigured.
By default, `.querySelectorAll(...)` returns a list of `DomNode`, which is the most abstract type possible: it's any "element in the DOM tree".
As such, they're mostly used to navigate the tree, with methods for getting parent, child, or sibling nodes.
They also allow you to access any attribute, such as the ID or classes, and their text content.
Here, the text is enough to make basic assertions about the information that's visible on the page.

But `HtmlUnit` is much richer!
It offers more specialized types than the humble `DomNode`, and allows you to check the visibility of an element, type text into input fields, click items, and even run some JavaScript code.
There's a bit of JavaScript in our web page: when a user wants to select a city, they type the name of the city in a field, and an auto-complete dropdown appears.
They can then select on the city of their choice from the dropdown, and the card will be added to the current document without reloading the full page.
We can write a test for this behavior:

In this test, we simulate a few interactions: the user selects the search input field and types "bogot".
The autocomplete shows a single result, Bogotá.
The user then clicks the result, and a weather card for Bogotá is added to the page.
To simulate these actions, we use the `.type(...)` method on the input and the `.click(...)` method on the first autocomplete result.
Here we ask `.querySelector("input#citySearch")` to return a specific type, `HtmlInput`.
It represents an HTML `<input />` element and has a `.type(...)` method used to simulate the user typing characters into the text box.
For the first element in the autocomplete results, we know it's an HTML element in the DOM, so we use `HtmlElement` as the return type from `.querySelector(...)`.
This type is slightly more specialized than `DomNode` and exposes a `.click()` method.
Both the "type" and "click" actions trigger some JavaScript on the page.
When the user enters data in the city search text box, the page makes HTTP requests to the backend to get matching cities and display autocomplete results.
When they click an entry, the page calls the API endpoint that selects the city and refreshes weather data on the page.
This JavaScript code runs asynchronously in the background, taking a few milliseconds to get the answer back from our server.
We want our tests to ensure that these operations are completed before moving on to the next steps.
Since `WebClient` is simulating the browser, it is responsible for running JavaScript on the page, so we can tell it to wait until JS code has finished executing.
We do this by calling `.waitForBackgroundJavaScript(1000)` with a 1000ms timeout, after which the `WebClient` stops waiting and test execution resumes.

So you can do quite a lot with HtmlUnit, including executing JavaScript ... in Java!
Quite a feat, isn't it?
But for all its features, HtmlUnit has only limited support for JavaScript.
If you look at the JS file that our page loads, it's called `legacy.js` and was written in ES6, the JavaScript standard from 2015.
But JS is a very active language, with a new release every year.
Our project has another version of the same script, called `modern.js`, which you can load into the page instead of the default by visiting http://localhost:8080/?mode=modern.
These scripts are functionally equivalent, but the modern version uses a more modern JavaScript version, with newer concepts such as classes or async/await.
Unfortunately, if you try to load the page with HtmlUnit by calling `webClient.getPage("/?mode=modern")`, you'll get a very cryptic error:

----
missing ; before statement (http://localhost/js/modern.js#11)
----

The error looks like a parsing error, but the only hint about the actual issue is that it happens on line 11. That's because the first word on that line is the `async` keyword, which HtmlUnit does not support.
And this brings us back to the beginning of this section: HtmlUnit is not a "full-fledged browser".
It is very solid for testing server-rendered applications, possibly sprinkled with a bit of JS, but not a complete replacement for a full web browser.

[NOTE]
.JavaScript support in HtmlUnit
====
HtmlUnit is a Java implementation of a web browser.
Using only Java, it builds an internal representation of the DOM and allows you to interact with it.
A regular browser has a dedicated JavaScript engine, a subsystem that parses and runs all JS code.
In Chrome, for example, it is called V8.
In HtmlUnit, this engine is implemented in Java, so all JS code runs inside the JVM.
It is based on a slightly modified version of a project called Rhino by Mozilla (https://github.com/mozilla/rhino).
It does not support all modern JS features, as we've seen above with the `async` keyword.
If you're curious about what features are included and what's missing, take a peek at Rhino's compatibility matrix at https://mozilla.github.io/rhino/compat/engines.html.
====

If your application uses unsupported JavaScript features, or more recent APIs such as `PublicKeyCredential` used for Passkeys login, HtmlUnit is not enough, and you'll need to run a full browser in your tests, such as Chrome or Firefox.
Spring Boot Tests has support for Selenium, the reference library for managing web browsers in Java tests.

[#ch4-section-5, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== Testing through a real web browser with Selenium

Selenium has been around for over 20 years. It started as a JavaScript in-browser testing library and evolved into the dominant testing tool, with integrations for most major programming languages, starting with Java.
It does not have the limitations of HtmlUnit, but since the tests use a real browser, your test app needs to be accessible over the network, and you need to run a web server, as described in section <<ch4-section-3>>.
Of course, your test code has no way to interact with the Chrome or Firefox that's installed on your desktop.
You need two pieces of dedicated tooling to make this work.
The first is a _WebDriver_, a piece of software that lets you programmatically interact with a browser, send it commands, and read state from it.
It exposes an HTTP interface for easy interoperability. While you could write the HTTP requests yourself, it would be repetitive, and you'd likely end up writing many helper functions.
Instead, you'll use the second tool, Selenium, which provides efficient abstractions for managing the driver lifecycle and interacting with it.

NOTE: The concept of a WebDriver started as an independent project, later merged with the Selenium project, and it is now a World Wide Web Consortium (W3C) specification, describing how programs can interact with web browsers.
Each major browser has its own driver implementing this specification.
If you want to learn more, take a moment to read the first chapter of the specification: https://www.w3.org/TR/webdriver2/.

To use Selenium in your project, first add the dependency:

Strikingly, this setup has way more code than our examples so far.
The reason is that Spring Boot Tests does not have opinions on how you should configure Selenium and requires you to choose which browser to use and how to configure it.
The second notable thing here is that we use `@BeforeAll` and `@AfterAll` instead of our usual `@BeforeEach` and `@AfterEach` setup methods.
With this, JUnit will run `startChromeBrowser` once before all tests and `stopChromeBrowser` after all tests in the file have finished executing.
Creating a new browser instance takes more than a second, so to keep execution times low, you want to avoid doing it before every single test.
The flipside of this is that the browser window is reused across tests, meaning that any local state is shared across tests.

TIP: If you need to reset cookies between tests, for example to log out a test user created in a given test, you may use `driver.manage().deleteAllCookies();`.

For our example, we use a `ChromeDriverService`, but you may swap it out for any driver you'd like, such as `SafariDriverService`, `EdgeDriverService` or `GeckoDriverService` for Firefox.
As long as that there is a version of the chosen browser installed on your local machine, Selenium will be able to start the matching driver service.

[NOTE]
.Browser management with Selenium
====
Selenium uses a _web driver manager_ to determine which executables it will use for the web driver and the browser itself.
Using the name of the browser, for example "chrome" when you use `ChromeDriverService`, and some heuristics, it will find the browser installed on your machine, detect its version and the associated web driver.
If it can't find the driver on your machine, it will download one for you.
Of course, you can override this behavior.
For the driver, use  `ChromeDriverService.usingDriverExecutable(...)`, and for the browser executable itself, use `ChromeOptions.setBinary()`.

If you want to see which versions your tests are using, you can turn on logging for Selenium with the usual Spring Boot property, `logging.level.org.openqa.selenium=DEBUG`.
This will print out which browser executable the Selenium Driver Manager found, the version, the version of the driver, etc.

If you want to learn more about the Selenium Driver Manager, take a look at the official documentation at: https://www.selenium.dev/documentation/selenium_manager/
====

The `ChromeDriver` instance represents a browser instance, that we launch in `--headless` mode, without any UI displayed.
This prevents Chrome from opening visible windows when you run your tests.
This configuration is required for CI environments, where there are no displays, and a browser with a GUI won't start.
Locally, this also avoids unexpectedly losing focus because Chrome just popped as the foremost window.
But when you are debugging your tests and want to observe the interactions, removing this option allows you to see the tests being executed in real time, live in the browser Selenium is currently driving.

The last configuration is the _implicit wait_ of the web driver, including a timeout for how long the driver should wait.
This makes the driver wait when you look for an element on the page that's not present.
So if your test says, "get element with id #popup", the driver will try to find it in the loop until it is present on the page, or until the driver times out.
And all of this happens without cluttering your tests with extra lines of code to wait for this or that element to be visible.
This is important for our single page app because most interactions are asynchronous.
When the user makes a change, the JavaScript code makes HTTP requests, and when they complete, JavaScript updates the page with the data from the response.
Instead of having to add test code to explicitly wait until the element is present, we can configure the web driver's implicit wait once, and it will be used every time we try to find an HTML element in our tests.
Lastly, it's important to clean up after the tests are finished so we don't have lingering open browsers and processes.

[WARNING]
====
Here we use a single browser instance for the whole test class, but it will not be reused between classes.
If you want to use a single browser for the whole test session, you can provide a custom `@TestConfiguration` you'd reuse across tests, as demonstrated in chapter 3.

But beware: Spring Boot Tests assigns all beans of type `WebDriver` to a specific Spring scope, and this will end up creating many browser instances.
That's the exact opposite of what you're trying to achieve!
If you want to override this behavior, use the `@Scope("singleton")` scope on your `@Bean WebDriver`.

See the file called `SeleniumDriverAsBeanTests.java` in the sample project for an example.
====

First, we locate the field with Selenium's `driver.findElement()`, passing it a query: `By.id("citySearch")`.
This is the Selenium equivalent of calling `window.getElementById("citySearch")` using the native DOM API.
Then we can simulate the user typing into the field by calling `citySearchInput.sendKeys("jak")`.
This triggers the same event as a user typing on a keyboard: `keydown`, `keyup`, and so on.

When our app detects those key presses, it performs an autocomplete search by issuing HTTP requests to our backend and displaying results.
We can look for those results by finding the div with `id=cityResult` on the page, again with `.findElement()`.
Unlike in the HtmlUnit tests, we do not need to add code to wait for those elements to appear, thanks to the implicit wait we added in <<ch4-listing-selenium-setup>>.
Instead, Selenium will run the "find" query until an element shows up or until the implicit-wait timeout (1 second) is reached.
In this `#cityResult` div, there are multiple child elements that represent individual results.
We look these up using `.findElements()` (plural), which returns a list.
Here, we use a different query, `By.css(...)`, the Selenium counterpart to the browser's `window.querySelectorAll()`, and then extract and clean up the text from those results.
Finally, we can assert that exactly three cities are displayed, in the following order: Djakotomé, Jakarta, and Kamirenjaku.

Selenium is a very powerful tool, but it's also very broad, and we can't possibly cover all the use-cases in this book, we'd have to dedicate multiple chapters to it.
In fact, there are whole books about it!
See for example _Hands-On Selenium WebDriver with Java_ by Boni Garcia (O'Reilly, 2022).

Selenium is the reference for browser-based testing in the backend world.
But it's not the only option, and there are more recent alternatives that originated in the frontend world, often written for JavaScript or TypeScript.
If you are developing a single-page app, a very rich frontend with a lot of business logic, chances are you've used a JS (or TS) framework, such as Angular, React or Vue.
In that case, it means you have significant expertise in your team, and you should consider using JS-based testing tools, such as Cypress or Playwright.

== Summary

- The majority of Spring Boot applications are web apps, and Spring Boot Tests has dedicated tooling for those use-cases.
- There are two ways to run a test app, either with a "mock" web stack or with a full web server.
- The mock MVC stack is lightweight, easy to test with `MockMvcTester`, and should cover 90% of your testing use-cases.
- If you need to test capabilities of your web server, such as error dispatch or session handling, use `@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)`, along with `RestTestClient` or `WebTestClient`.
- `MockMvcTester` and the `*TestClient` alternatives are best for testing APIs.
If you want to test HTML or JavaScript, use either HtmlUnit or Selenium.
- HtmlUnit works with the mock MVC stack, it runs 100% on the JVM, and is lightweight, but it doesn't perfectly emulate a web browser.
- Selenium requires a full web browser, is bigger and slower, but is better suited for more JavaScript-heavy applications.
