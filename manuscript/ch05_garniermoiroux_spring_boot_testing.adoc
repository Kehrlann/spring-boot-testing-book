= Testing subsets of an application

This chapter covers

* Testing a single layer of the application with test slices
* Testing the web layer with `@WebMvcTest`
* Testing the data layer with `@DataJpaTest`
* Creating a custom test slice

When testing applications with the `@SpringBootTest` annotation, as we've done extensively in the previous chapters, Spring Boot Tests loads the full application context, everything from controllers to repositories.
For big applications, with hundreds or thousands of beans, or with dependencies that have a long startup time like Hibernate, the impact on test suite execution time can be significant.
If your Spring application context takes a full minute to start up on your development machine, then launching a single test will test as long.
With context caching, subsequent tests should be much faster, but one minute is too long when you run tests very frequently.

I have practiced Test Driven Development (TDD for short), which advocates for very short feedback loops.
You write a test, execute it, watch it fail, fix it, then execute it again, watch it pass, etc.
Simple, non-Spring unit tests start in milliseconds and do not hinder your workflow.
But the moment you get into Spring Boot Tests, having to wait for as little as 10 seconds is already a productivity killer.

The solution to this particular problem is to reduce the number of components loaded in a particular test application.
You can do this manually, as we've seen in Chapter 3, "Configuring and running an application for testing".
For complex apps, creating smaller application contexts requires some non-trivial amount of boilerplate.
Spring Boot Tests addresses the issue with _slice tests_, which test only a specific subset of components that share common characteristics, such as "all web `@Controller` beans".
Spring does not know anything about your business logic, so these slices are technical in nature: there's a slice for web test, a slice for testing the data layer, and so on.

We'll start by discussing what slices are, and then we'll discover some example slices, explaining their scopes and how to use them.

== Test slices: isolating technical components

The name "test slice" brings the layered architecture pattern to mind.
This architecture pattern was very common in the 2000s, when Spring was first introduced.
It presents an application as a multi-layered cake, each with its own scope, and is sometimes referred to as "three-tier architecture".
The top layer is the _presentation_ layer, which, in your typical Spring Boot web application, would be the web part, with all the `@Controller`s and related beans.
It relies on Spring internals for handling requests and responses, for serializing or deserializing Java objects to JSON and for translating errors to HTTP codes.
Then comes the _business_ or _domain_ layer, the collection of `@Service`s that contain the business logic.
This layer, unlike others, does not interface with specific components in the tech stack, and thus does not require any dedicated infrastructure.
At the bottom sits the _data_ or _persistence_ layer, which contains your app's interfaces to the database.
Just like the web layer, it needs the framework's code to work.

For testing purposes, this cake can be _sliced_, separating layers and providing the required Spring artifacts to test it.
Spring Boot gives you simple annotations for each technical scope it manages, which you can use instead of `@SpringBootTest`.
Each carve out a slice of your application and add the appropriate beans for testing said slice.
For example, `@WebMvcTest` will only load your web layer, such as `@Controller` and `@ControllerAdvice` beans, and also autoconfigures `MockMvcTester`.
Another annotation, `@DataJpaTest`, helps with data tests and limits scanning to `@Entity` classes and associated repositories.
It also loads data-related auto-configurations, replaces the default database by an in-memory instance and makes all tests transactional.
In between these, the business layer doesn't need much in terms of framework support, so there is no dedicated annotation for it.

In fact, there are many more ways to design your apps, such as "hexagonal architecture" which has gained popularity in the current decade.
No matter what architectural pattern, test slices cover aspects of your application that need Spring code, and this extends beyond just the web and data interfaces.
Here is a non-exhaustive list:

* `RestClient` and `WebClient`
* Most data-related projects such as JDBC, jOOQ, Redis, Mongo, LDAP, ElasticSearch and more
* GraphQL
* Spring Web Services (SOAP)
* JSON serialization and deserialization with Jackson

For a full list, referer to the reference documentation, under Testing > Testing Spring Boot Applications: https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html

We have briefly touched on why you would want to test only a few classes in your application in chapter 3, when we discussed "Building a test application from manually selected classes", and "Stubbing out dependencies by using mocks".
Test slices are another strategy to make thinner applications for testing, and they come with opinions and specific tooling to make testing certain use-cases easier.
Of course, as the saying goes, "there's no such thing as a free lunch", and test slices have their own limitations and tradeoffs.

== When to use test slices

A slice, while loading a _smaller_ application, still builds a Spring app, and adds a few tens of milliseconds of overhead.
Over enough tests, this can add up.
In chapter 3, we discussed how Spring caches test apps between tests, dramatically speeding up integration tests.
By default, the size of the cache is 32, and going over that limit will cause cache eviction, leading to a lot of thrashing in bigger test suites.
I once met Spring developers at a conference who told me they used to have hundreds of slices tests.
They were suffering from both the performance overhead and cache churn described above.
Getting rid of them sped up their test suite by a factor of 4 or 5.

NOTE: I reproduced this experiment, running a thousand very thin slices versus running a thousand tests against a single app context, and the single slice is an order of magnitude faster.
You can find this very un-scientific benchmark in the examples repository, under `ch05/performance`.

Test slices shine when these two conditions are met:

* *The app you are trying to test is large*.
This may mean it has many dependencies, or that it is simply slow to start.
When it has dependencies, like messages queues, databases and so forth, and you start some resource intensive process to support those tests, for example Testcontainers.
This may be slow, resource intensive or both.
There are many reasons other for an app to be slow to start, like Hibernate scanning packages for JPA entities, or custom business logic you execute on startup.
* *You want a fast feedback loop*.
If your test app takes a minute to start, but you only pay the cost once, it may not be a problem for you.
On the other hand, imagine you are iterating on a given feature, and run your tests every few minutes.
Then getting around the startup overhead is a massive productivity boost.
