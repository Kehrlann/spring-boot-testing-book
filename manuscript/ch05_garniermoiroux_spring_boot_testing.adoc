= Testing subsets of an application

This chapter covers

* Testing a single layer of the application with test slices
* Testing the web layer with `@WebMvcTest`
* Testing rest clients with `@RestClientTest`
* Testing a Spring Modulith application module

When testing applications with the `@SpringBootTest` annotation, as we've done extensively in the previous chapters, Spring Boot Tests loads the full application context, everything from controllers to repositories.
For big applications, with hundreds or thousands of beans, or with dependencies that have a long startup time like Hibernate, the impact on test suite execution time can be significant.
If your Spring application context takes a full minute to start up on your development machine, then launching a single test will test as long.
With context caching, subsequent tests should be much faster, but one minute is too long when you run tests very frequently.

I have practiced Test Driven Development (TDD for short), which advocates for very short feedback loops.
You write a test, execute it, watch it fail, fix it, then execute it again, watch it pass, etc.
Simple, non-Spring unit tests start in milliseconds and do not hinder your workflow.
But the moment you get into Spring Boot Tests, having to wait for as little as 10 seconds is already a productivity killer.

The solution to this particular problem is to reduce the number of components loaded in a particular test application.
You can do this manually, as we've seen in Chapter 3, "Configuring and running an application for testing".
For complex apps, creating smaller application contexts requires some non-trivial amount of boilerplate.
Spring Boot Tests addresses the issue with _slice tests_, which test only a specific subset of components that share common characteristics, such as "all web `@Controller` beans".
Spring does not know anything about your business logic, so these slices are technical in nature: there's a slice for web test, a slice for testing the data layer, and so on.

We'll start by discussing what slices are, and then we'll discover some example slices, explaining their scopes and how to use them.

== Test slices: isolating technical components

The name "test slice" brings the layered architecture pattern to mind.
This architecture pattern was very common in the 2000s, when Spring was first introduced.
It presents an application as a multi-layered cake, each with its own scope, and is sometimes referred to as "three-tier architecture".
The top layer is the _presentation_ layer, which, in your typical Spring Boot web application, would be the web part, with all the `@Controller`s and related beans.
It relies on Spring internals for handling requests and responses, for serializing or deserializing Java objects to JSON and for translating errors to HTTP codes.
Then comes the _business_ or _domain_ layer, the collection of `@Service`s that contain the business logic.
This layer, unlike others, does not interface with specific components in the tech stack, and thus does not require any dedicated infrastructure.
At the bottom sits the _data_ or _persistence_ layer, which contains your app's interfaces to the database.
Just like the web layer, it needs the framework's code to work.

For testing purposes, this cake can be _sliced_, separating layers and providing the required Spring artifacts to test it.
Spring Boot gives you simple annotations for each technical scope it manages, which you can use instead of `@SpringBootTest`.
Each carve out a slice of your application and add the appropriate beans for testing said slice.
For example, `@WebMvcTest` will only load your web layer, such as `@Controller` and `@ControllerAdvice` beans, and also autoconfigures `MockMvcTester`.
Another annotation, `@DataJpaTest`, helps with data tests and limits scanning to `@Entity` classes and associated repositories.
It also loads data-related auto-configurations, replaces the default database by an in-memory instance and makes all tests transactional.
In between these, the business layer doesn't need much in terms of framework support, so there is no dedicated annotation for it.

No matter what architectural pattern, test slices cover aspects of your application that need Spring code, and this extends beyond just the web and data interfaces.
Here is a non-exhaustive list:

* `RestClient` and `WebClient`
* Most data-related projects such as JDBC, jOOQ, Redis, Mongo, LDAP, ElasticSearch and more
* GraphQL
* Spring Web Services (SOAP)
* JSON serialization and deserialization with Jackson

For a full list, referer to the reference documentation, under Testing > Testing Spring Boot Applications: https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html

We have briefly touched on why you would want to test only a few classes in your application in chapter 3, when we discussed "Building a test application from manually selected classes", and "Stubbing out dependencies by using mocks".
Test slices are another strategy to make thinner applications for testing, and they come with opinions and specific tooling to make testing certain use-cases easier.
Of course, as the saying goes, "there's no such thing as a free lunch", and test slices have their own limitations and tradeoffs.

== When to use test slices

A slice, while loading a _smaller_ application, still builds a Spring app, and adds a few tens of milliseconds of overhead.
Over enough tests, this can add up.
In chapter 3, we discussed how Spring caches test apps between tests, dramatically speeding up integration tests.
By default, the size of the cache is 32, and going over that limit will cause cache eviction, leading to a lot of thrashing in bigger test suites.
I once met Spring developers at a conference who told me they used to have hundreds of slices tests.
They were suffering from both the performance overhead and cache churn described above.
Getting rid of them sped up their test suite by a factor of 4 or 5.

NOTE: I reproduced this experiment, running a thousand very thin slices versus running a thousand tests against a single app context, and the single slice is an order of magnitude faster.
You can find this very un-scientific benchmark in the examples repository, under `ch5/performance`.

Test slices shine when these two conditions are met:

* *The app you are trying to test is large*.
This may mean it has many dependencies, or that it is simply slow to start.
When it has dependencies, like messages queues, databases and so forth, and you start some resource intensive process to support those tests, for example Testcontainers.
This may be slow, resource intensive or both.
There are many reasons other for an app to be slow to start, like Hibernate scanning packages for JPA entities, or custom business logic you execute on startup.
* *You want a fast feedback loop*.
If your test app takes a minute to start, but you only pay the cost once, it may not be a problem for you.
But imagine you are iterating on a given feature, and run your tests every few minutes.
Then getting around the startup overhead is a massive productivity boost.

NOTE: You write tests because they bring value to you.
But not all tests bring the same perspective on your code.
I often go back to Kent Beck's _Test Desiderata_, which describes 12 properties that make tests more valuable.
But some properties may interfere with each other.
For example, you can strive for _Predictive_ tests, meaning that "if the tests all pass, then the code under test should be suitable for production", at the expense of _Fast_ tests.
When I write a specific test suite, I try to qualify what I'm expecting to gain from it, and orient my design decisions around this.
Read more on the minisite https://testdesiderata.com.

The decision to use slices is very situational.
I cannot be much more specific than the general advice above without getting lost in the details, but we can think through a couple of concrete examples.

You work on a big, existing app, and a raw `@SpringBootTest` takes 20 seconds start.
You are working on a new `@Controller`, and iterating on custom input parsing and validation.
For now, you do not care about how the data flows to through your business domain after this initial step.
Since you practice test-driven development, tens of seconds is too long of a wait.
In this case, a slice test for the web layer is perfect.
It only exercises the specific code paths you are working on, requires little setup and runs in 50 milliseconds.

On the other hand, let's say you are working on a smaller CRUD application that only depends on a relational database, and exposes data through a few API endpoints.
You are creating a new repository, and adding a few query methods such as `findByNameOrderByNameAsc`.
Here a test slice won't be very useful.
You are touching the slowest aspect of the application, and removing a thin web layer won't noticeably speed up execution, and a regular `@SpringBootTest` will fail if you get your query method names wrong.

When a test suite starts being too slow, it's generally worth re-evaluating your current testing strategy, with mixes of slices and full `@SpringBootTest`.
And when you create a new test class, consider what aspect of your code you are testing and what properties you would like to surface.
This should inform you on whether to reach for a slice, or stay with a simpler `@SpringBootTest`.

At the time of this writing, there are 19 slice annotations.
This book does not strive to replace reference documentation, so we will not go over all of these, but we can study a few example among the most commonly used.

== `@WebMvcTest` for the web layer

In chapter 4, we went over all the available tools for testing web applications.
All of our examples used `@SpringBootTest`, and loaded the full app.
If you go back and browse the sample code, you'll find enough test to cover all the features in the application.
Some of these cover important edge cases that we have not discussed in detail.
These tests are good candidates for a slice test, as they exercise some of the web features, like `@ControllerAdvice`, without touching too much business logic.
Of course, the app is small enough that we can cover everything with full `@SpringBooTest`, but if you scale this demo 10 or 100-fold, it might become unwieldy, and a `@WebMvcTest` might become justified.
Let's see how you would use this slice in practice.

Before we start writing tests, let's discuss our weather application, and the changes we've made for this chapter..
You can find the complete code under `ch5/weather`, or directly at https://github.com/Kehrlann/spring-boot-testing-book-samples/tree/main/ch5/weather.
As usual, you can run the project with `./mvnw spring-boot:run`, and access the application at http://localhost:8080.
The sample has the same feature set and overall behavior as the application from chapter 4, with the addition of a "preferences" toolbar.
With this, users can use the app dark mode, sort cities alphabetically or by date added, and use either metric or imperial units.
You can see the toolbar in Figure <<ch5-figure-02>>.

The application also has some changes invisible to users.
It now renders 100% in the browser, without any server-side rendering: the JavaScript code aggregates data from HTTP APIs exposed by the application.
We have also re-architected the app using Spring Modulith, which we will discuss in detail further along in this chapter.
The consequence is that there is now a `@Controller` for cities, one for weather data, and one for preferences.

With this in mind, let's zoom in on one particular edge case we want to verify: a user can select a city only once.
The UI does not show cities that are already selected in the dropdown menu.
But if a race condition in the frontend causes the "select city" request to be sent twice, the Spring API also rejects it with a standard status code, `HTTP 409 Conflict`.
Internally, the business logic is implemented in the service layer, in a method called `addCityById(String cityId)`.
If the city has been selected previously, the method throws a `CityAlreadySelectedException`.
To avoid handling the exception manually, we use a Spring `@ControllerAdvice`, which handles exceptions throw in Spring controllers, and returns the appropriate response code.
We use the same mechanism for mapping `CityNotFoundException` to `HTTP 404 Not found`.

To write a slice test, we use the `@WebMvcTest` annotation instead of `@SpringBootTest`.
But, as the documentation states, only web-related components are loaded.
This means that `@Component`, `@Service` and other non-web beans are excluded from the test.
But our controllers have dependencies on such beans: the city controller depends on a `CityService`, and weather and preferences controllers have their own dedicated `WeatherService` and `PreferenceService`.
So if you were to write a slice test with just the `@WebMvcTest` annotation, as demonstrated in <<ch5-listing-webmvc-test-failing>>, they would error out because of missing dependencies.

[#ch5-listing-webmvc-test-failing, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']

[source,java]
----

The test above errors, with a message pointing a missing dependency: _Error creating bean with name 'cityController' defined in file [...]: Unsatisfied dependency expressed through constructor parameter 0_.
One level deeper in the stack trace, Spring will helpfully point to the required bean. with: _No qualifying bean of type 'wf.garnier.spring.boot.test.ch5.weather.city.CityService' available_.
A simple way to fix this particular problem is to provide the test app with the required bean, for example with a `@MockitoBean`, as we covered in chapter 3.
But you'd need to provide mocks for the dependencies of every controller in the application.
In our example, this represents only three services, but in a large production system, this might mean tens or hundreds of components, cluttering the test with just as many mocks you don't even use.

We have also reworked the architecture to use the Spring Modulith project, a Spring toolkit to build modular applications.
That project deserves its own full book, so we'll cover the big picture of how we use it in this particular case.
If you would like to learn more, a good place to start is the https://docs.spring.io/spring-modulith/reference/[official documentation].
With Modulith, each top-level package represents a _module_.
Modules may have an _internal_, inside which classes are considered, well, to that module.
Even if they are public, they cannot be accessed from other modules.
This renders dependencies between modules very explicit.
