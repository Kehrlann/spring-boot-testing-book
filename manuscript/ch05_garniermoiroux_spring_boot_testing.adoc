= Testing subsets of an application with test slices

This chapter covers

* Testing a single layer of the application with test slices, and when to use them
* Using slices in practice, such as `@WebMvcTest` and `@RestClientTest`
* Testing a business domain module with Spring Modulith
* Extending existing test slices and creating new slices

When testing applications with the `@SpringBootTest` annotation, as we've done extensively in the previous chapters, Spring Boot Tests loads the full application context, everything from controllers to repositories.
For big applications, with hundreds or thousands of beans, or with dependencies that have a long startup time like Hibernate, the impact on test suite execution time can be significant.
If your Spring application context takes a full minute to start up on your development machine, then launching a single test will take just as long.
With context caching, subsequent tests should be much faster, but one extra minute is already too long when you run tests very frequently.
And if you need multiple test contexts, the duration will scale linearly with the number of contexts, or worse.

I have practiced _Test Driven Development_ (TDD for short), which advocates for very short feedback loops.
Practitioners follow a _Red-Green-Refactor_ cycle: first you write a test, execute it and watch it fail (red), then write the minimal code you can to make it pass, execute it again and watch it pass (green).
You then take time to improve the code, for example removing duplication while keeping the tests green (refactor).
In TDD, basic unit tests start in milliseconds and do not hinder your workflow.
But the moment you introduce `@SpringBootTest`, you add latency, and having to wait for as little as 10 seconds is already a productivity killer.

The solution to this particular problem is to reduce the number of components loaded in your test application.
You can do this manually, as we've seen in Chapter 3, "Configuring and running an application for testing".
For complex apps, creating smaller application contexts requires some non-trivial amount of boilerplate.
Spring Boot Tests addresses the issue with _slice tests_, which test only a specific subset of components that share common characteristics, such as "all web `@Controller` beans".
Spring does not know anything about your business logic, so these slices are technical in nature: there's a slice for web tests, a slice for testing the data layer, and so on.

We'll start by discussing what slices are, and then we'll discover some example slices, explaining their scopes and how to use them.

[#ch5-section-1, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== Test slices: isolating technical components

The name "test slice" brings the _layered architecture_ pattern to mind.
It was very common in the 2000s, when Spring was first introduced.
It presents an application as a multi-layered cake, each with its own scope, and is sometimes referred to as "three-tier architecture".
The top layer is the _presentation_ layer, which, in your typical Spring Boot web application, would be the web part, with all the `@Controller` and related beans.
It relies on Spring internals for handling requests and responses, for serializing and deserializing Java objects to JSON and for translating errors to HTTP codes.
Then comes the _business_ or _domain_ layer, the collection of `@Service` that contain the business logic.
This layer, unlike others, contains your code only and does not use Spring tooling, and thus does not require any dedicated infrastructure.
At the bottom sits the _data_ or _persistence_ layer, which contains your app's interfaces to the database.
Just like the web layer, it needs the framework's code to work.

For testing purposes, this cake can be _sliced_, separating layers and providing the required Spring artifacts to test it.
Spring Boot gives you simple annotations for each technical scope it manages, which you can use instead of `@SpringBootTest`.
Each carves out a slice of your application and adds the appropriate beans for testing said slice.
For example, `@WebMvcTest` will only load your web layer, such as `@Controller` and `@ControllerAdvice` beans, and also autoconfigures `MockMvcTester`.
Another annotation, `@DataJpaTest`, helps with data tests and limits scanning to `@Entity` classes and associated repositories.
It also loads data-related auto-configurations, replaces the default database with an in-memory instance and makes all tests transactional.
In between these, the business layer doesn't need much in terms of framework support, so there is no dedicated annotation for it.

These are part of core Spring projects. Here is a non-exhaustive list of Spring APIs or projects that have dedicated test slices:

* Spring Web Services (SOAP)
* JSON serialization and deserialization with Jackson

Whatever technology dependency you are using, there's likely a test slice for you in Spring Boot.
As a rule of thumb, they are in a related `spring-boot-starter-<PROJECT>-test`, such as `spring-boot-starter-restclient-test` or `spring-boot-starter-data-jpa-test`.
For a full list, refer to the Spring Boot reference documentation, under https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html::[Testing > Testing Spring Boot Applications].

We have briefly touched on why you would want to test only a few classes in your application in chapter 3, when we discussed "Building a test application from manually selected classes", and "Stubbing out dependencies by using mocks".
Test slices are another strategy to make thinner applications for testing, and they come with opinions about what to include in your test app and how to configure it by default.
They also package specific tooling to make testing certain use-cases easier.
Of course, as the saying goes, "there's no such thing as a free lunch", and test slices have their own limitations and tradeoffs.

[#ch5-section-2, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== When to use test slices

A slice, while loading a _smaller_ application, still builds a Spring app, and adds a few tens of milliseconds of overhead.
Over enough tests, this can add up.
Previously, we discussed how Spring caches test apps between tests, dramatically speeding up integration tests.
By default, the size of the cache is 32, and going over that limit will cause entries to be _evicted_ (removed) from the cache.
This leads to a lot of _thrashing_ in bigger test suites, where a given test app is created, cached, evicted and then re-created later on.
Needless to say, this is a huge performance hit, as you are paying startup costs many times over.
I once met Spring developers at a conference who told me they used to have hundreds of slice tests.
They were suffering from both the performance overhead and cache issues described above.
Getting rid of slices and consolidating tests under a small number of test contexts sped up their test suite by a factor of four or five.

NOTE: I reproduced this experiment, running a thousand very thin slices versus running a thousand tests against a single app context.
Using a single slice is an order of magnitude faster.
You can find this very un-scientific benchmark in the examples repository, under `ch5/performance/web`.

Test slices shine when these two conditions are met:

* _The app you are trying to test is large_.
This may mean it has many dependencies, or that it is simply slow to start.
When it has dependencies, like message queues, databases and so forth, and you start some resource intensive process to support those tests, for example Testcontainers.
This may be slow, resource intensive or both.
There are many other reasons for an app to be slow to start, like Hibernate scanning packages for JPA entities, or custom business logic you execute on startup.
* _You want a fast feedback loop_.
If your test app takes a minute to start, but you only pay the cost once, it may not be a problem for you.
But imagine you are iterating on a given feature, and run your tests every few minutes.
Then getting around the startup overhead is a massive productivity boost.

NOTE: You write tests because they bring value to you.
"Value" is not a one-dimensional metric, and tests may be useful along multiple axes.
I often go back to Kent Beck's _Test Desiderata_, which describes twelve properties that make tests more valuable.
But some properties may interfere with each other.
For example, you can strive for _Predictive_ tests, meaning that "if the tests all pass, then the code under test should be suitable for production", at the expense of _Fast_ tests.
When I write a specific test suite, I try to qualify what I'm expecting to gain from it, and orient my design decisions around this.
Read more on the minisite https://testdesiderata.com.

The decision to use slices is very situational.
I cannot be much more specific than the previous general advice without getting lost in the details, but we can think through a couple of scenarios to illustrate the thought process:

You work on a big, existing app, and a raw `@SpringBootTest` takes 20 seconds start.
You are working on a new `@Controller`, and iterating on custom input parsing and validation.
For now, you do not care about how the data flows through your business domain after this initial step.
Since you practice test-driven development, tens of seconds is too long of a wait.
In this case, a slice test for the web layer is perfect.
It only exercises the specific code paths you are working on, requires little setup and runs in 50 milliseconds.

On the other hand, let's say you are working on a smaller CRUD application that only depends on a relational database, and exposes data through a few API endpoints.
You are creating a new repository, and adding a few query methods such as `findByNameOrderByNameAsc`.
Here a test slice won't be very useful.
You are touching the slowest aspect of the application already.
Removing a thin web layer won't noticeably speed up execution, and a plain `@SpringBootTest` will fail if you get your query method names wrong, so there is no need for dedicated tooling.

When a test suite starts being too slow, it's generally worth re-evaluating your current testing strategy, with a mix of slices and full `@SpringBootTest`.
And when you create a new test class, consider what aspect of your code you are testing and what properties you would like to surface.
This should inform you on whether to reach for a slice, or stay with a simpler `@SpringBootTest`.
If you settle on writing slice tests, and you want to improve performance, there are other options for speeding up your test suite.
You could use JUnit tags for organizing your tests, or Maven's Surefire "Integration Test" concepts.
Please refer to chapter 8 "Creating reusable test abstractions with JUnit" to learn more.

At the time of this writing, there are nineteen slice annotations.
This book does not strive to replace reference documentation, so we will not go over all of these, but we can study a few examples among the most commonly used.

This test only targets the `CityController`, and it's not possible to call endpoints declared in other controllers, such as `/api/weather`.
By reducing the scope of the test, we only need to provide a single bean to create a fully functional application context, here the `CityService`.
Mocks are most commonly used, but you can use any of the techniques discussed in chapter 3, such as custom test configurations or `@TestBean`.
This test verifies the edge case where users try to select a city, but it has already been selected.
To signal this, the `CityService` throws a `CityAlreadySelectedException`, so we configure our mock service to throw an exception, using `doThrow(...)`.
We use this instead of the familiar Mockito `when(...).then(...)` construct because `addCityById` returns `void`, thus `when(void)` is not valid Java and does not compile.
With the now familiar `MockMvcTester`, we make HTTP requests.
We did not need to annotate the class with `@AutoConfigureMockMvc`, because `@WebMvcTest` itself is annotated with that autoconfiguration.

This example shows a test slice loading a single controller, but this is a consequence of having such a small demo application.
In a bigger app, you typically want to avoid the "one controller, one test slice" pattern, as it leads to a lot of thrashing in the context cache, and much slower test suites.
Usually, you want to test _related_ controllers together, that share similar dependencies, so that you can provide a single set of mock beans.
The test annotation will have the list of controllers under test, in the form `@WebMvcTest(controllers = { A.class, B.class, ... })`.
In many codebases, boundaries are not perfectly defined, and it's common to see controllers depending on many unrelated dependencies, which makes grouping controllers very difficult.
If you struggle making clean web slice tests that have a limited number of dependencies, your tests are probably telling you something about the architecture of your application.
In that case, you may want to take a look at Spring Modulith to give you some tools to split up your app into decoupled modules.
We'll introduce Modulith in more detail in section <<ch5-section-5>>, and explain how it can help in testing.

But before we explore architecture concerns, let's cover another technical aspect of our application: the HTTP clients it uses to call the external weather API.
Spring Boot has a dedicated slice testing the client side of HTTP, called `@RestClientTest`.

== `@RestClientTest` for HTTP clients

The majority of Spring apps expose a web server, and `@WebMvcTest` has been included in Boot since version 1.4.0, in 2016.
It is common in Spring test suites.

Our application is a web app, but it is also a web *client*, that makes HTTP requests to Open Meteo to get weather data.
If we want to keep our tests local, and avoid reaching out to network resources, we have to replace the external service with something else.
One option is to stub the entire `WeatherService`, and assume the implementation will be fully covered by end-to-end tests.
But when you are creating the service itself, it'd be nice to have some tests to iterate faster.
Another option is to replace the third-party service with a server that presents pre-determined responses to our `RestClient`.
It does not ensure the full system works - after all, if Open Meteo decides to change the fields in their JSON responses, our tests would not catch it.
What we are testing is a _model of that service_, purposefully built for our test suite, which gives us two interesting properties.
First, it allows us to iterate quickly and locally, which is useful when the service contains logic we want to validate, for example transforming the upstream data to better fit our model.
Second, it serves as a record of our understanding of the external service, a documentation of sorts.
In tests, we write down example API responses that a human can parse at a glance, and we cover all HTTP errors we have encountered with the real service.

Spring has built-in utilities for testing how `RestClient` interacts with a server, by returning mock HTTP responses from a `MockRestServiceServer`.
It is not a full server, and does not serve real HTTP traffic, and is thus lighter than alternatives that require you to run a separate web server in your tests, such as WireMock or MockServer.
With this lightweight implementation, Spring hooks up to `RestClient` internals to create fake HTTP requests and produce programmed responses for most common use-cases.
Since `RestClient` is immutable, it is configured through a property of the `RestClient.Builder`.

This is a very small test slice, which only loads your service, the mock server and the infrastructure for testing HTTP clients.
Slice tests scan your code and select which classes to load at the type level, before loading the classes in the JVM.
They do not access methods or constructors, and cannot detect which Spring components accept a `RestClient.Builder` as a constructor dependency, so you need to explicitly list which Spring beans you intend to test.
In our example we're targeting a single service class, but you can add as many as you need.
The `@RestClientTest` annotation loads two beans, a `MockRestServiceServer` and a `RestClientCustomizer`
The customizer modifies the default Boot `RestClient` and connects it to the mock server.
Here, our service's constructor only takes a rest client builder as a dependency.
If your code requires more dependencies, such as other services, they will not be loaded automatically, and you'll have to provide them through the usual test configuration, Mockito bean or test bean, as discussed in chapter 3.

First, we configure expected requests for `MockRestServiceServer`, and the pre-defined responses it should return for certain requests.
The mock expectations are built using a `RequestMatcher` interface, which takes the client requests and decides if an incoming request matches.
For most common requests, you can build them using factory methods in the `MockRestRequestMatchers` class, such as `requestTo("https://example.com/foobar")`, `queryParam`, `header`, `method`, etc.
With this configuration, expectations are not strict: if no request is performed that matches the configuration, the test will not fail.
Each expectation corresponds to a single request, so configuring two expected requests and making three calls fail the test.
The order is also important: if the first configured request expects a latitude to be 48 and the second a latitude to be 32, making an HTTP request with latitude = 32 first will also fail.
The responses are created using the `ResponseCreator` interface, typically with factory methods from `MockRestResponseCreators`.
Here, we are using `withSuccess()` to return HTTP 200, with a pre-programmed body.

In this test, we expect at least one call to our mock rest server, and at most two.
We call verify at different stages of using our service.
When there are no calls made, `verify()` fails.
When we have 1 or 2 calls, it succeeds.
When we call the service a third time, it issues a third call to our mock server, which is unexpected, and fails.

`MockRestServiceServer` is both simple to use and versatile.
There are limitations to it though: it is not a full web server, and is not intended to become one.
Some features of `RestClient`, such as read and connect timeouts, are implemented at the network layer by the underlying HTTP client, and cannot be tested this way.
Other features are beyond the scope of the mock server, such as server-sent-events or websockets.
If you want to write tests for such features, you'll need to either perform end-to-end testing or use full mock web servers in your integration tests.
But for simple request-response scenarios, `MockRestServiceServer` is more than enough.

[#ch5-section-5, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== Business-logic slices with Modulith

Spring Boot ties projects from the Spring portfolio together, adds ease of use, good defaults and many extension points.
Each project brings its own specific technical capabilities, such as connecting to a database or serving web requests, and Boot can discover those aspects and offer dedicated slices.
It does not know anything about your business domain and the architecture of your code.
But there is a project in the ecosystem that focuses on architecture: Spring Modulith.

[QUOTE,Spring Modulith reference documentation]
____
Spring Modulith is an opinionated toolkit to build domain-driven, modular applications with Spring Boot.
In the same way that Spring Boot has an opinion on the technical arrangement of an application, Spring Modulith implements an opinion on how to structure an app functionally and allows its individual, logical parts to interact with each other.
____

Since it is a relatively new project compared to most Spring projects, it is not widely adopted yet.
Before we get to testing with Modulith, let's explain what the project does, and how we used it in our weather application.

[#ch5-section-5-introduction-modulith, reftext={chapter}.{section}.{counter:subsection}, caption='{chapter}.{section}.{subsection}']
=== A short introduction to Spring Modulith

The main idea behind Modulith is to _modularize_ your codebase, by splitting it up into small, cohesive chunks of code.
Each group of features is called a _module_ and is represented by a Java package.
For example, in our app, we have a module called City which handles listing and searching cities as well as selecting/unselecting cities.
Each module has an exposed API, which consists of public Java classes at the root of the package.
It also has code that should only be accessed from the module.
For that, you can use Java's package-private visibility level, but when you have nested packages you sometimes need to make classes public.
Modulith allows you to make certain public classes internal, by either calling them `...Internal.java`, or placing them in an `.internal` sub-package.
If you reference an internal class from another module, this is valid Java code, but it breaches the module's contract.
Modulith has testing utilities to verify that boundaries are respected:

=== Testing with Modulith

Since Modulith is an architecture-focused project, it can infer things about the _structure_ of your application, and help you test small, self-contained domains.
In a way, it introduces _vertical_ test slices, that load all technical aspects, the web layer, the data layer, etc., but restricts the scope of the test to a given application module, without loading other modules.

Our test has to provide a test implementation, and defines a `class TestCity implements City` that we use as a return value for our Mockito bean.

== Navigating tradeoffs of data-layer tests

One of the most common test slices you'll find in examples online is `@DataJpaTest`.
When you learn about slice testing the first time, there's a temptation to slice everything.
As we've touched on in section <<ch5-section-2>>, there's a cost to using test slices, and you should weigh tradeoffs before making the decision, and decide if they bring enough value.
Specifically, annotations for testing the data layer, such as `@DataJpaTest` or `@DataJdbcTest` have core differences with web-layer tests.
`Repository` beans sit at the bottom of the stack, or, more precisely, they are leaves in your bean graph: other beans depend on them, and they themselves have no dependencies.
Data slices contain only repositories and do not require you to inject or mock other beans.
If you already have `@SpringBootTest` tests, repositories are already included, and you can autowire them directly into your test classes.
This means you can write data-focused tests using the same cached application as your regular `@SpringBootTest` tests, without incurring the costs of bootstrapping the data infrastructure a second time, saving seconds or tens of seconds at a time.
There are legitimate use-cases for using data-layer slices, starting with the reasons we outlined in section <<ch5-section-2>>: the application under test is large, and you'd like to avoid loading the full context.
You may also want to run tests that require specific fixtures loaded in the database when a test suite starts, and you don't want to mix this with the rest of your integration tests.

If you do go for `@DataJpaTest` or `@DataJdbcTest`, there are a few things you should be aware of.
First, all tests are _transactional_.
Your test class will be meta-annotated with `@Transactional`, and all tests will run inside a transaction.
Any change you make to the database within a given test will be rolled back when the test finishes.
We will not explore `@Transactional` support here, but you can refer to the Spring Framework https://docs.spring.io/spring-framework/reference/testing/testcontext-framework/tx.html::[Reference documentation] for more context.
By default, the data annotations also replace the default database of your application with an in-memory database implemented in Java.
This is controlled by the `@AutoConfigureTestDatabase` annotation that slice tests embed.
Supported test databases are Apache Derby and H2.
For this to work, you need to import either of these in your classpath:

[#ch5-listing-h2-derby, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Dependencies for H2 or Derby
[source,xml]
----
<!-- H2 -->
<dependency>
  <groupId>com.h2database</groupId>
  <artifactId>h2</artifactId>
  <scope>test</scope>
</dependency>
<!-- Or Derby -->
<dependency>
  <groupId>org.apache.derby</groupId>
  <artifactId>derby</artifactId>
  <scope>test</scope>
</dependency>
----

This may be useful when you want to execute tests without running a full standalone relational database alongside your test suite.
In `@DataJpaTest` and its JDBC equivalent, replacing the database is controlled by another annotation, `@AutoConfigureTestDatabase`.

TIP: You use `@AutoConfigureTestDatabase` in conjunction with the usual `@SpringBootTest` annotation, and use an in-memory database in those tests.

Replacing your production database with an in-memory implementation only really works if your queries are portable across DB systems.
If you use an engine-specific dialect, or database extensions, they won't be supported by these in-memory databases.
In that case, you need to run an instance of, for example, Postgres.
Spring Boot Tests can automate this via the Testcontainers project.
It simplifies setting up and managing Docker containers, and connects your test app to those containers automatically.
To learn more, refer to chapter 9, "Testing against real service dependencies with Testcontainers".

== Going further: understanding how test slices work

We've seen how you can use test slices to write focused tests, and how to use them.
They autoconfigure things, and load beans selectively.
Like most things in Spring Boot, it looks like magic on the surface, but it is nothing more than solid infrastructure code, designed for reuse and extensibility.
You can use this foundation to build your own slices.
Existing test slice annotations are built on this, and can be a good source of inspiration.
Similar to what we've done with `@SpringBootTest` in chapter 3, let's look at `@WebMvcTest` in detail to understand the different parts:

[#ch5-listing-wembvctest-explained, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Simplified code for `@WebMvcTest` annotation
[source,java]
----
@ExtendWith(SpringExtension.class) <1>
@BootstrapWith(WebMvcTestContextBootstrapper.class) <2>
@TypeExcludeFilters(WebMvcTypeExcludeFilter.class) <3>
@OverrideAutoConfiguration(enabled = false) <4>
@ImportAutoConfiguration <4>
@AutoConfigureWebMvc <4>
@AutoConfigureMockMvc <4>
public @interface WebMvcTest {

	String[] properties() default {}; <5>

	Class<?>[] controllers() default {}; <6>

	Filter[] includeFilters() default {}; <7>

	Filter[] excludeFilters() default {}; <7>

}

----
<1> The Spring JUnit extension
<2> Configure the JUnit extension
<3> Configure which beans will be included by default
<4> Selectively import auto-configurations
<5> Configure application properties
<6> Configure which controllers are included
<7> User override for which beans are included

To explain what this annotation does, let's start with a few elements you might recognize from the `@SpringBootTest` annotation.
It imports the Spring JUnit extension, which hooks Spring into the JUnit lifecycle.
It has its own "context bootstrapper" `WebMvcTestContextBootstrapper`, which is a subtype of the `SpringBootTestContextBootstrapper` that `@SpringBootTest` uses.
It configures the app for testing, by reading the `properties` parameter, and specifically setting up the equivalent of `webEnvironment = MOCK` mode, since we are doing web tests.
There can only ever be one `TestContextBootstrapper` for a given test class, and therefore, a test class can only ever have a single slice annotation.
If you try to combine test slices, the tests won't run and you'll get the following Spring TestContext Framework exception:

----
Configuration error: found multiple declarations of @BootstrapWith for test class [your class]: ...
----

`@WebMvcTest` also has code you won't find in `@SpringBootTest`, falling in one of two categories: autoconfiguration and selecting which beans to load in the context.
Every slice is built this way, and the difference is in the configuration of these features.

[#ch5-section-6-autoconfiguration, reftext={chapter}.{section}.{counter:subsection}, caption='{chapter}.{section}.{subsection}']
=== Test slice autoconfiguration

On the autoconfiguration side, `@OverrideAutoConfiguration(enabled = false)` disables the default Boot setup.
This avoids loading, say, JPA autoconfiguration when we only want to configure web-related components.
To load the few autoconfiguration classes you need for your web tests, the annotation uses `@AutoConfigureWebMvc` and `@AutoConfigureMockMvc`.
The former loads configurations used in a typical web application, for example WebMVC or HTTP encoding config.
We've used the latter manually in some tests: it adds Mock MVC support to your tests, with, for example, `MockMvcTester`.

There's also `@ImportAutoConfiguration`, which is a Spring Boot hook for registering additional autoconfiguration classes on any given annotation.
In your production Boot application, autoconfiguration is done through the `@EnableAutoConfiguration` annotation, which will automatically discover config classes as needed.
But in tests, you want to restrict what is loaded in the context to match what you are currently testing, and ideally nothing more.
This is where `@ImportAutoConfiguration` comes in.
It mimics the behavior of the regular Spring Boot autoconfiguration mechanism, but scopes down which classes will be considered.
You can pass a list of class you want to load, e.g. `@ImportAutoConfiguration(classes = { WebMvcAutoConfiguration.class })`, and in that case, it behaves like a Spring `@Import` but respecting the autoconf lifecycle.
If you omit the classes parameter, the annotation acts as a signal that Boot should search the classpath for file describing which autoconfiguration classes to load.
It will find any file in `META-INF/spring/<fully qualified annotation name>.imports`, read it, and load the classes listed in it.
For example, here's `META-INF/spring/org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureWebMvc.imports` from the `spring-boot-starter-webmvc-test` module, with package names shortened to fit on the page:

----
o.s.b.autoconfigure.context.MessageSourceAutoConfiguration
o.s.b.autoconfigure.task.TaskExecutionAutoConfiguration
o.s.b.servlet.autoconfigure.HttpEncodingAutoConfiguration
o.s.b.webmvc.autoconfigure.WebMvcAutoConfiguration
o.s.b.webmvc.autoconfigure.error.ErrorMvcAutoConfiguration
optional:o.s.b.h.c.a.HttpMessageConvertersAutoConfiguration
optional:o.s.b.validation.a.ValidationAutoConfiguration
----

This mechanism enables you to provide your own customizations for `@WebMvcTest`, `@AutoConfigureWebMvc` or any annotation that bears `@ImportAutoConfiguration`.
Simply create a file with the correct naming, list the classes you want to load as autoconfiguration, one class per line, and Spring Boot will load them when it detects the corresponding annotation.
We won't showcase a full example here, but if you'd like to see it in action, check out the `WebMvcTestUserAutoConfiguration` file in the samples for this chapter.
It uses the import infrastructure to add a log line to every web slice test.
Spring Boot itself has modular configuration built using these hooks.
For example, testing dependencies for the Thymeleaf templating engine is imported in the module `org.springframework.boot:spring-boot-starter-thymeleaf-test`.
The jar contains its own `AutoConfigureWebMvc.imports` file, which adds `ThymeleafAutoConfiguration` to every web-related test, without users having to add anything to their config.

[#ch5-section-6-type-exclusion, reftext={chapter}.{section}.{counter:subsection}, caption='{chapter}.{section}.{subsection}']
=== Type exclusion (and inclusion)

The second category of `@WebMvcTest` specific code is related to _Type Exclusion_.
The name originates from Spring's _Component Scanning_, which scans your classpath to find beans to add to the application context.
This tool enables users to selectively exclude certain types from the context.
In testing, though, it focuses on _including_ certain beans in your application context, rather than explicitly excluding things.
The `@TypeExcludeFilters(WebMvcTypeExcludeFilter.class)` annotation defines default rules for bean selection.
The filter class is where you'll find the list of included types, `@Controller`, `@ControllerAdvice`, etc.
In addition to the defaults, it reads the `controllers = ...` parameter from the annotation, to include only certain specific controllers rather than all controllers in your app.
You can customize the behavior with `includeFilters` and `excludeFilters`.
Each slice annotation has its own filter.
For example, `@DataJpaTest` does not include _any_ Spring component, and relies on pure JPA and Hibernate scanning for finding and wiring repository-related components.
Type filtering is designed to be blazing fast.
It does not load the classes in the JVM to make decisions, and instead reads the Java bytecode from the class files and parses just enough to read packages, class names and annotations.
This is how it can find, for example, all `@Controller`-annotated classes without massively slowing down the startup time of the test application.

In the vast majority of cases, you shouldn't need to write your custom slices.
Even if you have common configuration across many test classes, a single custom annotation that is meta-annotated with Spring annotations is often enough.
Custom slices become interesting when you want to provide test automation that Spring Boot Tests do not support.
For example, if your app has many integrations with third-party HTTP APIs, and you need a more powerful mock server, a custom `@WireMockTest` slice may be a good choice.

[#ch5-summary, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== Summary

- To avoid loading a full application context for tests, you can use Spring Boot test slices.
- Test slices provided by Spring boot are technical in nature, and isolate a subset of the application by technical domain (Web, Data, RestClient, GraphQL, etc).
- While powerful, test slices have associated costs and should be a conscious choice.
Watch out for context thrashing when using too many test slices.
- `@WebMvcTest` is an annotation for tests focused on the web layer of your application.
It brings all the required web components, including your own web code, such as `@Controller` beans.
Other layers are not present, so you need to provide replacement beans for the dependencies of your controllers, for example with `@MockitoBean` or `@TestBean`.
- `@RestClientTest` provides all the necessary infrastructure for testing HTTP client integrations.
It connects your `RestClient` instances to a mock HTTP server, `MockRestServiceServer`, which you can configure with canned responses for your tests.
- Spring Modulith brings _vertical_ slices, cutting the application along business domain boundaries, or more specifically, slicing by _module_.
`@ApplicationModuleTest` is an equivalent of `@SpringBootTest` scoped to a single module, and `@ModuleSlicing` restricts existing Spring Boot slices to a module.
- Data layer tests can often be achieved with the test context provided by `@SpringBootTest`, but dedicated slice tests may prove useful when you want fast feedback on a large app with many dependencies.
They integrate annotations you can use in other contexts, such as `@AutoConfigureTestDatabase` and `@Transactional`.
- A test slice is built on a Spring Boot specific `TestContextBootstrapper` which sets up the app for testing.
It has specific `TypeExcludeFilters` to decide which classes to load, using Spring scanning technologies.
It also has autoconfiguration dedicated to the technologies under test, such as `@AutoConfigureWebMvc` or `@AutoConfigureTestDatabase`, and third party libraries can contribute additional autoconfig through `.imports` files.
