= Configuring and running an application for testing

This chapter covers

* How the `@SpringBootTest` annotation works
* Accessing beans and properties in your tests
* Configuring the application under test
* Stubbing and mocking dependencies
* Speeding up the tests by caching the test app

When you annotate a test class with `@SpringBootTest`, it automatically detects your application's configuration, configures and optimizes it for a testing scenario, manages its lifecycle, and makes it accessible in your tests.
You might need to update the configuration, for example to stub out an external service that you do not want to touch in your test, as we've seen in the <<ch02_garniermoiroux_spring_boot_testing.adoc#ch2-section-6, previous chapter>>.
You may have created several variants of your software depending on user configuration, for example with region-specific behavior controlled by properties or profiles, and want to run separate test suites for each.
Or maybe you would like to split your integration tests by logical "module", and you want to run only a subset of your application for each given module.

Spring Boot Test has dedicated tooling for all of these use-cases, from changing a few properties to manually selecting which components are loaded in your test application.
Of course, there are important tradeoffs associated with customizing the application under test, and you should be aware of them when creating tests.
Let's dive in!

NOTE: All samples in this chapter are in the `ch3/configuration` directory of the samples repository, accessible directly at https://github.com/Kehrlann/spring-boot-testing-book-samples/tree/main/ch3/configuration.
There many more examples than those listed in this chapter, variations that won't go over but that may be useful.
I encourage you to download the project and skim over the test files as you go through the chapter.

[#ch3-section-1, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== Understanding how the `@SpringBootTest` annotation works

In the <<ch02_garniermoiroux_spring_boot_testing.adoc#ch2-title, previous chapter>>, we've annotated our test class with `@SpringBootTest`, and you'll encounter it throughout this entire book.
It is useful and easy to get started with, but sometimes described as "auto-magic":
it does so many things automatically in the background, most of which you don't understand or even realize are happening, that it feels like magic.
While the implementation details are deep and intricate, at a high level, it is not particularly scary.
It does roughly four different things:

1. It tells JUnit that a Spring application is required for the tests, and that it should trigger Spring-specific behavior
2. It creates a Spring application context from your Spring Boot configuration, suitable for testing scenarios
3. It runs this application context, and shuts it down when the tests are finished
4. It allows you to interact with the application in your tests, through annotations such as `@Autowired`, `@MockitoBean`, etc.

It also provides a few configuration options so you can tweak the default test application.
For example, you can disable the web capabilities by using `@SpringBootTest(webEnvironment = NONE)`.
Spring is an open-source project, so, to understand how it achieves all those things, you can peek under the cover and look at the code of the annotation.
I've simplified it for you in listing <<ch3-listing-springboottest>>.

[#ch3-listing-springboottest, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Simplified code for @SpringBootTest extension.
[source,java]
----
@ExtendWith(SpringExtension.class) // <1>
@BootstrapWith(SpringBootTestContextBootstrapper.class) // <2>
public @interface SpringBootTest {

  // Below are generic Spring configuration options, exposed by @SpringBootTest
  String[] properties() default {}; // <3>

  Class<?>[] classes() default {}; // <3>

  // Below are Spring Boot specific configuration options
  WebEnvironment webEnvironment() default WebEnvironment.MOCK; // <3>

  UseMainMethod useMainMethod() default UseMainMethod.NEVER; // <3>

  String[] args() default {}; // <3>

}
----
<1> A Spring-provided JUnit extension
<2> Configuration for the SpringExtension
<3> Configuration for @SpringBootTest

As you see, it's a meta-annotation: it brings in other annotations.
The first interesting bit is `@ExtendWith(...)`, which registers a JUnit extension.
It allows you to add custom code to run on the lifecycle of a test, for example "after each test" or "when the test class is created".
In this case, it registers the `SpringExtension`.
This is the most important class, the glue between your tests and your Spring application, which does most of the heavy lifting for Spring Boot Tests.
It is the entrypoint into the Spring "TestContext" framework, which is responsible for putting together a test app, running it before a test is executed and shutting it down after, and making it available to the test class through `@Autowired` annotations.
The second annotation, `@BootstrapWith(...)`, is a TestContext annotation, which specifies how to create a Spring app from your own configuration.
In this case, it uses Spring Boot specific setup, which detects your `@SpringBootApplication` on your main class, and marginally adjusts the configuration to make it a "test app".
For example, it does not run an embedded web server by default.
The last notable elements are the `@SpringBootTest` annotation parameters.
Those are detected by the `SpringBootTestContextBootstrapper`, which uses the values to further modify the configuration of the test app before running it.
For example, you can instruct Spring Boot Tests to start a full web server, or to use the main method of the app.

NOTE: All the Spring Framework utilities for testing are grouped under the "Spring TestContext Framework" umbrella, part of Spring Framework itself.
It has a large feature set, that goes way beyond Spring Boot apps.
Although it is fairly advanced material, I encourage you to take the time to at least skim the reference documentation, available at https://docs.spring.io/spring-framework/reference/testing/testcontext-framework.html, with a focus on the first few sections.
Having a rough idea of the architecture and the affordances it offers could prove useful one day, when you have specific test architecture needs.

With its simplicity and core configuration parameters, the `@SpringBootTest` annotation is the one-stop shop for configuring, managing and accessing an app for your integration tests.
Let's start by interacting with our test application.

== Interacting with the application

With Spring Boot Test, as we've already seen, you can access any bean in the context.
You can also access any environment property loaded in the app.
Say we have an extremely basic application, that provides 4 beans of type `Thing`:

}

Three main Spring annotations are supported in tests.
The most interesting is `@Autowired`, which allows you to fetch a bean or collection of beans from the `ApplicationContext`.
It's perfect for calling internal APIs or verifying the state in the database.
You can use it both on a field of the test class, like the "things" list in `InteractWithAppTests`, or as a parameter for a test method, like the "redThing" parameter in the method of the same name.
Following the semantics of `@Autowired` in Spring code, you can also pair it with `@Qualifier` to obtain a bean by name, as we do for the "redThing".
The last supported annotation is `@Value(...)`, which allows you to access values from your configuration files like `application.properties` and `application.yml`.
It is less frequently used in tests, but can prove useful when you want to use a property in tests, for example to verify the default configuration values for your application.
It is the same annotation that you sometimes use in your production code, so you can even use it with the Spring Expression Language, or SpEL, and compute data dynamically.
Therefore `@Value("#{21 + 21}") int value` is a perfectly valid expression, albeit of limited value.
Technically, you can also autowire the entire `ApplicationContext`, which then allows you to access any bean or any property in the context, at the expense of writing a little bit more code.
This is rarely seen in the wild.

NOTE: The Spring Expression Language (SpEL) is a mini programming language inside strings that Spring evaluates at runtime.
In your annotations, you can write expressions in special markers like `#{"Hello " + user.name}`, and Spring will use the context (your configuration files, method parameters, ...) to compute the value.
To learn more, please refer to the official documentation: https://docs.spring.io/spring-framework/reference/core/expressions.html.

We've seen the basics "reading" from our application, like accessing beans and property values.
Now let's "write to", or more precisely, "configure" our test app.

[#ch3-section-3-activating-a-profile, reftext={chapter}.{section}.{counter:subsection}, caption='{chapter}.{section}.{subsection}']
=== Activating a profile

Spring supports adding the `@Profile` annotation on bean definitions to express that some beans are to be loaded when a given profile is active.
A profile is activated using a system property, for example `spring.profiles.active="prod,france"` turns on profiles "prod" and "france".
Additionally, Spring Boot will pick properties files with the profile name, such as `application-prod.properties` or `application-france.yml`.
If you would like to override many properties in your tests, you can group them in a test-specific properties file, and give it a profile name, such as "test".
Be sure to add that file to `src/test/resources`, so that it is never picked up by your production code.
Then add the profile in your tests using `@ActiveProfiles`:

[#ch3-listing-profile, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Using a profile in tests
[source,java,indent=0]
----
include::../code/ch3/configuration/src/test/java/wf/garnier/spring/boot/test/ch3/configuration/PropertiesTests.java[tags=properties-profile;!ignored]
----

With this, the "test" profile is applied to the test app, and Spring Boot will read the `src/test/resources/application-test.properties` file (YAML works, too), and use it to override properties.
It will also pick up any bean that is annotated with `@Profile("test")`.
In practice, you should not add test-specific code to your production app.
Those features could be turned on by mistake in a live environment, likely to cause bugs and unintended behavior.
Remember: we've added the properties file in `src/test/resources`.
To add beans to test scenarios without touching your production code, you can use the regular `@Configuration` annotation, and Spring Boot Tests also has a specific annotation: `@TestConfiguration`.

NOTE: It is acceptable to use `@ActiveProfiles` to turn on certain production features selectively.
For example, imagine you have an optional "Single Sign On" feature behind an `sso` profile, and you only want to turn it on in some subset of tests, you can use `@ActiveProfiles("sso")`.

[#ch3-section-3-adding-configuration, reftext={chapter}.{section}.{counter:subsection}, caption='{chapter}.{section}.{subsection}']
=== Adding configuration with `@Configuration` and `@TestConfiguration`

If you would like to add test-specific beans, there are two possibilities.
First, you can create a `@Configuration` class in your test directory.
If it is located in the same package as your Spring Boot main class, or any sub-package, they will be added to the configuration of the test application.
Let's examine a concrete example, with the following file structure:

[#ch3-listing-file-structure, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Project file structure for custom configurations
----
src
├─ main
│  └─ java
│     └─ com
│        └─ example
│           ├─ DemoApplication.java <1>
│           ├─ ProductionConfiguration.java
│           └─ ... more production code ...
└─ test
   └─ java
      └─ com
         └─ example
         │  ├─ TopLevelConfiguration.java <2>
         │  ├─ nested
         │  │ └─ NestedConfiguration.java <2>
         │  └─ ... your tests ...
         └─ notincluded
            └─ ExcludedConfiguration.java <3>
----
<1> The main class
<2> These configuration files will be included
<3> This will not be included in the test app

In this setup, the app's main class, `DemoApplication`, is in the package `com.example`.
Since it is a `@SpringBootApplication`, component scanning is active: Spring Boot will look at the JVM's classpath and find every `@Configuration`, `@Component`, `@Repository`, etc., included in `com.example` and its sub-packages.
When the tests are compiled, the classpath will contain `com.example.ProductionConfiguration` from the production code, but also classes from the test directory, including `com.example.TopLevelConfiguration`, `com.example.nested.NestedConfiguration`, `com.notincluded.ExcludedConfiguration`, as well as classes containing your tests.
In that case, both `MaintTestConfiguration` and `NestedConfiguration` are under `com.example.*`, and will be considered part of the test app's configuration.

But there's one big caveat with this approach: every single `@SpringBootTest` will pick up these two additional configuration classes, "Main" and "Nested".
It is useful when adding beans that you want to have in all your tests, but there are cases where you only want to modify the config for a subset of tests.
While you could hack your way around with different packages or custom exclude rules for component scanning, that would be a lot of boilerplate.
So the Spring Boot team came up with the appropriate tool for the job, namely, the `@TestConfiguration` annotation.
It works like a regular Spring configuration, but you have to enable it explicitly.
The first possibility is to nest the configuration class inside your test class, like so:

So far, we've seen how to make a test application and add custom, test-specific bean to the default "production" configuration.
But for a big application, say your typical multi-module monolith, starting the full app might be "expensive" and take a long time. `@SpringBootTest` has a dedicated parameter for that very specific use-case: `classes=`, which you can use to create an application from a subset of configuration classes.

[#ch3-section-3-configuring-from-scratch, reftext={chapter}.{section}.{counter:subsection}, caption='{chapter}.{section}.{subsection}']
=== Building a test application from manually selected classes

We have mentioned in <<ch02_garniermoiroux_spring_boot_testing.adoc#ch2-section-7, chapter 2>> that, when you just want to test a few classes, you may not need `@SpringBootTest`.
Specifically, if you want to test a `FooService` that has a dependency on a `BarService` and a `FooRepository`, you do not need Spring to do the auto-wiring for you.
In some cases, though, you do need a bit of Spring machinery.
Say you want to have Spring parse `properties` files for you, perform data validation, or activate `@Conditional` annotations on your beans, without booting the full production app.
In that case, you can configure a much smaller test application context while retaining the bulk of Spring Boot features, as demonstrated in listing <<ch3-listing-classes>>:

.Using the `classes = {...}` parameter

----

<1> List the classes you want to include

By using `classes = { ThingConfiguration.class }`, we ensure that only the beans in `ThingConfiguration` will be loaded, and nothing from your custom code.
The classes can be either `@Configuration` classes containing beans, or singleton bean classes annotated with `@Component`, `@Service`, `@Repository`, etc.
Since Spring Boot auto-configurations are loaded from your main application class annotated with `@SpringBootApplication`, they are not included here, and will not be loaded either.
Please note that if your `ThingConfiguration` has annotations which triggers other classes being present, such as `@Import`, `@ComponentScan`, `@EnableConfigurationProperties`, etc, those annotations will be used.
In that case, your test app may contain many more beans than you expected.
To avoid those issues, you must structure your code in a way that is composable, and avoid using a single giant configuration class that pulls the entire universe in your application.
Instead, you write separate config classes with focused areas of concerns, for example one for data-related infrastructure bean, one for security, etc.

Of course, if you want this test application to start, all the beans in `ThingConfiguration` must have access to their full dependency graph.
If they rely on beans defined outside the scope of this configuration class, the app cannot start.
You can visualize the issue in figure <<ch3-figure-01>>.

[#ch3-figure-01, reftext={chapter}.{counter:figure}, caption='{figure-caption}.{counter:figure-number} ']
.Our test only imports the `ThingConfiguration`. The scope of the test is included in the box. The dashed arrows point from beans to the configuration classes in which they are defined, and the solid arrows represent dependencies. Through the GreenThing bean, our test has dependencies on components outside its scope.
image::ch03_f001_garniermoiroux.png[]

In this example, both the `RedThing` and `PinkThing` beans have all the dependencies they need to be wired up.
But the `GreenThing` does not respect the boundaries of our test, and needs components defined outside our scope.
To fix the issue, we need to provide `YellowGizmo` and a `BlueWidget`.
We could make the scope of our test bigger by adding more entries to `classes = {...}`, but it would defeat the entire purpose of this exercise: we're trying to make the test application as small as possible.
And if went down that path, we might need to pull our dependencies' dependencies, sometimes multiple levels deep.
To find all the classes that are required for a test to run, you'd have to slowly follow the bean graph and find all the dependencies, losing many of the benefits of the Spring IoC container along the way.
Instead, it is much easier to write a custom `@TestConfiguration` class, to provide just the beans we are missing, in this case `YellowGizmo` and a `BlueWidget`.
We do not even need to use the real classes: as long as Spring finds an implementation or a subclass of `Gizmo` and `Widget` available, it can create a `GreenThing` instance.
This means we can provide stub implementations, that have no behavior, and the test app will start.
And since we are not using the real classes, we are free to ignore any dependency that the real, production code would have.
For all the cases where you'd want to provide or replace existing beans, the Spring TestContext framework provides two handy features: mock beans and test beans.

[#ch3-section-4, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== Stubbing out dependencies by using mocks

Let's build up on the example from the previous section <<ch3-section-3-configuring-from-scratch>>.
If we ran a Spring Boot Test with just the `ThingConfiguration` class, it would fail with the usual Spring Boot message:

----
***************************
APPLICATION FAILED TO START
***************************

Description:

Parameter 0 of method greenThing in wf.garnier.spring.boot.test.ch3.configuration.ThingConfiguration required a bean of type 'wf.garnier.spring.boot.test.ch3.configuration.Gizmo' that could not be found.
----

We want to write a test that covers the scope of our `ThingConfiguration`, but our `GreenThing` depends on the `YellowGizmo` and `BlueWidget`.
We are not interested in the behavior of these classes, but we need to have them in the test application's context before it can start.
The easiest way to get around this issue is to provide a _stub_ implementation, that is, an implementation that provides a pre-programmed response.

In Spring Boot Tests, the most common way to inject a dummy object into your app is to use the `@MockitoBean` annotation:

[#ch3-listing-mockitobean, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Providing beans with `@MockitoBean`
[source,java,indent=0]
----
include::../code/ch3/configuration/src/test/java/wf/garnier/spring/boot/test/ch3/configuration/CustomConfigTests.java[tags=mockito-beans;!ignored]
----
<1> Scope our test to ThingConfiguration
<2> Provide a stub Gizmo bean
<3> Provide a named stub Widget bean

In this example, the dependencies for our `GreenThing` bean are fulfilled, and the application starts, because we provided the missing beans, using two distinct Spring Boot Test APIs.
First, both beans are annotated `@MockitoBean`.
That means that the instances of those bean will not be real implementations, but instead will be a Mockito mock.
The `Gizmo` does not need a name, because our application assumes there's only one bean of this class.
However, if you refer back to the app diagram in figure <<ch3-figure-01>>, you'll notice that are multiple `Widget` beans.
Since we rely on bean names for auto-wiring, we provide a name in the annotation itself to differentiate it from the `blackWidget`.
Both beans being Mockito mock objects, by default, they have no behavior and provide default values to every method call, most often just a `null`.
In our case, we do not use the methods of the object, so default values are absolutely fine.
These objects that you do not use in your tests are often referred to as a _dummy_ object.
This is perfect when you only need it to satisfy a dependency without needing to actually use it in your tests.
If your test actually needs to use code from that bean, and expects those beans to return specific values, you can always program the mock and set up your own "canned" response - this is called a _stub_.
Although we don't use it here, we have already seen an example of stubs in the previous chapter, in listing <<ch02_garniermoiroux_spring_boot_testing.adoc#ch2-listing-mocks, 2.8>>.
Since these are Mockito `Mock` instance, you can technically also run behavior verifications, asking questions such as "was this method called, with value 42?", but I'd argue that this is misguided in this case: we're testing a subset of our application, and only providing a few configuration patches here and there to make it start, not testing deep integration.
If you want to test full-blown features, you'll probably want to run a regular `@SpringBootTest` instead.

NOTE: If you work with Spring Boot version prior to 3.4, you might encounter `@MockBean` annotations.
It achieves the same result as `@MockitoBean`: it is an earlier implementation that used to be a Spring Boot-only feature.
In 3.4, these features were implemented in Spring Framework itself, renamed, and the Boot `@MockBean` was deprecated.

There is another way to provide a bean in tests that does not rely on the Mockito library: you can use a `@TestBean` annotation.

.Providing beans with @TestBean

This is not a Mockito mock, but instead any instance that you construct yourself.
The only thing you need to do is create a static _factory method_, which is used to create the instance of that bean.
By default, Spring looks up a static method with a name matching that of the field in the class.
This is a case for the `Gizmo` bean: both the field in the test class and the factory method are named `gizmo`.
In that method, you can add any code you'd like to create your test bean.
If you need to use the same factory method for multiple beans, or if you would simply like to give it a descriptive name, you can use the `methodName` parameter of the annotation.
This is what we're doing with the `blueWidget` using the `makeBlueWidget` method.
You can even refer to static methods from external classes, using a fully-qualified name like `org.example.TestUtils#makeBlueWidget`.
While this is a little bit more verbose than using Mockito beans, it allows you to provide any code without having to use any of the Mockito apis "when this then return that".
And, since you control the creation of the object, you do not need to instantiate all the dependencies that it would need in production.
You could instead pass null values in the constructor if your object supports it, or create a subclass that does not rely on dependencies.

TIP: If you're using Spring Boot Tests, you will likely be using `@MockitoBean`.
On the other hand, if you're working on a Spring-based library, not an app, Spring Boot may not be available as a dependency.
In that case, `@TestBean` is a good option if you don't want to bring Mockito as a dependency.

In both examples in above, we have created beans that were _missing_ in the context of our test application.
But with these annotations, it is also possible to replace beans entirely.
We saw an example of this in the previous chapter, in section <<ch02_garniermoiroux_spring_boot_testing.adoc#ch2-section-6, 2.6>> when we replaced the "Weather Service" by a stub implementation.
To replace beans where there is only one instance of the given type, such as the `Gizmo` in our example, you need to register a `@MockitoBean` or `@TestBean` of the same type as your replacement target.
When there are multiple beans in your app, to tell Spring Boot Test which exact bean to replace, you can specify the name of the target in the annotation, as we've done with our `@MockitoBean(name = "blueWidget")` above.

Mockito-based beans also support a "spy" mode, by using the `@MockitoSpyBean` annotation.
It does exactly what it says on the tin: it creates a Mockito "spy", essentially a wrapper around the real bean, which allows you to check how it was called and used.
Why aren't we demonstrating this feature here?
It's generally accepted that spies should rarely be used, as Mockito warns... _in their very own reference documentation_!

[QUOTE,Mockito reference documentation]
____
Real spies should be used **carefully and occasionally**, for example when dealing with legacy code.

Source: https://javadoc.io/doc/org.mockito/mockito-core/latest/org.mockito/org/mockito/Mockito.html#13[]
____

Spies do have their place, otherwise Mockito and Spring Boot Tests would not support it.
But, as a rule of thumb, you probably do not need to use this.
If you do, it is likely a sign that you have a design problem somewhere, either in your tests or in your production code.

NOTE: To learn more about Mockito, please refer to chapter 10, "Writing elegant tests with Spring Boot’s bundled testing libraries".

And with that, you now know most of the configuration hooks for creating a test app.
Powerful as they are, all these tools and abstractions do come at a cost, which might unacceptably slow down your test suites.
To help you navigate the tradeoffs, let's take a look at how they impact your test suite.

[#ch3-section-5, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== Speeding up tests by reusing the ApplicationContext between tests

When you have multiple test files, and they all have different configurations, they produce different test apps, or, more precisely, different Spring `ApplicationContext`, each with specific properties and profiles, or even different beans.
As a result, each of these test apps need to be started separately before the test in which they are used.
But starting a Spring application may take anywhere between 100ms for very small projects to tens of seconds for much larger use-cases, and the memory and CPU usage spikes on startup.
Imagine you have 20 test files and starting the application takes 10 seconds, that would mean more than three minutes spent waiting for test apps to come up.
For your test suites to be fast, you need to minimize the number of test apps starting.
Fortunately, the Spring TestContext framework is here to help you by caching the `ApplicationContext` between tests.

=== Using the Spring ContextCache

Consider the small, toy Spring application:

But if we write a second test class with the exact same configuration, the test will run instantly.

<1> Tell JUnit the order in which tests should run

This test file contains two nested `@SpringBootTest`, so you would expect the tests to take approximately 2 * 3 = 6 seconds to run.
When you run this test file, and measure the runtime, it will be around 3 seconds, plus a few hundred milliseconds to start up the JVM, but not 6 seconds.
If you observe the logs, you will see that the "Spring Boot" banner and our log "==> Configuring slow bean..." only show up once.
This is because of the caching provided by the Spring TestContext Framework: the test app is started when the `SlowTests` start, and then it is reused for the `FastTests`.

NOTE: We've hardcoded the order in which our tests run.
It is not generally a good practice, but here it helps us reason about when the test app starts and when it is reused.

The way this works is through a cache of the Spring `ApplicationContext`.
Whenever a test class needs to interact with a test application, the Spring TestContext framework first looks up if such an app exists in its cache.
If that's not the case, then a test app is started, and a reference to that app is stored in the cache.
If there is a cache entry, then the existing app, which is already configured and running, is used.
The cache key is, broadly speaking, the "configuration" of the test application: properties, profiles, and "configuration classes" or "beans" loaded in the application.
In our case, both test classes have the exact same configuration, so they can use the same test application.
You can observe the cache behavior by turning logging on, by adding the appropriate properties to your test `application.properties` file:

[#ch3-listing-cache-logs, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Turning on logging for the Spring TestContext Framework
[source,properties]
----
logging.level.org.springframework.test=DEBUG
----

Your tests will now print out many, many log lines, essentially displaying:

----
[...] Spring test ApplicationContext cache statistics: [DefaultContextCache
[CA]@57c47a9e size = 1, maxSize = 32, parentContextCount = 0, hitCount = 0, 
[CA]missCount = 1, failureCount = 0]
[...] Spring test ApplicationContext cache statistics: [DefaultContextCache
[CA]@57c47a9e size = 1, maxSize = 32, parentContextCount = 0, hitCount = 1, 
[CA]missCount = 1, failureCount = 0]
[... other logs ...]
----

The first log line represents the first time the Spring tests need to access an `ApplicationContext`.
First things first, you can see that the size of the cache is 1, and that's perfectly normal: Spring Boot tests is wiring up an app for you, and putting it in the cache.
That's also why the `missCount` is 1, since the cache was initially empty, with no test app started.
Reading the logs, you'll also learn that, by default there are a maximum of 32 "test apps" slots available in the cache.
Each of these cache entries will contain a reference to a live, running application.
32 apps is A LOT.
In general, you do not want to get anywhere near that number of apps, especially if they represent a full-scale version of your Spring Boot app, with the majority of its dependencies.
Why?
First, because wiring up an application context takes a long time, and this will noticeably slow down your tests.
If you start evicting from the cache some test apps that took tens of seconds to start, and restart them multiple times, your test suite will take an unbearably long time to run.
Second, these apps consume CPU and memory, especially if you're relying on external resources, such as Testcontainers.
This might be manageable on a beefy developer machine or a big CI server, but if your tests are running on tiny cloud instances, you won't even be able to run your full test suite before running out of memory.
So you want to keep the `size` and `missCount` as low as possible.

On the other hand, the `hitCount` can increase very rapidly without a hitch.
If you try this for yourself, you'll even notice that `hitCount` increases much faster than your number of tests.
That happens because the Spring Test Context framework needs to read from the cache very often, for example to populate the `@Autowired` fields you have in your tests.
If you want further information on what the cached configuration actually is, you can increase the log level to `TRACE`, and get a description of how a test app is "indexed" in the cache.

Caching massively speeds up your tests, and, to benefit from it, you should avoid creating many variations of your test app.
It is better to start the full test app once, and reuse it to verify separate aspects of your business logic rather than starting many variations across tests.
But how do you keep the number of test apps low?

=== Avoiding creating too many test apps

Reading from the `ApplicationContext` does not modify the configuration, so using `@Autowired` or `@Value` in your tests to access beans does not trigger the creation of new test apps.
But most other changes you might do to a test file will change the configuration of the app under test, and will result in an increased test app count.
Here is a non-comprehensive list of annotations and parameters that you should avoid changing, when possible:

- Changing properties, through `@SpringBootApplication(properties = ...)` and `@TestPropertySource(...)`
- Applying inconsistent styling to your custom properties, such using `key=value` in one place and `key = value` in another.
- Adding a profile with `@ActiveProfile(...)`
- Selecting configuration classes manually, through `@SpringBootApplication(classes = ...)`
- Adding configuration classes with `@TestConfiguration`
- Adding auto-configuration classes, for example with `@AutoConfigureMockMvc`
- Overriding beans with `@MockitoBean`, `@MockitoSpyBean` and `@TestBean`
- Forcing a cache eviction through `@DirtiesContext`
- Any Spring TestContext Framework customization, not detailed here, that you may want to try out (context initializers, context loaders, adding a parent context, ...)

TIP: The complete explanation of how the caching key is computed is detailed in the reference documentation: https://docs.spring.io/spring-framework/reference/testing/testcontext-framework/ctx-management/caching.html . If you find yourself trying to optimize test execution speed, take a peek.

Again, the issue is about having _different_ configurations resulting in separate test apps.
If all your testing scenarios require the same configuration change, say, changing a few properties and using `@MockitoBean` on some beans, you are totally free to do so, as long as you apply the same customizations to all test apps.
In fact, you can create your own custom meta-annotation, reusable across all your tests, for example:

NOTE: The rule of thumb is to try and keep the app number to a minimum, ideally a single test app.
And for every rule, there are exceptions!
There might be cases when you want to test two or three separate configurations, and verify their specific behavior.
In that case, there is no way around starting multiple test apps, and the startup and memory costs are worth taking on.

If you follow these basic principles, your test suite should remain lean and fast.
But there's no such thing as a free lunch, and there are limitations to this caching.

=== Tradeoffs, side effects and limitations

The most important side effect is a direct consequence of re-using the same app between tests.
Since all the classes remain up and running in-memory between tests and hold references to external systems like databases, message brokers, filesystem, etc, any change in one of your test will be visible to the next test.
This can lead to so-called "test pollution", where tests are not isolated anymore.
For example, if you have a database running in a Docker container and test 1 inserts data, then that data will be in the database when test 2 runs.
Or if a test deletes some in-memory data, that data will not be available for the rest of the test suite.
To work around this, there are two possibilities: you can either write tests that only depend on state that is initialized locally, for example in the test method itself, or ensure that the global state is reset before, or after, every test.
This usually involves writing custom logic, like we did in the previous chapter, in section <<ch02_garniermoiroux_spring_boot_testing.adoc#ch2-section-5, previous chapter>>, by deleting every entry in the repository before every test, essentially "resetting the universe" from the point of view of our test methods.
Some tests may delete data or "break" components in way that are hard to recover from, and, in that case, the easiest might be to reset the test app entirely.
You can achieve that by using the `@DirtiesContext` annotation, either on a test class or on a test method:

Refer to the https://docs.spring.io/spring-framework/reference/testing/annotations/integration-spring/annotation-dirtiescontext.html[reference documentation] if you would like to learn more.
But, above all, remember:
using this will slow down your test, as it will force the creation of a brand new test app, and it should be a last resort annotation that you avoid using as much as possible.

Another limitation of the cache is that it's a static cache, literally a Java `static` variable.
So there is one cache per process running.
If you run your tests in multiple processes, the cache is not shared across test processes, and you risk launching more apps than when you run your apps sequentially in a single process.
If you run tests in parallel within the same process, the cache is shared.
As the reference documentation puts it, "can result in unexpected side effects, strange runtime behavior, and tests that fail intermittently or seemingly randomly."

== Summary

- Testing Spring Boot apps goes beyond `@SpringBootTest` and `@Autowired`, and is built on a powerful foundation: the Spring TestContext Framework
- You can read from the test app's `ApplicationContext` with `@Autowired`, `@Qualifier` and `@Value`.
- There is a host of options and hooks for configuring the test application, the most useful being the parameters in `@SpringBooTest(properties = { ... })` and the `@TestConfiguration` annotation.
- It is possible to test only a subset of the application with `@SpringBootTest(classes = { ... })`, but it is useful only for a select number of use-cases.
- When you want to stub out external services, or when you want to add missing beans to your tests, use `@MockitoBean` or `@TestBean`.
- Most importantly: use all these tools with parsimony and care.
Avoid creating many variations of your app's configuration in your tests, or you will wind up with slow, resource-intensive tests.
