= Configuring and running an application for testing

This chapter covers:

* How the `@SpringBootTest` annotation works
* Configuring the application under test
* Accessing beans and properties in your tests
* Stubbing and mocking dependencies
* Caching the application context between tests

When you annotate a test class with `@SpringBootTest`, it automatically detects your application's configuration, configures and optimizes it for a testing scenario, manages its lifecycle, and makes it accessible in your tests.

You might need to update the configuration, for example to stub out an external service that you do not want to touch in your test, as we've seen in xref:ch02_garniermoiroux_spring_boot_testing.adoc#ch2-section-6[Chapter 2].
You may have several configurations possible for your software, for example with region-specific behavior controlled by properties or profiles, and want to run separate test suites for each.
Or maybe you would like to split your integration tests by logical "module", and you want to run only a subset of your application for each given module.

We'll explore all the different ways you can configure the test application, from changing a few properties to manually selecting which components are loaded in your test application.
And you will learn the tradeoffs associated with customizing the application under test.

== The `@SpringBootTest` annotation in detail

In the xref:ch02_garniermoiroux_spring_boot_testing.adoc#ch2_title[previous chapter], we've annotated our test class with `@SpringBootTest`, and you'll encounter it throughout this entire book.
While useful and easy to get started with, it is sometimes described as "auto-magic".
It does so many things automatically, in the background, most of which you don't understand or even realize are happening, that it feels like magic.
While the implementation details are deep and intricate, at a high level, it is not particularly scary.
It does roughly four different things:

1. It tells JUnit that a Spring application is required for the tests, and that it should trigger Spring-specific behavior
2. It creates a Spring application context from your Spring Boot configuration, suitable for testing scenarios
3. It runs this application context, and shuts it down when the tests are finished
4. It allows you to interact with the application in your tests, through annotations such as `@Autowired`, `@MockBean`, etc.

It also provides a few configuration options so you can tweak the default test application.
For example, you can disable the web capabilities by using `@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.NONE)`.
To understand how it achieves all those things, you can peek under the cover and look at the code of the annotation.
I've simplified it for you in listing <<ch3-listing-springboottest>>.
You'll see it's actually a meta-annotation, that brings in other annotations.

But Spring has testing capabilities for apps too, without Boot, and Boot builds upon it.

By using `@SpringBootTest`, you automatically register the JUnit `SpringExtension` with your test class, through the `@ExtendWith` annotation.
It is the glue that ties your tests to the Spring parts in your application.
It is responsible for managing the lifecycle of the test application in sync with the lifecycle of the test.
JUnit have hooks that allow you to execute code at different points in the lifecycle, for example "before every test in the class", "after all the tests in the class have run", "after the test class' instance has been constructed".
The Spring extension takes advantage of this, and detects when it should start a test app.
It also modifies the test class at runtime, to inject values into fields, or parameters in test methods - this is what happens when you use `@Autowired` or `@MockBean` in a test.
Lastly, it detects the context in which the test is run, and uses that information to configure the test application.
One of the way it does this is by detecting annotations present on the test class.
For example, the `@ActiveProfile` annotation which adds a Spring profile to the test app, or the `@TestPropertySource` which sets properties.

NOTE: All the Spring Framework utilities for testing are grouped under the "Spring TextContext Framework" within Spring.
It has a rich feature set, that goes way beyond Spring Boot apps.
Although it is fairly advanced material, I encourage you to take the time to at least skim the reference documentation, available at https://docs.spring.io/spring-framework/reference/testing/testcontext-framework.html, with a focus on the first few sections.

As is signaled in the name, `@SpringBootTest` is about testing Spring _Boot_ applications, not plain Spring apps.
Using the primitives in the Spring TestContext framework, it tailors the experience to Spring Boot, starting with the `SpringBootTestContextBootstrapper`.
That class is responsible for detecting your "production" application and its configuration, and using that to create the Spring `ApplicationContext` for the test applications.
It also applies test-specific configuration, like not running a full web-server unless specifically required.

It also provides direct configuration hooks in the annotation itself, so you can add configuration properties, use the main method or not, or turn off web support.

// - Configuring a version of your application suitable for testing, with appropriate properties, profiles or even configuration classes.
// - Replacing beans selectively, for example to avoid connecting to external systems.
// - Managing the lifecycle of the application in your tests, by starting and stopping it at appropriate times.
// - Interacting with the running application using low level APIs, for example to access certain beans in the application context, or to get the port of the running server.
// - Optionally, writing utility classes to make tests less verbose.
