= Configuring and running an application for testing

This chapter covers:

* How the `@SpringBootTest` annotation works
* Configuring the application under test
* Accessing beans and properties in your tests
* Stubbing and mocking dependencies
* Caching the application context between tests

When you annotate a test class with `@SpringBootTest`, it automatically detects your application's configuration, configures and optimizes it for a testing scenario, manages its lifecycle, and makes it accessible in your tests.

You might need to update the configuration, for example to stub out an external service that you do not want to touch in your test, as we've seen in xref:ch02_garniermoiroux_spring_boot_testing.adoc#ch2-section-6[Chapter 2].
You may have several configurations possible for your software, for example with region-specific behavior controlled by properties or profiles, and want to run separate test suites for each.
Or maybe you would like to split your integration tests by logical "module", and you want to run only a subset of your application for each given module.

We'll explore all the different ways you can configure the test application, from changing a few properties to manually selecting which components are loaded in your test application.
And you will learn the tradeoffs associated with customizing the application under test.

[#ch3-section-1, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== The `@SpringBootTest` annotation in detail

In the xref:ch02_garniermoiroux_spring_boot_testing.adoc#ch2_title[previous chapter], we've annotated our test class with `@SpringBootTest`, and you'll encounter it throughout this entire book.
While useful and easy to get started with, it is sometimes described as "auto-magic".
It does so many things automatically, in the background, most of which you don't understand or even realize are happening, that it feels like magic.
While the implementation details are deep and intricate, at a high level, it is not particularly scary.
It does roughly four different things:

1. It tells JUnit that a Spring application is required for the tests, and that it should trigger Spring-specific behavior
2. It creates a Spring application context from your Spring Boot configuration, suitable for testing scenarios
3. It runs this application context, and shuts it down when the tests are finished
4. It allows you to interact with the application in your tests, through annotations such as `@Autowired`, `@MockBean`, etc.

It also provides a few configuration options so you can tweak the default test application.
For example, you can disable the web capabilities by using `@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.NONE)`.
To understand how it achieves all those things, you can peek under the cover and look at the code of the annotation.
I've simplified it for you in listing <<ch3-listing-springboottest>>.

[#ch3-listing-springboottest, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Simplified code for @SpringBootTest extension.
[source,java]
----
@ExtendWith(SpringExtension.class) // <1>
@BootstrapWith(SpringBootTestContextBootstrapper.class) // <2>
public @interface SpringBootTest {

  // Below are generic Spring configuration options, exposed by @SpringBootTest
  String[] properties() default {}; // <3>

  Class<?>[] classes() default {}; // <3>

  // Below are Spring Boot specific configuration options
  WebEnvironment webEnvironment() default WebEnvironment.MOCK; // <3>

  UseMainMethod useMainMethod() default UseMainMethod.NEVER; // <3>

  String[] args() default {}; // <3>

}
----

<1> A Spring-provided JUnit extension
<2> Configuration for the SpringExtension
<3> Configuration for @SpringBootTest

As you see, it's a meta-annotation: it brings in other annotations.
The first interesting bit is `@ExtendWith(...)`, which registers a JUnit extension.
It allows you to add custom code to run on the lifecycle of a test, for example "after each test" or "when the test class is created".
In this case, it registers the `SpringExtension`.
This is the important class, the glue between your tests and your Spring application.
It does most of the heavy lifting for Spring Boot Tests.
It is the entrypoint into the Spring "TestContext" framework, which is responsible for putting together a test app, running it before a test is executed and shutting it down after, and making it available to the test class through `@Autowired` annotations.
The second annotation, `@BootstrapWith(...)`, is a TestContext annotation, which specifies how to create a Spring app from your own configuration.
In this case, it uses Spring Boot specific setup, which detects your `@SpringBootApplication` on your main class, and marginally adjusts the configuration to make it a "test app".
For example, it does not run an embedded web server by default.
The last notable elements are the annotation parameters.
Those are detected by the `SpringBootTestContextBootstrapper`, which uses the values to further modify the configuration of the test app before running it.
For example, you can instruct Spring Boot Tests to _not_ start a web server, or to use the main method of the app.

NOTE: All the Spring Framework utilities for testing are grouped under the "Spring TextContext Framework" within Spring Framework.
It has a large feature set, that goes way beyond Spring Boot apps.
Although it is fairly advanced material, I encourage you to take the time to at least skim the reference documentation, available at https://docs.spring.io/spring-framework/reference/testing/testcontext-framework.html, with a focus on the first few sections.

With that, the `@SpringBootTest` annotation is the one-stop shop for configuring, managing and accessing an app for your integration tests.
Let's start by configuring the application.

[#ch3-section-2-activating-a-profile, reftext={chapter}.{section}.{counter:subsection}, caption='{chapter}.{section}.{subsection}']
=== Activating a profile

Spring supports adding the `@Profile` annotation on bean definitions to express that some beans are to be loaded when a given profile is active.
A profile is activated using a system property, for example `spring.profiles.active="prod,france"` turns on profiles "prod" and "france".
Additionally, Spring Boot will pick properties files with the profile name, such as `application-prod.properties` or `application-france.yml`.
If you would like to override many properties in your tests, you can group them in a test-specific properties file, and give it a profile name, such as "test".
Be sure to add it to `src/test/resources`, so that it is never picked up by your production code.
Then add the profile in your tests, as shown in listing <<ch3-listing-profile>>.

=== Adding configuration with `@Configuration` and `@TestConfiguration`

If you would like to add test-specific beans, there are two possibilities.
First, you can create a `@Configuration` class in your test directory.
If it is located in the same package as your Spring Boot main class, or any sub-package, they will be added to the configuration of the test application.
Let's examine a concrete example, with the file structure represented in listing <<ch3-listing-file-structure>>.

[#ch3-listing-file-structure, reftext={chapter}.{counter:listing}, caption='{listing-caption}.{counter:listing-number} ']
.Project file structure for custom configurations
----
src
├─ main
│  └─ java
│     └─ com
│        └─ example
│           ├─ DemoApplication.java <1>
│           ├─ ProductionConfiguration.java
│           └─ ... more production code ...
└─ test
   └─ java
      └─ com
         └─ example
         │  ├─ MainTestConfiguration.java <2>
         │  ├─ nested
         │  │ └─ NestedTestConfiguration.java <2>
         │  └─ ... your tests ...
         └─ notincluded
            └─ ExcludedConfiguration.java <3>
----

<1> The main class
<2> These configuration files will be included
<3> This will not be included in the test app

In this setup, the app's main class, `DemoApplication`, is in the package `com.example`.
Since it is a `@SpringBootApplication`, component scanning is active: Spring Boot will find every `@Configuration`, `@Component`, `@Repository`, ..., included in `com.example` and its sub-packages.
When the tests are compiled, the classpath will contain `com.example.ProductionConfiguration` from the production code, but also `com.example.MainTestConfiguration`, `com.example.nested.NestedTestConfiguration`, `com.notincluded.ExcludedConfiguration`, as well as your test classes.
In that case, both `MaintTestConfiguration` and `NestedTestConfiguration` are under `com.example.*`, and will be considered part of the "test app's" configuration.
But there's one big caveat with this approach: every single `@SpringBootTest` will pick up this config class.
It is useful, but there are cases you want to modify the config for a subset of tests.
While you could hack your way around with different packages or custom exclude rules for component scanning, Spring Boot Test has just the right tool for you: `@TestConfiguration`.
It works like a regular Spring configuration, but you have to enable it explicitly.
The first possibility is to nest the class inside your test, like in listing <<ch3-listing-nested-testconfiguration>>.

So far, we've seen how to make a test application and add custom, test-specific bean to the default "production" configuration.
But for a big application, your typical multi-module monolith, starting the full app might be "expensive" and take a long time. `@SpringBootTest` has a dedicated parameter for that very specific use-case: `classes=`.

[#ch3-section-2-configuring-from-scratch, reftext={chapter}.{section}.{counter:subsection}, caption='{chapter}.{section}.{subsection}']
=== Configuring the application from scratch

We have mentioned in xref:ch02_garniermoiroux_spring_boot_testing.adoc#ch2-section-7[chapter 2] that, when you just want to test a few classes, you may not need `@SpringBootTest`.
Specifically, if you want to test a `FooService` that has a dependency on a `BarService` and a `FooRepository`, you do not need Spring to do the auto-wiring for you.
In some cases, though, you do need a bit of Spring machinery.
Maybe you want to have Spring parse `properties` files for you, perform data validation, or activate `@Conditional` annotations on your beans, without booting the full production app.
In that case, you can configure a much smaller application context while retaining the bulk of Spring Boot features, as shown in listing <<ch3-listing-classes>>.

[source,java,indent=0]
----

----

<1> List the classes you want to include

By using `classes = { ThingConfiguration.class }`, we ensure that only the beans in `ThingConfiguration` will be loaded, and nothing from your custom code.
The classes can be either `@Configuration` classes containing beans, or direct beans themselves, annotated with `@Component`, `@Service`, `@Repository`, etc.
Since Spring Boot auto-configurations are loaded from your main application class annotated with `@SpringBootApplication`, they are not included here, and will not be loaded either.
Please note that if your `ThingConfiguration` has annotations which triggers other classes being present, such as `@Import`, `@ComponentScan`, `@EnableConfigurationProperties`, etc, those annotations will be triggered.
In that case, your test app may contain many more beans than you expected.
To avoid those issues, you must structure your code in a way that is composable, and avoid using a single giant configuration class that pulls the entire universe in your application.

Of course, if you want this test application to start, all the beans in `ThingConfiguration` must have access to their full dependency graph.
