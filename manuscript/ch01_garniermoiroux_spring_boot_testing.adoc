= Spring Boot-specific test tooling

This chapter covers

* What's included in the "test" Spring Boot Starter
* How Spring and Boot help you write tests
* When to use Spring-specific testing tools

Testing applications and verifying that they have the intended behavior is an unavoidable aspect of the development lifecycle.
In any serious software engineering project, automating at least some of these tests is table stakes.
If you picked up this book, chances are you have already implemented extensive testing yourself, and you do not need to be convinced that you should write tests.

Because it is such a foundational requirement in modern software engineering, many projects in the Spring portfolio cover testing.
This includes both Spring Framework and Spring Boot.
Spring Framework's programming model is _declarative_: you describe your app's configuration through annotations on classes and methods, such as `@Component class MyService`.
You don't have to stitch components together _imperatively_ with calls such as `new MyService()`.
Spring brings this paradigm to your test code, with familiar concepts you use in your apps, such as `@Autowired`, and dedicated test annotations such as `@TestConfiguration`.

Spring Boot simplifies Spring development by following a "convention over configuration" philosophy.
For example, when Spring Boot detects that your project depends on `spring-boot-starter-webmvc`, it starts your app in a web server on port 8080.
Similarly, it automatically creates testing utilities, such as `MockMvcTester`, and connects them to your application, without requiring complex, dedicated configuration.
Spring Boot also curates a list of test-focused dependencies, providing most of the tools you need to write tests, and ensures that the versions of these libraries work well together and integrate cleanly with Spring code.

Like everything in the Spring ecosystem, these tools are powerful and versatile, but come with tradeoffs.
Knowing when to use them and, just as importantly, when _not_ to use them can have important implications, for example, on the speed of your test suite.

First and foremost, this book offers a hands-on approach to learning how to write tests for your Spring Boot applications, beyond just using the `@SpringBootTest` annotation you'll see in every "Getting started" guide.
The second goal is to give you a solid understanding of how Spring Boot Tests works, occasionally peeking under the covers to reveal what the abstractions really do.
With these insights, you will be able to create robust test suites and avoid the all-too-common pitfalls and performance killers.
Lastly, you will get an overview of most of the testing libraries that Spring Boot packages.
The idea is to learn when to use these tools, discover new components you may never have used before, and gain enough context to continue learning on your own.

In this chapter, we will discuss the tools that Spring and Spring Boot offer to simplify testing, in practice.
You will discover with which types of tests these tools shine, and how they outperform manually crafting complex test cases.

== What's "Spring Boot Tests"?

_Spring Boot Tests_ contains Spring code specifically designed for writing tests, and bundles dedicated testing libraries that work well together.
With this, you have standard, powerful building blocks at your disposal to write the vast majority of tests you will need.

Before we take a look at these testing tools, I need to clarify that there is no such thing as an official _Spring Boot Tests_ project.
However, the Spring Boot project has "starter" dependencies specifically used for testing:

- `spring-boot-starter-test`, which contains the basics for testing Boot applications, without any web capabilities
- `spring-boot-starter-webmvc-test` and `spring-boot-starter-webflux-test`, which contain `spring-boot-starter-test`, plus a few specific classes for testing web applications, based on either MVC or WebFlux
- A dedicated starters for many elements of the Spring portfolio: RestClient, Security, Data, Batch, etc.

When you create a new project using the Spring Initializr, better known as https://start.spring.io, no matter which projects you select from the dropdown list, you get the appropriate test starter as a dependency and an example test that uses the `@SpringBootTest` annotation.
The Spring Boot Starter Test project is the testing version of the Spring Boot "batteries included" approach: it contains a curated list of dependencies that will make writing tests easier, with dedicated tooling.

The majority of Boot applications use Spring MVC, which is what you get when you select "Spring Web" on https://start.spring.io. It is the default stack for building web apps, based on a Java Servlet container like Tomcat.
This is opposed to the alternative stack, WebFlux, based on Netty and built around the "reactive" programming model.
In MVC apps, the build file will have the Spring Boot `webmvc-test` starter.
It is configured with the `test` scope of your project, as shown in listing <<ch1-listing-pom-xml>>.
This means the testing-specific dependencies it brings cannot be used by your main application code, sometimes referred to as "production" code.

The libraries you get from the starter are broadly divided into two categories.

First, every dependency in the `org.springframework` and `org.springframework.boot` groups is Spring-specific tooling, created and maintained by the Spring team, with contributions from the Spring community.
It contains code specifically designed to simplify testing Spring and Spring Boot applications.
This is where you will find, for example:

- The `SpringExtension`, a JUnit extension.
JUnit runs your tests, and with this "plugin", Spring extends the default JUnit behavior to drive Spring apps in tests.
It simplifies the lifecycle management of Spring applications by starting and stopping the Spring `ApplicationContext`, and allows you to easily configure and access Spring beans within your tests.
- The well-known `@SpringBootTest` annotation, which automatically detects your Spring Boot application's configuration classes and makes your code ready for testing.

These testing classes are the connective tissue between your application code and your test code, and they make your *Spring* code easier to test.
You typically use them _declaratively_, with annotations: you describe _what_ you want.
For example, by putting `@SpringBootTest` on your test classes, Spring handles the lifecycle of the application under test for you.
No need to write _imperative_ code, a list of instructions describing _how_ to execute code, such as "first `new SpringApplicationBuilder(...)`, then  `SpringBootTest.run(...)`, then ...".
This results in much more concise code, with less boilerplate, that focuses on your test logic.

The second category of dependencies contains testing utilities that are not specific to Spring.
Just like in your production code, Spring Boot provides a list of curated dependencies that are useful in the most common scenarios.
It manages dependency versions to ensure that all these libraries work well together, and that they integrate without a hitch with your Spring code.
Here is a non-exhaustive list of the "goodies" you'll find in the toolkit:

- JUnit, the testing framework, with `org.junit.jupiter:junit-jupiter`.
This is where you will find your `@Test` annotation.
JUnit is the most popular testing framework in Java, no other framework even comes close.
In Spring Boot 4, you get the most recent JUnit major, which is version 6.
For advanced JUnit usage, please refer to chapter 8, "Creating reusable test abstractions with JUnit".
- Two assertion libraries: Hamcrest (`org.hamcrest:hamcrest`) and AssertJ (`org.assertj:assertj-core`).
With these, you can write assertions that explain what your test expects to be true.
For example, after "When I add one widget," you want to express "I expect the widget count to be 5."
With AssertJ, you would write in code: `assertThat(widgetCount).isEqualTo(5)`.
When assertions are not fulfilled, the assertion framework throws a nice, human-readable exception.
Hamcrest is the "historical" library, and AssertJ has a more "modern" take on assertions.
In this book, all of our assertions will be written with AssertJ.
To learn more, refer to chapter 10, "Writing elegant tests with Spring Boot’s bundled testing libraries."
- A "mocking" library, Mockito (`org.mockito:mockito-core`).
Mocking allows you to easily create "fake" objects that have the same API as your classes, and customize their behavior.
This is useful for replacing classes with complex business logic.
For example, you might want to disconnect your tests from external dependencies such as databases or remote services and APIs, or treat some subset of your object graph as a black box that returns pre-determined results.
You can add behavior ("when the user calls `widgetService.count()`, return 5") as well as verifications ("verify that the `emailService.sendEmail()` method was called once, with email user@example.com").
To learn more, refer to chapter 10, "Writing elegant tests with Spring Boot’s bundled testing libraries".
- And a few other utilities, such as XMLUnit for checking properties on XML, JSONassert for checking properties on JSON, Awaitility for waiting on asynchronous conditions.
To learn more, please refer to chapter 10, "Writing elegant tests with Spring Boot’s bundled testing libraries".

These utilities are not related to Spring, and can be used in all your tests, including in your "business logic" tests that do not involve Spring.
You use them imperatively, for example by calling `Awaitility.await().until(() -> { /* ... */ });` or `assertThat(someResult).isEqualTo(42);`.

== When to use Spring Boot Test

For any given application, whether it was developed using Spring Boot or any other technology, there are many types of tests you can write.
They can be very low-level, centered on tiny pieces of business logic and focused on a few classes or methods: those are unit tests.
They are deterministic, specific, and extremely fast to run, but they have a narrow focus and do not give confidence that the system functions as a whole.
At the other end of the spectrum, you can deploy your application to a dedicated test or staging environment, with all its many dependencies, and execute a dedicated testing program against the running app.
Those are sometimes called end-to-end tests.
They ensure that the system works as expected at the highest level, from the user's perspective, but they are slower, more difficult to set up, and more fragile.
There is a whole continuum of test types in between.

Spring Boot tests shine somewhere in the middle, in what I'd call _integration tests_.
The term is not universally accepted, so it's worth defining it in the context of this book.
Integration tests ensure that multiple units of code, usually developed independently, work well together.
In this book, we consider integration tests to not only test the code you developed but also verify that it integrates correctly with Spring.
Such tests typically involve many of the classes you've developed and must include some Spring capabilities, such as the web layer or the data layer.
It may cover your entire application and include external dependencies such as a database, but it typically does not cover the entire system with all its external dependencies.
Figure <<ch1-figure-02>> shows where Spring Boot tests are most useful.

[#ch1-figure-02, reftext={chapter}.{counter:figure}, caption='{figure-caption}.{counter:figure-number} ']
.The testing spectrum. On one end, unit tests that involve one or a few classes, and no Spring-specific code. On the other end, there are full-blown end-to-end tests, that may involve many complex components, that need tooling beyond the context of Spring. In between those two ends, there is a whole category of "integration tests".
image::ch01_f02_garniermoiroux.png[]

Think of it in terms of testing a car.
Unit tests ensure that the cylinders run smoothly in the engine block, or that the fuel pump delivers the appropriate flow of gasoline.
They give confidence that a single, independently developed unit functions according to spec and help you catch problems early.
An integration test verifies that the engine can actually run.
This requires assembling the engine block, the ignition system, the fuel pump, the exhaust, and so on, and checking that the crankshaft rotates at the expected speed.
As the name implies, it gives confidence that our units can be _integrated_ and that they work well together.
In this analogy, it could catch "bugs" like the pump not delivering fuel fast enough for the engine to accelerate.
Notice that this test does not include all the components of the car, only a subset.
An end-to-end test is a test drive once the vehicle is fully assembled, with a user at the wheel.
It's an essential test, which gives you the most confidence that the car can do what it was designed for.
But it's an expensive test: you need to assemble a full car to verify this!
You don't want to realize that the fuel pump doesn't even start at this stage; that's why we run unit and integration tests in earlier phases.
In the world of computer programs and Spring applications, Spring Boot Tests straddles the line between unit tests and end-to-end tests, getting the best of both worlds:

- They are reasonably fast to run, in the order of magnitude of a few seconds.
This is much slower than unit tests, but does not disrupt your development flow: you can get fast feedback whenever you make a change, without switching context.
- They focus on broad use-cases, beyond simply testing a method.
They ensure that components in your system collaborate correctly, and give confidence that the application works as a whole, more than unit tests would.
- They exercise all of your code, including Spring annotations and configuration.
They ensure that you have correctly programmed behavior, beyond the imperative statements within your methods.
For example, they validate application properties that Spring Boot uses for autoconfiguration of common libraries, that your `@ExceptionHandler` annotation covers the appropriate exceptions.
- They provide hooks into your production application code, to easily set up tests, and to run verifications.
For example, you can access the Spring JPA `@Repository` classes, and verify that some particular data is present after a given test.
- They do not try to interact with the application from a user's perspective.
This is the realm of end-to-end tests, which bring specific technology for simulating user behavior, and sometimes even specific, dedicated testing language to model scenarios.
- The tooling required to run them is limited in scope, and mostly independent of the architecture of your application or software system.
For example, you do not need to manage a full web browser and a webdriver.
Usually, having Java, and maybe a way to run Docker containers, is enough.
- They have no external dependencies, or very few.
You do not need to run and synchronize three separate microservices for your tests.
Instead, you provide "mocks" and "stubs" of your dependencies, with programmable behavior that simulates "real" dependencies.
As a result, they are reasonably easy to run in multiple environments: your local machine, your coworker's machine, the CI environment and so on.
- They can test for some complex error conditions.
Specifically, any error condition from a mocked dependency can be simulated: timeouts, protocol errors, invalid data, etc.
- They are usually fairly deterministic.
They have few moving pieces in the software under test, and few side effects.
For example, you do not have to deal with the asynchronous behavior and latency inherent to UI components, such as "wait until that element becomes visible".
A failure is a sign of an issue in your production code, not a network latency issue or a change in configuration in a third-party service.

With so many benefits, you could be tempted to use Spring Boot Tests everywhere.
They work great to ensure that your application works well together, and are best used to verify user flows, by expressing "when the user does this action, this is the expected result".
But, like everything in software engineering, there's no silver bullet for testing, and the approach comes with tradeoffs.
For example, Spring Boot tests are not well suited for testing narrow aspects of your application that have many conditional branches, resulting in a lot of possible outcomes.
The drawbacks fall in the following categories:

- They are slower to run than unit tests.
Incorrectly setting up the tests may lead to test suites that take minutes to run, if not hours.
- They cannot easily test all the conditions, branches and code paths of a given feature.
This is better done in unit tests, where you can control the inputs of every test with minimal friction, by wiring classes manually, and introducing stubs and mocks in your dependency graph.
- They cannot simulate all possible error conditions.
If you include a live, external web service in your tests, you cannot control or simulate its multiple failure modes.
- They are less specific than unit tests.
Since they typically exercise a lot of code, a failed integration test does not indicate precisely which part of the code is wrong.
You may need to spend some time debugging before figuring out what the underlying problem is.
- They are more prone to test pollution, where running tests in a different order results in different outcomes.
You may need to write some cleanup code to run between tests, or ensure the data in your test is unique.
- While they give some confidence in how your app behaves, they may have blind spots in system behavior as a whole.
If a dependency that you mocked out changes its API, such as an external service changing the structure of its responses, it will break your application but the error will go undetected.
- Because they test the full depth of the program, you need to set up a lot of state to exercise a specific behavior.
For example, "GIVEN The user has three Widgets in their basket, AND they have a membership card, AND they have bought at least five Doodads in the past six months, BUT they never had a GoldenSale discount, THEN they have access to a GoldenSale 10% discount".
This may result in a lot of setup before a given test.

Given where they lie in the testing spectrum, Spring Boot Tests have their own unique set of constraints.
Writing tests for the scenarios mentioned above comes with particular challenges, and Spring provides specific tooling to make it easier for you.

== Why is Spring-specific tooling required?

When developers write their first Spring Boot tests, they get a lot of value out of the box, by using the `@SpringBootTest` annotation.
It's so ingrained in our practices that we never stop to think about it, and the exact benefits you get from Spring Boot Tests is unclear.
To understand everything that you get for free, it might be worth exploring what a world without Spring Boot Tests would look like.
What would it take to create and run the integration tests mentioned in section <<ch1-section2>>.

The Spring Framework provides powerful abstractions for connecting different parts of an application.
With these abstractions and just a few lines of declarative code, you can resolve component dependencies, decide which flavor of a specific interface to use in a specific case, turn off some components, and more.
Through the Spring `ApplicationContext`, you can discover, access, and manipulate the _beans_, or component instances, used throughout the application.
With these abstractions, you could create your own "test application" that looks a lot like your production application, except for a few test-specific changes, such as mocking out an external service or the data layer.
Then you would programmatically run the app and interact with the created _beans_ in your tests.
But if you tried to do this manually with the Spring Framework, you would end up writing a lot of boilerplate code.
You would also face testing challenges when managing multiple configurations for different tests.

To make sense of the code you would need to write, let's examine a concrete example.
The application is fairly simple and is responsible for handling Widgets.
Users interact with it by making HTTP requests.
The API is exposed through a Spring REST Controller, `WidgetController`, and data is ultimately stored in a repository, `WidgetRepository`.
The `WidgetValidator` service represents an external service that's accessible over HTTP and is used to validate Widgets before they're stored.
It has complex logic and is difficult to run on a developer machine, so you'll want to avoid running it locally.
The class diagram in figure <<ch1-figure-03>> shows the dependency graph of these components.

The first challenge is configuring the "test application."
Spring Boot gives you automatic configuration through the `@SpringBootApplication` annotation on your main class.
For example, by scanning the classpath, it discovers classes with Spring annotations and adds them to the application context, as Spring beans.
It finds the `@Service WidgetValidator` that represents your external service and makes it available in the application.
But we said that, for our test case, we would like to remove it!
Ideally, we would replace it with a "fake" `WidgetValidator` that we can program to behave similarly to the real implementation without actually making network calls.
To avoid triggering this auto-discovery behavior, you can't simply rely on the `@SpringBootApplication` annotation.
Instead, you need to create a custom configuration class with your test-related configuration, along with the appropriate autoconfiguration that Spring Boot brings, while excluding configurations that aren't relevant.
Even for a simple use-case, where we replace a single bean, the amount of configuration required to make it work quickly gets out of control.
And writing it requires advanced knowledge of Spring Framework, without Spring Boot.
An example of what such configuration would look like is available in listing <<ch1-listing-testconfiguration>>.
The exact content of the configuration is not relevant, but it shows how much knowledge and effort would need to go into test-specific configuration, here with five distinct annotations.

Second, you have to manage the lifecycle of the "test application" manually.
You need to start the application before the tests and shut it down once the tests have completed.
While this is fairly straightforward, it means adding repetitive boilerplate code for setting up your test instance before running a test and then tearing it down once the tests have finished.
But it also raises the surprisingly complex question: when exactly do you start a "test application"?
Starting a Spring Boot application usually takes a few seconds, sometimes tens of seconds for more complex apps.
If you have a thousand tests, paying the startup cost a thousand times would mean your tests now take hours to run.
You might be able to re-use the same application across tests, but sometimes you may need to restart it because some tests demand a very specific setup.
And what if you want to test multiple scenarios, each with its own configuration details?
In that case, you add another layer of complexity, with multiple "test applications", each associated with the exact subset of tests that need a given configuration.

Third, you need to access the "test application(s)", to execute your test code and your verifications.
But since the tests themselves are not a Spring application, you cannot simply use the declarative, annotation-driven programming model you are familiar with.
Again, achieving this is straightforward but requires some boilerplate code.
You must also take the lifecycle of the application into consideration, to ensure beans are ready before you try and use them.
And you will be calling the method `ApplicationContext.getBean(...)` a lot.

Lastly, with your "test application" running, you'll probably end up copying and pasting a lot of code, or writing utility methods.
For example, the `RestClient` API for making HTTP requests is very versatile, and covers a wide range of production use-cases.
But when calling into your test application, most requests will look the same, and you probably won't need the flexibility.
So you'll likely write utility methods, possibly different per project, that every new engineer on the team will need to learn.
In listing <<ch1-listing-restclient>>, we show the code required to send an HTTP `POST` request, with a content type of `application/x-www-form-urlencoded`.
It requires using the verbose `LinkedMultiValueMap` class and setting the content type, which obscures the meaning of the test.
It would be better wrapped in some utility, where you could call, say, `post("uri", requestBody)`.

With the first three steps we mentioned above, configuration, setup and test, you are able to execute tests against a running application, swapping some beans for a stub.
We've seen that writing such tests is cumbersome, and requires advanced knowledge of the Spring Framework.
We have not explored all the ways things can go wrong when manually creating test applications.
But trust me, if you go down this path, you will run into many, many side effects that are specific to certain testing scenarios, and that you will need to handle one by one.

To recap, in the absence of dedicated Spring tooling for tests, here is a list of everything you'd need to think about:

- Configuring a version of your application suitable for testing, with appropriate properties, profiles or even configuration classes.
- Replacing beans selectively, for example to avoid connecting to external systems.
- Managing the lifecycle of the application in your tests, by starting and stopping it at appropriate times.
- Interacting with the running application using low level APIs, for example to access certain beans in the application context, or to get the port of the running server.
- Optionally, writing utility classes to make tests less verbose.

Luckily, Spring Boot does have helpful capabilities in tests.

In the world of Spring Boot, things "just work" out of the box.
You can enhance configuration and add your own components with just a few annotations.
This also applies to your test code.
Writing tests for the Widget application from <<ch1-section3>> requires much less code, and may look somewhat like the code in listing <<ch1-listing-test-configuration>>.

<2> Make HTTP calls to your application, without having to worry about the URL or the exact details about the body of the request.
<3> Assert that the response returns HTTP 201.
<4> Inspect the headers of the request.
<5> Ensure the widget is actually created in the repository.

The test is simpler and easier to read, with noticeable gains in the boilerplate, or lack thereof:

- You do not need to touch lower-lever Spring abstractions like the `ApplicationContext`.
- You do not need to think about the lifecycle of the application, with start and stop.
- The focus is on your test code, not on configuration: you express what is different in your test configuration compared to the "normal" configuration, which beans of the application you want to interact with, and Spring Boot Tests takes care of the rest for you.
- There are helpful utility methods and classes, such as `MockMvc`, with its simpler API and its ability to make assertions on the HTTP responses from your application.

== What you will learn in this book

In this book, you'll learn how to write tests for your Spring Boot applications.
Each chapter focuses on an aspect of testing, such as configuring the app under test, or testing the security layer, and demonstrates how you can use Spring Boot Tests for each use-case.
To get the most out of it, you must be familiar with Spring Framework and Spring Boot.
If you are not, consider reading a primer on the topic.
There are many great publications, but you could pick either _Spring In Action, Sixth Edition_ by Craig Walls (Manning, 2022) or _Spring Start Here_ by Laurențiu Spilcă (Manning, 2021).

You must also have some experience with writing tests in the first place.
You will not find general-purpose advice on writing tests, the philosophy of testing, or nuances between different testing techniques.
It is focused on Spring applications, and assumes you have written and executed automated tests before.
If you have not, you should get familiar with those concepts before focusing on Spring-specific content.
There are countless resources both in print and online.
For Java developers, a good starting point is _Pragmatic Unit Testing in Java with JUnit, Third Edition_, by Jeff Langr (The Pragmatic Programmers, 2024).

As it often is the case with Spring Boot, the first few steps in Spring Boot testing are deceptively simple.
You can achieve a lot very quickly with the `@SpringBootTest` annotation, without needing much context on how Boot works under the hood.
As we have seen with the examples in section <<ch1-section3>> and <<ch1-section4>>, Spring Boot Tests takes care of a lot of things in the background.
But it is just a set of abstractions, and, as the saying goes:

[QUOTE,Joel Spolsky,The Law of Leaky Abstractions]
____
All non-trivial abstractions, to some degree, are leaky.

Source: https://www.joelonsoftware.com/2002/11/11/the-law-of-leaky-abstractions/[]
____

This means that the more you use it, the more likely you will face one or more limitations of what comes "out-of-the box".
For example, your test suite might get unbearably slow.
In those cases, you need to know what's going on under the hood, so you can wield the abstraction properly—or even give up on using it altogether, when it does not make sense!

The second goal of this book is to help you get familiar with the lesser-known aspects of testing Spring applications, and guide you around the many pitfalls of "just" relying on the `@SpringBootTest` for all your tests.
You will learn the fundamentals, how the magic `@SpringBootTest` annotation works and what are the costs associated with it, and how to work around limitations.

The third goal is to introduce you to the testing libraries bundled with Spring Boot Test.
Some of these might be new to you, and you'll add new tools to your kit.
Others you may already know and use daily, but you may not be familiar with the full range of what they offer.
It's not possible to cover the full extent of several testing libraries in a single book, but I want to give you a glimpse of some of the cool things you can do with them and point you to next steps if you want to learn more.
This book will introduce the concepts and show you how to use them, highlight some lesser-known aspects, and explain how they can help you write elegant, stable, and better tests overall.

== Summary

- Spring Boot Starter Tests comes with "batteries included" and bundles all the core libraries used in a test suite: test runner, assertions and mocking, plus a few useful extras.
It provides integrations with testing libraries using the familiar Spring annotation-driven programming model.
- There exists a spectrum of types of tests, ranging from focused unit tests to external, black-box end-to-end tests, each with their dedicated ecosystem.
While the Spring Framework is versatile enough to allow you to write tests in the middle of that spectrum, it would require some non-trivial amount of boilerplate.
Spring Boot Tests offers a packaged solution to avoid that boilerplate, and write what we will call "Integration Tests".
- Spring Boot Tests manages the lifecycle of the application under test for you, and synchronizes it with your test classes.
It starts the app before executing any test, shuts down the application once the tests are done and performs any necessary clean up.
- Spring Boot Tests links your application to your test classes.
You can access beans in tests with `@Autowired` and perform actions or checks, such as verifying the state of your repositories.
You can also update the configuration and replace existing beans.
- There are tradeoffs to using Spring Boot Tests, and you should avoid using it as a silver bullet.
It's well-suited for testing user scenarios that exercise the full application, but becomes unwieldy for validating fine-grained conditional logic, or for tests that rely on a lot of state.
