= Spring Boot-specific test tooling

This chapter covers

* What's included in the "test" Spring Boot Starter
* How Spring and Boot help you write tests
* When to use Spring-specific testing tools

Testing applications and verifying that they have the intended behavior is an unavoidable aspect of the development lifecycle.
In any serious software engineering project, automating at least part of these tests is table stakes.
If you picked up this book, chances are you have already implemented extensive testing yourself, and you do not need to be convinced that you should, in fact, write tests.

Because it is such a foundational requirement in modern software engineering, many projects in the Spring portfolio cover testing.
These, of course, include both Spring Framework and Spring Boot.
Spring Framework brings the familiar declarative programming model to your test code, with annotations such as `@Autowired` or `@TestConfiguration`.
As for Spring Boot, it extends its core values of "convention over configuration" to tests, and enables you to set up tests without having to write complex, dedicated configuration.
Spring Boot also curates a list of test-focused dependencies, offering most of the tools you need to write tests, and ensures all the versions of these libraries work well together and integrate well with Spring code.

Like everything in the Spring ecosystem, those tools are very powerful and versatile, but come with tradeoffs.
Knowing when to use them, and, as importantly, when _not_ to use them, can have important implications, for example, on the speed of your test suite.

In this chapter, we will discuss the tools that Spring and Spring Boot offer to simplify testing.
You will discover with which types of tests these tools shine, and how they outperform manually crafting complex test cases.

[#ch1-section1, reftext={chapter}.{counter:section}, caption='{chapter}.{section}']
== What's "Spring Boot Testing"?

There is no such thing as an official "Spring Boot Test" project.
However, the Spring Boot project has a "starter" dependency specifically used for testing, called `spring-boot-starter-test`.
When you create a new project using the Spring Initializr, better known as https://start.spring.io , no matter which projects you select from the dropdown list, you get this starter as a dependency and an example test that uses the `@SpringBootTest` annotation.
The Spring Boot Starter Test project is the testing version of the Spring Boot "batteries included" approach: it contains a curated list of dependencies that will make writing tests easier, with dedicated tooling.

.The spring-boot-starter-test dependency in the pom.xml a typical Boot project

    <artifactId>spring-boot-starter-test</artifactId>

</dependencies>

<1> The dependencies are in the `test` scope

The starter pulls many useful test dependencies into the `test` scope of your project, as show on listing <<ch1-listing-pom-xml>>.
This means they cannot be used by your main application code, sometimes referred to as "production" code.

The libraries you get from the starter are broadly divided into two categories.

First, every dependency in the `org.springframework` and `org.springframework.boot` groups is Spring-specific tooling, created and maintained by the Spring team, with contributions from the Spring community.
It contains code specifically designed to simplify testing Spring and Spring Boot applications.
This is where you will find, for example:

- The `SpringExtension`, a JUnit extension that adds Spring-related behavior to JUnit.
It simplifies the lifecycle management of Spring applications by starting and stopping the Spring `ApplicationContext`, and allows you to easily configure and access Spring beans within your tests.
- The well-known `@SpringBootTest` annotation, which automatically detects your Spring Boot application's configuration classes and makes your code ready for testing.

These testing classes are the connective tissue between your application code and your test code, and make your *Spring* code easier to test.
In your code, you typically use them with annotation, rather than imperative calls: you put `@SpringBootTest` on your test classes and Spring does the lifecycle management for you, no need to write `SpringBootTest.run(...)`.

The second category of dependencies contains testing utilities that are not specific to Spring.
Just like in your production code, Spring Boot provides a list of curated dependencies that are useful in the most common scenarios.
It manages dependency versions to ensure that all these libraries work well together, and that they integrate without a hitch with your Spring code.
Here is a non-exhaustive list of the "goodies" you'll find in the toolkit:

- JUnit, the testing framework, with `org.junit.jupiter:junit-jupiter`.
This is where you will find your `@Test` annotation.
JUnit is the most popular testing framework in Java, no other framework even comes close.
For advanced JUnit usage, please refer to chapter 8, "Creating reusable test abstractions with JUnit".
- Two assertion libraries, Hamcrest (`org.hamcrest:hamcrest`) and AssertJ (`org.assertj:assertj-core`).
With these, you can write assertions that explain what your test expects to be true.
For example after "When I add one widget", you want to express "I expect the widget count to be 5".
With AssertJ, you would write in code: `assertThat(widgetCount).isEqualTo(5)`.
When the assertions are not fulfilled, the assertion framework throws a nice, human-readable exception.
Hamcrest is the "historical" library, and AssertJ has a more "modern" take on assertions.
In this book, all of our assertions will be written with AssertJ.
To learn more, please refer to chapter 10, "Writing elegant tests with Spring Boot’s bundled testing libraries".
- One "mocking" library, Mockito, with `org.mockito:mockito-core`.
Mocking allows you to easily create "fake" objects that have the same API as your classes, and customize their behavior.
This is useful for replacing classes with complex business logic.
For example, when you want to disconnect your tests from external dependencies such as databases or remote services and APIs, or when you want to treat some subset of your object graph as a black box that returns pre-determined results.
You can add behavior ("when the user calls widgetService.count(), return 5") as well as verifications ("verify that the emailService.sendEmail() was called once, with email user@example.com").
To learn more, please refer to chapter 10, "Writing elegant tests with Spring Boot’s bundled testing libraries".
- And a few other utilities, such as XMLUnit for checking properties on XML, JSONassert for checking properties on JSON, Awaitility for waiting on asynchronous conditions.
To learn more, please refer to chapter 10, "Writing elegant tests with Spring Boot’s bundled testing libraries".

These utilities are not related to Spring, and can be used in all your tests, including in your "business logic" tests that do not involve Spring.
You use them imperatively, for example by calling `Awaitility.await().until(() -> { /* ... */ });` or `assertThat(someResult).isEqualTo(42);`.

== When to use Spring Boot Test

For any given application, whether it was developed using Spring Boot or any other technology, there are many types of tests you can write.
They can be very low-level, centered on tiny pieces of business logic, focusing on a few classes or methods: those are unit tests.
They are deterministic, specific, and extremely fast to run, but they have a very narrow focus and do not give confidence that the system functions as a whole.
On the other end of the spectrum, you can deploy your application in a dedicated test or staging environment, with all its many dependencies, and execute a dedicated "testing" program against this running app.
Those are sometimes called end-to-end tests.
They ensure that the system works as expected from the highest level, from the user's perspective, but they are slower, more difficult to set up, and more fragile.
And there is a whole continuum of test types in between.

Spring Boot tests shine somewhere in the middle, for what I'd call "Integration Tests".
The term is not universally accepted, so it is worth defining it in the context of this book.
Integration tests typically involve many of the classes you have developed, and must include some capabilities of Spring, such as the web layer or the data layer.
They may cover your entire application, and include some external dependencies such as a database, but not your entire system with its many dependencies. Figure <<ch1-figure-02>> shows where Spring Boot tests are most useful.

[#ch1-figure-02, reftext={chapter}.{counter:figure}, caption='{figure-caption}.{counter:figure-number} ']
.The testing spectrum. On one end, unit tests that involve one or a few classes, and no Spring-specific code. On the other end, there are full-blown end-to-end tests, that may involve many complex components, that need tooling beyond the context of Spring. In between those two ends, there is a whole category of "integration tests".
image::ch01_f002_garniermoiroux.png[]

Spring Boot tests straddle the line between unit tests and end-to-end tests, getting the best of both worlds:

- They are reasonably fast to run, in the order of magnitude of a few seconds.
This is much slower than unit tests, but does not disrupt your development flow: you can get fast feedback whenever you make a change, without switching context.
- They focus on broad use-cases, beyond simply testing a method.
They ensure that components in your system collaborate correctly, and give confidence that the application works as a whole, more than unit tests would.
- They exercise all of your code, including Spring annotations and configuration.
They ensure that you have correctly programmed behavior, beyond the imperative statements within your methods.
For example, they validate application properties that Spring Boot uses for autoconfiguration of common libraries, that your `@ExceptionHandler` annotation covers the appropriate exceptions.
- They provide hooks into your production application code, to easily set up tests, and to run verifications.
For example, you can access the Spring JPA `@Repository` classes, and verify that some particular data is present after a given test.
- They do not try to interact with the application from a user's perspective.
This is the realm of end-to-end tests, which bring specific technology for simulating user behavior, and sometimes even specific, dedicated testing language to model scenarios.
- The tooling required to run them is limited in scope, and mostly independent of the architecture of your application or software system.
For example, you do not need to manage a full web browser and a webdriver.
Usually, having Java, and maybe a way to run Docker containers, is enough.
- They have no external dependencies, or very few.
You do not need to run and synchronize three separate microservices for your tests.
Instead, you provide "mocks" or "stubs" of your dependencies, with programmable behavior that simulates "real" dependencies.
As a result, they are reasonably easy to run in multiple environments: your local machine, your coworker's machine, the CI environment, ...
- They can test for some complex error conditions.
Specifically, any error condition from a mocked dependency can be simulated: timeouts, protocol errors, invalid data, ...
- They are usually fairly deterministic.
They have few moving pieces in the software under test, and few side effects.
For example, you do not have to deal with the asynchronous behavior and latency inherent to UI components, such as "wait until that element becomes visible".
A failure is a sign of an issue in your production code, not a network latency issue or a change in configuration in a third-party service.

With so many benefits, you could be tempted to use Spring Boot Test everywhere.
But, like everything in software engineering, there's no silver bullet for testing, and the approach comes with tradeoffs:

- They are slower to run than unit tests.
Incorrectly setting up the tests may lead to test suites that take minutes to run, if not hours.
- They cannot easily test all the possible scenarios of a given feature.
This is better done in unit tests, where you can control the inputs of every test with minimal friction, by wiring classes manually, and introducing stubs and mocks in your dependency graph.
- They cannot simulate all possible error conditions.
If you include a database in your tests, you can't simulate latency in the database connection.
- They are less specific than unit tests.
A failed test does not indicate precisely what in your code is wrong, and you may need to spend some time debugging before figuring out what the underlying problem is.
- They are more prone to test pollution, where running tests in a different order results in different outcomes.
You may need to write some cleanup code to run between tests, or ensure the data in your test is unique.
- While they give some confidence in how your app behaves, they may have blind spots in system behavior as a whole.
If a dependency that you mocked out changes its API, such as an external service changing the structure of its responses, it will break your application but the error will go undetected.
- Because they test the full depth of the program, you need to set up a lot of state to exercise a specific behavior.
For example, "GIVEN The user has three Widgets in their basket, AND they have a membership card, AND they have bought at least five Doodads in the past six months, BUT they never had a GoldenSale discount, THEN they have access to a GoldenSale 10% discount".
This may result in a lot of setup before a given test.

Given where they lie in the testing spectrum, Spring Boot Tests have their own unique set of constraints.
Writing tests for the scenarios mentioned above comes with particular challenges, and Spring provides specific tooling to make it easier for you.

== Why is Spring-specific tooling required?

When developers write their first Spring Boot tests, they get a lot of value out of the box, by using the `@SpringBootTest` annotation.
It's so ingrained in our practices that we never stop to think about it, and the exact benefits you get from Spring Boot Test is unclear.
To understand everything that you get for free, it might be worth exploring what a world without Spring Boot Test would look like.
What would it take to create and run the integration tests mentioned in section <<ch1-section2>>.

The Spring Framework provides powerful abstractions to connect different parts of an application.
With those abstractions, with just a few lines of declarative code, you can resolve component dependencies, decide which flavor of a specific interface should be used in some specific cases, turn off some components, etc.
Through the Spring `ApplicationContext`, you can discover, access and manipulate the "beans", or component instances, used throughout the application.
With those abstractions, you could create your own "test application" that looks a lot like your production application, save for a few test-specific changes, such as mocking out an external service or the data layer.
Then, you would programmatically run the app, and interact with the created beans inr your tests.
But if you tried to use the Spring Framework to do this manually, you would end up writing a lot of boilerplate code.
You would also face specific testing challenges managing multiple configurations for different tests.

To make sense of the code you would need to write, let's examine a concrete example.
The application is a fairly simple app, responsible for handling Widgets.
Users interact with the application by making HTTP requests.
The API is therefore exposed through a Spring REST Controller, `WidgetController`, and data is ultimately stored in a repository, `WidgetRepository`.
The `WidgetValidator` service represents an external service, used to validate Widgets before they are stored.
It has complex logic, and is difficult to run on a developer machine, so you want to avoid running it locally.
A simple class diagram in figure <<ch1-figure-03>> shows the dependency graph of these components.

[#ch1-figure-03, reftext={chapter}.{counter:figure}, caption='{figure-caption}.{counter:figure-number} ']

The first challenge is to configure the "test application".
Spring Boot gives you automatic configuration through the `@SpringBootApplication` annotation on your main class.
For example, by scanning the classpath, it discovers classes with Spring annotations, and adds them to the application context, as Spring beans.
It finds the `@Service WidgetValidator` that represents your external service, and makes it available in the application.
But we said that, for our test case, we would like to remove it!
Ideally, we would replace it by some "fake" `WidgetValidator` with custom behavior.
To avoid triggering this auto-discovery behavior, you cannot rely on the simple `@SpringBootApplication` annotation.
Instead, you need to create a custom configuration class, with your test-related configuration as well as the appropriate autoconfiguration that Spring Boot brings, while excluding configurations that are not relevant.
Even for a simple use-case, where we replace a single bean, the amount of configuration required to make it work quickly gets out of control.
And writing it requires advanced knowledge of Spring Framework, without Spring Boot.
An example of what such configuration would look like is available in listing <<ch1-listing-testconfiguration>>.
The exact content of the configuration is not relevant, but shows how much knowledge and effort would need to go into test-specific configuration, here with five distinct annotations.

Second, you have to manage the lifecycle of the "test application" manually.
You need to start the application before the tests, and to shut it down once the tests have completed.
While this is fairly straightforward, it means adding repetitive boilerplate code, to set up your test instance before running a test, and then tear it down once the tests have finished.
But it also begs the surprisingly complex question: when exactly do you start a "test application"?
Starting a Boot application usually takes a few seconds, sometimes tens of seconds for more complex apps.
If you have a thousand tests, paying the startup costs a thousand times would mean your tests now take hours to run.
You might be able to re-use the same application across tests, but sometimes you may need to restart it because some tests demand a very specific setup.
And what if you want to test multiple scenarios, each with some specific configuration details?
In that case, you add another layer of complexity, with multiple "test applications", each associated to the exact subset of tests that need a given configuration.

Third, you need to access the "test application(s)", to execute your test code and your verifications.
But since the tests themselves are not a Spring application, you cannot simply use the declarative, annotation-driven programming model you are familiar with.
Again, achieving this is straightforward but requires some boilerplate code.
You must also take the lifecycle of the application into consideration, to ensure beans are ready before you try and use them.
And you will be calling the method `ApplicationContext.getBean(...)` a lot.

And lastly, with your "test application" running, you will probably end up copy-pasting a lot of code, or writing utility methods.
For example, the `RestTemplate` API for making HTTP requests is very versatile, and covers a wide range of production use-cases.
But when calling into your test application, most requests will look the same, and you will probably not need the flexibility.
So you will likely write utility methods, possibly different per project, that every new engineer on the team will need to learn.
In listing <<ch1-listing-resttemplate>>, we show the code required to send an HTTP `POST` request, with a content type of `application/x-www-form-urlencoded`.
It requires using the verbose `LinkedMultiValueMap` class, and possibly a `RequestEntity`.
These obscure the meaning of the test, and would be better wrapped in some utility, where you could call, say `post("uri", requestBody)`.

With the first three steps we mentioned above, configuration, setup and test, you are able to execute tests against a running application, swapping some beans for a stub.
We've seen that writing such tests is cumbersome, and requires advanced knowledge of the Spring Framework.
We have not explored all the ways things can go wrong when manually creating test applications.
But trust me, if you go down this path you will run into many, many side effects that are specific to certain testing scenarios, and that you will need to handle one by one.

To recap, everything you would to think about if there was not dedicated Spring tooling for tests:

- Configuring a version of your application suitable for testing, with appropriate properties, profiles or even configuration classes.
- Replacing beans selectively, for example to avoid connecting to external systems.
- Managing the lifecycle of the application in your tests, by starting and stopping it at appropriate times.
- Interacting with the running application using low level APIs, for example to access certain beans in the application context, or to obtain the port of the running server.
- Optionally, writing utility classes to make tests less verbose.

The examples from the previous section are far from the delightful Spring Boot user experience that we've grown accustomed to!
Luckily, Spring Boot does have helpful capabilities in tests.

In the world of Spring Boot, things "just work" out of the box.
You can enhance configuration and add your own components with just a few annotations.
This also applies to your test code.
Writing tests for the Widget application from <<ch1-section3>> requires much less code, and may look somewhat like the code in listing <<ch1-listing-test-configuration>>.

The configuration above is much clearer than the complicated config class we wrote in the previous section.
Using the usual annotation-driven programming model, you can access beans in your application, register or swap beans.
With the `@SpringBootTest` annotation, you declare this a test of your entire Spring Boot application, and that you want to tweak certain properties just for testing.
With `@Autowired`, you can access beans in the application context to perform actions or verifications.
Replacing a production bean with a test-specific mock can be done with a single `@MockitoBean` annotation.
The code for the test itself would not be very different in both cases.

For example, you can set the body of the request by simply using `.param("key", "value")`.
Similarly, you can use `.andExpect(status().isCreated())` to verify that the return code of the HTTP request is `201 Created`.

The test is simpler and easier to read, with noticeable gains in the boilerplate, or lack thereof:

- You do not need to touch lower-lever Spring abstractions like the `ApplicationContext`.
- You do not need to think about the lifecycle of the application, with start and stop.
- The focus is on your test code, not on configuration: you express what is different in your test configuration compared to the "normal" configuration, which beans of the application you want to interact with, and Spring Boot Test take care of the rest for you.
- There are helpful utility methods and classes, such as `MockMvc`, with its simpler API and its ability to make assertions on the HTTP responses from your application.

== What you will learn in this book

First and foremost, this book offers a hands-on approach to learning how to write tests for your Spring Boot applications.
To get the most out of it, you must be familiar with Spring Framework and Spring Boot.
If you are not, consider reading a primer on the topic.
There are many great publications, but you could pick either _Spring In Action, Sixth Edition_ by Craig Walls (Manning, 2022) or _Spring Start Here_ by Laurențiu Spilcă (Manning, 2021).

You must also have some experience with writing tests in the first place.
You will not find general-purpose advice on writing tests, the philosophy of testing, or nuances between different testing techniques.
It is focused on Spring applications, and assumes you have written and executed automated tests before.
If you have not, you should get familiar with those concepts before focusing on Spring-specific content.
There are countless resources both in print and online.
For Java developers, a good starting point is _Pragmatic Unit Testing in Java with JUnit, Third Edition_, by Jeff Langr (The Pragmatic Programmers, 2024).

As it often is the case with Spring Boot, the first few steps in Spring Boot testing are deceptively simple.
You can achieve a lot very quickly with the `@SpringBootTest` annotation, without needing much context on how Boot works under the hood.
As we have seen with the examples in section <<ch1-section3>> and <<ch1-section4>>, Spring Boot Test takes care of a lot of things in the background.
But it is just a set of abstractions, and, as the saying goes:

[QUOTE,Joel Spolsky,The Law of Leaky Abstractions (https://www.joelonsoftware.com/2002/11/11/the-law-of-leaky-abstractions/)]
____
All non-trivial abstractions, to some degree, are leaky.
____

This means that the more you use it, the more likely you will face one or more limitation of what comes "out-of-the box".
For example, your test suite might get unbearably slow.
In those cases, you need to know what's going on under the hood, so you can wield the abstraction properly - or even give up on using altogether, when it does not make sense!

The second goal of this book is to help you get familiar with the lesser-known aspects of testing Spring applications, and guide you around the many pitfalls of "just" relying on the `@SpringBootTest` for all your tests.
You will learn the fundamentals, how the magic `@SpringBootTest` works and what are the costs associated with it, and how to work around limitations.

The third goal is to give you an introduction to the testing libraries that are bundled with Spring Boot Test.
While you may use some or all of those libraries daily, you might not know the full depth of their scope and how they can help you write elegant, stable and overall better tests.

== Summary

- Spring Boot Starter Tests comes with "batteries included" and bundles all the core libraries used in a test suite: test runner, assertions and mocking, plus a few useful extras.
- There exists a spectrum of types of tests, ranging from focused unit tests to external, black-box end-to-end tests, each with their dedicated ecosystem.
- While the Spring Framework is versatile enough to allow you to write tests in the middle of that spectrum, it would require some non-trivial amount of boilerplate.
- Spring Boot Test offers a packaged solution to avoid that boilerplate, and write what we will call "Integration Tests".
- Spring Boot also provides you with familiar programming paradigms to write your tests, such as configuring your application through annotations.
